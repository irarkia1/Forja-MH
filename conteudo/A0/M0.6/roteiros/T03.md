# M0.6.T03 — Memória: pilha, heap, estático, `volatile`, `const`

## Ao final você consegue
- Classificar onde cada variável vive (pilha, heap, estático; .text, .rodata, .data, .bss) e qual é o seu tempo de vida.
- Prever o comportamento de variáveis locais static, globais e automáticas, e da inicialização padrão de cada uma.
- Usar malloc/free corretamente e justificar por que firmware de microcontrolador costuma evitar a heap.
- Explicar quando usar volatile (registradores mapeados em memória, variáveis alteradas por interrupção) e const, e o que cada um garante e não garante.

## Resumo
**1. Mapa de memória de um programa.**

| Região | O que guarda | No PC | No microcontrolador |
|---|---|---|---|
| `.text` | código | só leitura | flash |
| `.rodata` | `const` globais, literais de string | só leitura | flash |
| `.data` | globais e `static` **com** valor inicial ≠ 0 | RAM | RAM (valor inicial copiado da flash no boot) |
| `.bss` | globais e `static` sem inicializador (ou = 0) | RAM, zerada | RAM, zerada pelo código de partida |
| heap | `malloc`/`calloc` | cresce sob demanda | área fixa, geralmente pequena |
| pilha (*stack*) | variáveis locais, parâmetros, endereço de retorno | MBs | poucos KB |

O comando `size programa` (ou `size arquivo.o`) mostra `text`, `data` e `bss`. Num MCU, **flash** usada ≈ text + data; **RAM estática** ≈ data + bss (o resto da RAM é para pilha e heap). Uma tabela grande sem `const` vai para `.data` e gasta RAM **e** flash; com `const`, vai para `.rodata` e fica só na flash.

**2. Duração e escopo.** *Escopo* é onde o nome é visível; *duração* (tempo de vida) é quando o objeto existe.
- **Automática** (variável local comum): nasce ao entrar no bloco e morre ao sair; **não é inicializada** — o valor é indeterminado até a primeira atribuição.
- **Estática** (global, ou local com `static`): existe durante todo o programa e é inicializada **uma vez**, antes do `main`, com zero se não houver inicializador.
```c
int conta(void)
{
    static int n = 0;   /* inicializada uma vez; mantém o valor entre chamadas */
    int a = 0;          /* recriada a cada chamada                              */
    n++; a++;
    return n * 10 + a;  /* 1ª: 11, 2ª: 21, 3ª: 31                              */
}
```
`static` numa **global** muda outra coisa: o nome fica visível só naquele arquivo (linkage interna, T06).
- **Alocada**: da heap, existe de `malloc` até `free`.

**3. Pilha.** Cada chamada de função empilha um quadro (*frame*) com parâmetros, locais e endereço de retorno — é o que o `bt` do GDB mostra. Num microcontrolador a pilha tem poucos KB e **não há proteção**: um array local grande ou uma recursão profunda passam por cima de `.bss` ou da heap em silêncio. `gcc -fstack-usage` gera arquivos `.su` com o uso de pilha de cada função.

**4. Heap: `malloc`/`free`.**
```c
uint8_t *buf = malloc(n);          /* conteúdo indeterminado; calloc(n, 1) zera  */
if (buf == NULL) { /* trate a falta de memória */ }
/* ... usa buf[0] .. buf[n-1] ... */
free(buf);                         /* uma vez, e só o que veio do malloc          */
buf = NULL;                        /* evita usar ou liberar de novo por engano     */
```
Erros: esquecer o `free` (vazamento), `free` duas vezes (*double free*), usar depois do `free` (*use after free*), escrever além de `n`. `free(NULL)` é permitido e não faz nada. O AddressSanitizer (T09) detecta todos esses erros, inclusive vazamentos.

**Por que firmware evita a heap**: (1) **fragmentação** — depois de muitos `malloc`/`free` de tamanhos diferentes, pode não haver um bloco contínuo do tamanho pedido, mesmo com memória livre suficiente no total; (2) **tempo não determinístico** — o `malloc` procura um bloco, e o tempo varia; (3) a falha aparece **em campo**, horas depois, e não há o que fazer quando `malloc` devolve `NULL` dentro de uma interrupção; (4) a RAM é pequena e não há sistema operacional para "matar" o processo. Por isso as regras de codificação (MISRA C, T11) proíbem a alocação dinâmica, e o padrão é **alocação estática**: buffers globais `static` de tamanho fixo, *pools* de blocos iguais, ou alocar tudo uma vez na inicialização e nunca liberar.

**5. `volatile`.** Diz ao compilador: "este objeto pode mudar (ou ser lido) por algo que você não vê; faça **cada** leitura e escrita de verdade, na ordem do código". Sem `volatile`, o otimizador pode guardar o valor num registrador e nunca mais ler a memória:
```c
int pronto = 0;                  /* alterada por uma interrupção (ou um sinal, no PC) */
while (!pronto) { }              /* com -O2, vira um laço infinito: pronto é lido uma vez só */

volatile int pronto2 = 0;        /* agora cada volta lê a memória                      */
```
Use `volatile` em: **registradores de periférico** (a leitura do registrador de status muda sozinha; escrever duas vezes no registrador de dados envia dois bytes), **variáveis compartilhadas com interrupção**, e laços de espera que o otimizador não pode remover. Registrador mapeado em memória:
```c
#define GPIOA_ODR (*(volatile uint32_t *)0x40020014u)   /* STM32F4: saída do GPIOA */
GPIOA_ODR |= (1u << 5);                                   /* liga o pino PA5 (T05)    */
```
O que `volatile` **não** faz: não torna `contador++` atômico (é ler, somar e escrever — uma interrupção no meio perde uma contagem), não impede que a CPU reordene acessos em processadores com cache, e não substitui desligar interrupções, operações atômicas ou mutex. Para variáveis compartilhadas com um tratador de sinal no PC, a norma prevê `volatile sig_atomic_t`.

**6. `const`.** Promete que o programa não altera o objeto **por aquele nome** — o compilador recusa a escrita. Benefícios: documenta a intenção, pega erros e, em variáveis globais, coloca o dado na flash. Não garante que o valor nunca muda: `volatile const uint32_t *STATUS` descreve um registrador que **o seu código** não pode escrever, mas o **hardware** muda a qualquer momento. Em C, uma variável `const int N = 10;` **não** é uma constante de compilação (não serve como rótulo de `case`); para isso use `enum` ou `#define` (T06), ou `constexpr` em C++ (T08).

## Pratique
Use `~/treino-c/t03/`.
1. Escreva um programa com uma global inicializada, uma global sem inicializador, uma `const` global, uma local `static` e uma local comum. Imprima o endereço de cada uma (`%p`) e de uma função. Agrupe por região.
2. Rode `size` no `.o` antes e depois de acrescentar `static uint8_t buffer[1024];`. Depois troque por `static uint8_t buffer[1024] = {1};`. Que coluna muda em cada caso?
3. Escreva a função `conta()` do resumo e chame-a três vezes. Preveja os valores antes de rodar.
4. Leia uma variável local sem inicializá-la, compilando com `-O2 -Wall`. Leia o aviso. Rode com `-O0` e `-O2`: os valores coincidem?
5. Aloque um array com `malloc`, preencha, imprima e libere. Rode com `-fsanitize=address`. Depois tire o `free` e veja o relatório de vazamento.
6. Provoque um *use after free* e um *double free* e leia o que o AddressSanitizer diz em cada caso.
7. No PC, simule a interrupção com um sinal: `signal(SIGALRM, h); alarm(1); while (!pronto) { }`, com o tratador `h` fazendo `pronto = 1`. Compile com `-O2` com e sem `volatile` (`volatile sig_atomic_t pronto`). Use `timeout 3 ./prog` para não travar o terminal.
8. Compile o laço do exercício 7 com `-O2 -S` e procure no `.s` a diferença entre as versões (sem `volatile`, não há leitura da memória dentro do laço).
9. Escreva `void preenche(void) { uint8_t grande[200000]; ... }` e compile com `-fstack-usage`. Quanto o `.su` indica? Isso caberia num ATmega328P (2 KB de RAM)?
10. Declare `const uint16_t tabela[256] = {1, 2, 3};` (global) e depois a mesma tabela sem `const`. Compare `size` do `.o` nos dois casos.

## Armadilhas comuns
- Achar que local não inicializada vale 0 (só globais e `static` começam zeradas).
- Inicializar uma `static` local achando que a inicialização roda a cada chamada.
- `malloc` sem testar `NULL`; `free` duplicado; usar o ponteiro depois do `free`; esquecer o `free` no caminho de erro.
- Usar heap em firmware com laço de `malloc`/`free` de tamanhos variados (fragmentação que só aparece depois de dias ligado).
- Array local enorme numa função de MCU (estouro de pilha silencioso).
- Esquecer `volatile` em flag alterada por interrupção ("funciona em -O0, trava em -O2").
- Achar que `volatile` resolve condição de corrida (`contador++` continua não atômico).
- Tabela constante sem `const`: ocupa RAM à toa.
- Achar que `const` faz uma variável virar constante de compilação em C.

## Gabarito
1. Função, `const` e literais ficam em endereços baixos (text/rodata); globais e `static` logo acima (data/bss); a local, num endereço alto (pilha, perto de `0x7ffc…` no x86-64).
2. Sem inicializador: só `bss` cresce (+1024 no `.o`). Com `= {1}`: o array vai para `.data` (+1024 em `data`) — agora os 1024 bytes de valor inicial precisam ficar gravados no executável (na flash, num MCU).
3. 11, 21, 31.
4. `warning: 'x' is used uninitialized`. Os valores podem diferir: ler a variável é comportamento indefinido — não há "valor certo".
5. Sem `free`: `ERROR: LeakSanitizer: detected memory leaks` com o tamanho e a linha do `malloc`.
6. `heap-use-after-free` e `attempting double-free`, cada um com a linha do erro e as linhas do `malloc` e do `free`.
7. Sem `volatile`, com `-O2`, o programa não termina (o `timeout` o mata, código 124); com `volatile`, imprime e sai após 1 s.
8. Sem `volatile`, o laço vira um salto para si mesmo (`jmp .L…`) sem nenhuma leitura; com `volatile`, há um `mov` da variável a cada volta.
9. Cerca de 200 000 bytes de pilha — 100 vezes a RAM inteira do ATmega328P. Num MCU, use um buffer `static` de tamanho adequado.
10. Sem `const`: `data` = 512 (a tabela vai para `.data`, ocupando RAM). Com `const`: `data` = 0 e `text` cresce cerca de 512 bytes (o `size` soma `.rodata` ao `text`) — num MCU, a tabela fica só na flash.
