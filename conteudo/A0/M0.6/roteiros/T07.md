# M0.6.T07 — Make e CMake

> Vem logo depois do T06 porque Make e CMake só automatizam o que você já fez à mão: compilar cada `.c` em `.o` e ligar os objetos. Quem entende as etapas entende os erros do sistema de build.

## Ao final você consegue
- Escrever um Makefile com alvos, dependências, receitas e variáveis (CC, CFLAGS) e prever quais arquivos são recompilados.
- Usar variáveis automáticas ($@, $<, $^), regras de padrão e alvos .PHONY (all, clean).
- Escrever um CMakeLists.txt com add_executable, add_library, target_include_directories e target_link_libraries.
- Configurar e compilar um projeto CMake fora da árvore de fontes, escolhendo o tipo de build (Debug/Release) e integrando os testes com CTest.

## Resumo
**1. A regra do Make.**
```make
alvo: pré-requisitos
	receita (cada linha começa com um TAB, não com espaços)
```
O Make compara datas de modificação: refaz o **alvo** se ele não existe ou se algum **pré-requisito** é mais novo, e faz isso recursivamente (os pré-requisitos são alvos de outras regras). Sem argumentos, `make` constrói o **primeiro** alvo do arquivo. Espaços no lugar do TAB dão `*** missing separator. Stop.`
```make
CC     = gcc
CFLAGS = -std=c11 -Wall -Wextra -g

app: main.o sensor.o
	$(CC) $^ -o $@

main.o: main.c sensor.h
	$(CC) $(CFLAGS) -c $< -o $@

sensor.o: sensor.c sensor.h
	$(CC) $(CFLAGS) -c $< -o $@
```
Depois de um build completo: mexer em `sensor.c` refaz só `sensor.o` e o link (2 comandos); mexer em `sensor.h` refaz os dois `.o` e o link (3). Se as regras **não** listarem o `sensor.h`, mexer nele não refaz nada (`'app' is up to date`) — e o executável fica com código velho, um defeito silencioso.

**2. Variáveis e regras de padrão.**
- `$@` = o alvo; `$<` = o **primeiro** pré-requisito; `$^` = **todos** os pré-requisitos (sem repetições).
- `%.o: %.c` é uma regra de padrão: vale para qualquer `.o` feito do `.c` de mesmo nome.
- `=` expande na hora do uso (recursiva); `:=` expande na hora da definição (simples). `?=` só define se ainda não existir. Na linha de comando, `make CFLAGS=-O2` sobrescreve.
- Referência de substituição: `OBJS := $(SRCS:.c=.o)` troca `.c` por `.o` em cada palavra.
- O Make já tem regras embutidas (`%.o: %.c` usa `$(CC) $(CPPFLAGS) $(CFLAGS) -c`) — por isso os nomes `CC`, `CFLAGS`, `CPPFLAGS`, `LDFLAGS` e `LDLIBS` são convenção.
- `.PHONY: all clean test` declara alvos que **não** são arquivos: `make clean` roda sempre, mesmo que exista um arquivo chamado `clean`.

Um Makefile de projeto, com dependências de header automáticas:
```make
CC      := gcc
CFLAGS  := -std=c11 -Wall -Wextra -g -MMD -MP -Iinclude
LDLIBS  := -lm
SRCS    := src/main.c src/sensor.c src/filtro.c
OBJS    := $(SRCS:.c=.o)

.PHONY: all clean
all: app

app: $(OBJS)
	$(CC) $(LDFLAGS) $^ -o $@ $(LDLIBS)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)        # os .d gerados por -MMD listam os headers de cada .c

clean:
	rm -f app $(OBJS) $(OBJS:.o=.d)
```
Comandos úteis: `make -n` (mostra o que faria, sem fazer), `make -j8` (8 tarefas em paralelo), `make -B` (refaz tudo), `make V=1`/`VERBOSE=1` em builds que escondem os comandos.

**3. CMake.** O CMake não compila: ele **gera** o sistema de build (Makefiles ou Ninja) a partir de uma descrição de alto nível, e funciona igual no Linux, no Windows e para compilação cruzada (no A1, com um *toolchain file* para `arm-none-eabi-gcc`; o ESP-IDF é todo baseado em CMake).
```cmake
cmake_minimum_required(VERSION 3.16)
project(forja LANGUAGES C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

add_library(sensor STATIC src/sensor.c)                 # biblioteca: libsensor.a
target_include_directories(sensor PUBLIC include)        # quem usar sensor também enxerga include/
target_link_libraries(sensor PRIVATE m)                  # libm só para a implementação

add_executable(app src/main.c)
target_link_libraries(app PRIVATE sensor)                # herda o include/ (PUBLIC) do sensor
target_compile_options(app PRIVATE -Wall -Wextra)

enable_testing()
add_executable(testes tests/teste_sensor.c)
target_link_libraries(testes PRIVATE sensor)
add_test(NAME testes COMMAND testes)                     # o ctest roda e confere o código de saída
```
- **Alvos** (`app`, `sensor`, `testes`) carregam suas propriedades; prefira sempre os comandos `target_*` aos globais (`include_directories`, `CMAKE_C_FLAGS`).
- **PRIVATE**: só para o próprio alvo. **PUBLIC**: para o alvo e para quem se liga a ele. **INTERFACE**: só para quem se liga (bibliotecas só de header).
- `target_link_libraries(app PRIVATE m)` liga a libm; não ponha `-lm` em flags de compilação.

**4. Configurar, compilar, testar.** Sempre **fora** da pasta dos fontes (*out-of-source*): tudo o que é gerado fica em `build/`, que vai para o `.gitignore`.
```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug     # configura (uma vez, ou quando mudar o CMakeLists)
cmake --build build -j                           # compila (chama make ou ninja por você)
ctest --test-dir build --output-on-failure       # roda os testes registrados com add_test
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release   # outra pasta, outra configuração
```

| `CMAKE_BUILD_TYPE` | Flags padrão do gcc |
|---|---|
| `Debug` | `-g` |
| `Release` | `-O3 -DNDEBUG` |
| `RelWithDebInfo` | `-O2 -g -DNDEBUG` |
| `MinSizeRel` | `-Os -DNDEBUG` |

Repare no `-DNDEBUG`: em Release, os `assert` **somem**. Testes que dependem de `assert` precisam ser compilados em Debug (ou usar um framework de testes, T10). `-G Ninja` troca o gerador (mais rápido); `cmake --build build --target clean` limpa.

## Pratique
Use `~/treino-c/t07/` com `main.c`, `sensor.c`, `sensor.h` (do T06).
1. Escreva o Makefile do item 1 do resumo (com TAB). Rode `make` duas vezes: o que a segunda diz?
2. Faça `touch sensor.c` e `make`; depois `touch sensor.h` e `make`. Conte os comandos executados em cada caso.
3. Tire o `sensor.h` das regras e repita o `touch sensor.h`. O que acontece? Por que isso é perigoso?
4. Troque as regras de `.o` por uma regra de padrão `%.o: %.c` e use `SRCS`/`OBJS` com substituição. Confira com `make -n`.
5. Acrescente `-MMD -MP` e `-include $(OBJS:.o=.d)`. Abra um `.d` e explique o conteúdo. Repita o exercício 3.
6. Crie um arquivo chamado `clean` na pasta e rode `make clean` sem e com `.PHONY`.
7. Rode `make CFLAGS="-O2 -Wall"` e veja os comandos.
8. Converta o projeto para CMake (estrutura `src/`, `include/`, `tests/`) com uma biblioteca `sensor` e o executável `app`.
9. Troque `PUBLIC` por `PRIVATE` no `target_include_directories(sensor …)` e compile. Qual erro aparece em `main.c`?
10. Acrescente um executável de teste com `assert` e registre-o com `add_test`. Rode `ctest` em Debug e em Release, com um `assert` que falha. O resultado muda? Por quê?
11. Gere com `-G Ninja` (instale `ninja-build`) e compare o tempo de um build do zero.
12. Escreva um alvo `test` no Makefile que compila e roda os testes, e marque-o como `.PHONY`.

## Armadilhas comuns
- Espaços no lugar do TAB na receita (`missing separator`).
- Não listar os headers como dependências: mudanças no `.h` não recompilam nada.
- Esquecer `.PHONY` em `clean`/`all`/`test`.
- Confundir `$<` (só o primeiro pré-requisito) com `$^` (todos).
- Compilar CMake dentro da pasta dos fontes (`cmake .`) e sujar o repositório; não pôr `build/` no `.gitignore`.
- Usar `include_directories` e `CMAKE_C_FLAGS` globais em vez dos comandos `target_*`.
- Achar que o CMake "compila": depois de mudar o `CMakeLists.txt`, o `cmake --build` reconfigura sozinho, mas variáveis em cache (`-D…`) persistem entre execuções — às vezes é preciso apagar o `build/`.
- Rodar testes com `assert` em Release (`-DNDEBUG`) e achar que passaram.

## Gabarito
1. `make: 'app' is up to date.` — nada mudou desde o último build.
2. `touch sensor.c`: 2 comandos (compila `sensor.o` e liga). `touch sensor.h`: 3 (os dois `.o` e o link).
3. `'app' is up to date`: o executável continua com o código antigo, embora o header tenha mudado (ex.: uma constante ou o layout de uma struct). Pode gerar defeitos que somem com `make clean`.
4. `%.o: %.c` com `$(CC) $(CFLAGS) -c $< -o $@`; `make -n` lista os comandos sem executá-los.
5. O `main.d` contém `main.o: main.c sensor.h` e, por causa do `-MP`, uma regra vazia `sensor.h:` (evita erro se o header for apagado). Agora o `touch sensor.h` recompila.
6. Sem `.PHONY`: `make: 'clean' is up to date.` (o arquivo existe e não tem pré-requisitos). Com `.PHONY`, a receita roda.
7. `gcc -O2 -Wall -c main.c -o main.o` etc.: a variável da linha de comando sobrescreve a do Makefile.
8. Use o `CMakeLists.txt` do resumo; `cmake -S . -B build && cmake --build build`.
9. `fatal error: sensor.h: No such file or directory` ao compilar `main.c`: com `PRIVATE`, o caminho `include/` vale só para a própria biblioteca.
10. Em Debug, o teste falha (o `assert` aborta e o ctest acusa *Subprocess aborted*); em Release, o `-DNDEBUG` remove o `assert` e o teste "passa".
11. O Ninja costuma ser mais rápido, sobretudo em rebuilds incrementais.
12. `test: testes` com receita `./testes`; `.PHONY: test`.
