O resultado é a primeira biblioteca do seu firmware — o buffer circular vai receber os bytes da UART no A1.

- Aplicar o ciclo do TDD (vermelho, verde, refatorar) e isolar o código de hardware atrás de uma interface para testá-lo no PC.

## Resumo
**1. Por que testar no PC.** Um teste unitário exercita uma unidade pequena (uma função, um módulo) isolada do resto, de forma automática e repetível. No PC, o ciclo editar → compilar → testar leva segundos, há GDB e AddressSanitizer, e o mesmo teste roda a cada commit. Grenning chama isso de *dual targeting*: o mesmo código C compilado para o PC (testes) e para o microcontrolador (produto). Só o que toca registradores precisa da placa — e mesmo isso pode ser isolado (item 5).

**2. O Unity.** Framework de testes em C puro, com três arquivos (`unity.c`, `unity.h`, `unity_internals.h`), feito para embarcados. Um arquivo de teste:
```c
#include "unity.h"
#include "buffer_circular.h"

static bc_t b;
static uint8_t mem[4];

void setUp(void)    { TEST_ASSERT_TRUE(bc_inicia(&b, mem, sizeof mem)); }   /* antes de CADA teste */
void tearDown(void) { }                                                      /* depois de CADA teste */

static void test_novo_buffer_esta_vazio(void)
{
    TEST_ASSERT_TRUE(bc_vazio(&b));
    TEST_ASSERT_EQUAL_UINT32(0, bc_quantidade(&b));
}

static void test_retira_o_que_colocou(void)
{
    uint8_t v = 0;
    TEST_ASSERT_TRUE(bc_coloca(&b, 42));
    TEST_ASSERT_TRUE(bc_retira(&b, &v));
    TEST_ASSERT_EQUAL_UINT8(42, v);          /* (esperado, obtido) — nessa ordem */
}

int main(void)
{
    UNITY_BEGIN();
    RUN_TEST(test_novo_buffer_esta_vazio);
    RUN_TEST(test_retira_o_que_colocou);
    return UNITY_END();                      /* devolve o número de falhas: 0 = sucesso */
}
```
Saída:
```
tests/test_buffer_circular.c:20:test_novo_buffer_esta_vazio:PASS
tests/test_buffer_circular.c:28:test_retira_o_que_colocou:FAIL: Expected 42 Was 41

-----------------------
2 Tests 1 Failures 0 Ignored
FAIL
```
- Asserções mais usadas: `TEST_ASSERT_TRUE/FALSE`, `TEST_ASSERT_EQUAL_INT`, `_UINT8`, `_UINT32`, `_HEX8` (mostra a falha em hexadecimal), `TEST_ASSERT_EQUAL_UINT8_ARRAY(esperado, obtido, n)`, `TEST_ASSERT_EQUAL_STRING`, `TEST_ASSERT_NULL`/`NOT_NULL`, `TEST_ASSERT_BITS(mascara, esperado, obtido)`, `TEST_ASSERT_FLOAT_WITHIN(delta, esperado, obtido)` e as versões `_MESSAGE` (com um texto explicativo). `TEST_IGNORE()` marca um teste como pendente.
- Quando uma asserção falha, **o resto daquele teste não roda** (o Unity salta para o fim do teste); o `tearDown` roda e o próximo teste começa do zero, com novo `setUp`. Por isso cada teste deve ser independente dos outros.
- `UNITY_END()` devolve o número de falhas; o `main` o retorna, e o código de saída diferente de zero é o que o CTest, o Make e o CI usam para saber que algo falhou. Diferente do `assert` (T07), as asserções do Unity não somem com `-DNDEBUG`.

**3. A biblioteca: buffer circular (FIFO) de bytes.** Uma fila de tamanho fixo sobre um array; quando o índice chega ao fim, volta ao começo. É o que a interrupção da UART usa para guardar bytes até o laço principal lê-los.
```c
typedef struct {
    uint8_t *dados;       /* memória fornecida por quem usa — sem malloc (T03) */
    size_t   capacidade;
    size_t   inicio;      /* índice do elemento mais antigo */
    size_t   quantidade;
} bc_t;

bool   bc_inicia(bc_t *b, uint8_t *memoria, size_t capacidade);  /* false se argumentos inválidos */
bool   bc_coloca(bc_t *b, uint8_t valor);                         /* false se cheio: não sobrescreve */
bool   bc_retira(bc_t *b, uint8_t *saida);                        /* false se vazio: *saida intacta */
bool   bc_vazio(const bc_t *b);
bool   bc_cheio(const bc_t *b);
size_t bc_quantidade(const bc_t *b);
```
Posição de escrita: `(inicio + quantidade) % capacidade`; ao retirar, `inicio = (inicio + 1) % capacidade`. Guardar a **quantidade** resolve a ambiguidade clássica da versão com dois índices (`cabeca == cauda` pode significar vazio ou cheio); a alternativa sem contador sacrifica uma posição: "cheio" quando `(cauda + 1) % N == cabeca`, e cabem só N − 1 elementos. Decida e documente o que acontece no cheio: **recusar** o novo (o que esta API faz) ou **sobrescrever** o mais antigo (útil para logs).

**Lista de testes** (escreva antes de programar — Grenning, cap. 3 e 4): novo buffer está vazio e não cheio; colocar um e retirar devolve o mesmo valor; ordem FIFO com vários; encher até a capacidade → `cheio`; colocar no cheio devolve `false` e **não** altera o conteúdo; retirar do vazio devolve `false` e não altera `*saida`; a quantidade acompanha cada operação; **volta do índice** (encher, retirar alguns, colocar de novo, conferir a ordem); capacidade 1; argumentos inválidos (`NULL`, capacidade 0). Os defeitos moram nas **bordas**: vazio, cheio, último índice, volta.

**4. TDD — vermelho, verde, refatorar.** (1) Escreva **um** teste pequeno para o próximo comportamento e veja-o **falhar** (vermelho) — isso prova que o teste testa algo; (2) escreva o **mínimo** de código para ele passar (verde), mesmo que pareça ingênuo; (3) **refatore** (melhore nomes, tire duplicação) com todos os testes verdes. Repita em ciclos de minutos. Os testes viram uma especificação executável e uma rede de segurança para mudanças.

**5. Isolar o hardware.** O código que decide (quando ligar, quanto esperar, o que fazer com um byte) não deve conversar com registradores diretamente; ele chama uma **interface**:
```c
/* gpio.h — a interface */
void gpio_escreve(uint8_t pino, bool nivel);

/* gpio_stm32.c — produção: escreve no registrador (só compila para o MCU)   */
/* gpio_fake.c  — testes: guarda as chamadas numa variável que o teste lê     */
static bool ultimo_nivel[16];
void gpio_escreve(uint8_t pino, bool nivel) { ultimo_nivel[pino] = nivel; }
bool gpio_fake_nivel(uint8_t pino) { return ultimo_nivel[pino]; }
```
O alvo de testes liga com `gpio_fake.c`; o firmware, com `gpio_stm32.c` (*substituição no link*, Grenning cap. 7). Outras técnicas: ponteiros para função escolhidos em tempo de execução (cap. 9) e passar o endereço do "registrador" como parâmetro, para o teste usar uma variável comum no lugar (cap. 8: o *spy* do driver de LEDs). Esse dublê (*test double*) deixa você testar a lógica no PC, rápido, sem placa.

**6. Cobertura com gcov.** Compile e ligue com `--coverage` (equivale a `-fprofile-arcs -ftest-coverage`), rode os testes e peça o relatório:
```bash
gcc -std=c11 -g -O0 --coverage -Iinclude -Ivendor/unity/src -c src/buffer_circular.c -o buffer_circular.o
gcc ... (compile os testes e o unity.c do mesmo jeito) ...
gcc --coverage buffer_circular.o test_buffer_circular.o unity.o -o testes
./testes
gcov -b buffer_circular.c        # resumo + buffer_circular.c.gcov anotado
```
```
Lines executed:100.00% of 24
Branches executed:100.00% of 10
Taken at least once:100.00% of 10
```
- **Cobertura de linhas**: quais linhas executaram ao menos uma vez; no `.gcov`, `#####` marca as que **nunca** rodaram.
- **Cobertura de desvios** (`-b`): cada `if`, `&&`, `||` e `?:` tem dois lados; "taken at least once" mostra a porcentagem de lados que ocorreram. Linhas a 100 % com desvios a 75 % significa que alguma condição nunca foi verdadeira (ou nunca falsa) nos testes.
- Use `-O0` para medir (a otimização embaralha as linhas). Ao compilar e ligar num comando só, o gcc 14 prefixa os `.gcda` com o nome do executável (`testes-buffer_circular.gcda`); compilar com `-c` em separado evita a confusão. Com CMake, `target_compile_options(... --coverage)` e `target_link_options(... --coverage)` num tipo de build próprio, e o `gcovr` (`pip install gcovr`; `gcovr -r . --html-details -o cobertura.html`) simplifica o relatório.
- Cobertura mede o que foi **executado**, não o que foi **verificado**: 100 % de linhas sem asserções úteis não prova nada, e faltar um teste de borda (capacidade 1) passa despercebido se o código não tiver um `if` específico para ela. Use-a para achar o que **não** foi testado.

## Laboratório

### Material
- Computador com Ubuntu, gcc, gdb, make, cmake e git (M0.7 e tópicos anteriores); `pip install gcovr` num venv (opcional).
- Unity: clone `https://github.com/ThrowTheSwitch/Unity` e copie `src/unity.c`, `src/unity.h` e `src/unity_internals.h` para `vendor/unity/` do seu projeto (ou use `git submodule`). Guarde no README o commit/versão usado e a licença (MIT).
- Conta no GitHub.
- Opcional, para o Experimento 4: o caderno com o esquema de um LED num pino de GPIO (você vai simular o registrador no PC).

### Passo a passo
**Experimento 1 — Esqueleto e primeiro teste vermelho (≈ 3 h).**
1. Crie o repositório `buffer-circular-c` com `include/`, `src/`, `tests/`, `vendor/unity/`, `.gitignore` (`build/`, `*.o`, `*.gcda`, `*.gcno`, `*.gcov`), `LICENSE` e um README esqueleto.
2. Escreva o `buffer_circular.h` com a API do resumo e um `buffer_circular.c` em que todas as funções só devolvem `false`/`0`.
3. Escreva o `CMakeLists.txt`: biblioteca `buffer_circular` (`target_include_directories(... PUBLIC include)`), biblioteca `unity`, executável `testes`, `enable_testing()` e `add_test`. Flags: `-Wall -Wextra -Werror`.
4. Escreva **só** `test_novo_buffer_esta_vazio`. Rode `cmake -S . -B build && cmake --build build && ctest --test-dir build --output-on-failure`. Ele falha? Anote a mensagem. Commit: "Esqueleto e primeiro teste (vermelho)".

**Experimento 2 — TDD da biblioteca (≈ 6 h).** Percorra a lista de testes do resumo **um teste por vez**, sempre: escrever o teste → ver falhar → código mínimo → ver passar → refatorar → commit. Registre num arquivo `docs/diario-tdd.md` cada ciclo em uma linha (teste, por que falhou, o que mudou). Inclua pelo menos 10 testes, entre eles: volta do índice, cheio que recusa sem sobrescrever, vazio que não altera a saída, capacidade 1 e argumentos inválidos.

**Experimento 3 — Defeitos plantados e ferramentas (≈ 2 h).**
1. Plante, um de cada vez, três defeitos e confira que algum teste falha: (a) troque `% b->capacidade` por nada no `bc_retira`; (b) troque `==` por `>` em `bc_cheio` (e pense: trocar por `>=` mudaria algum resultado? Se nenhum teste pode pegar uma mudança, ela é equivalente — não é defeito); (c) esqueça de decrementar `quantidade`. Se algum defeito passar sem nenhum teste falhar, escreva o teste que faltava.
2. Compile os testes com `-fsanitize=address,undefined` (um tipo de build `Asan` no CMake ou um `-DCMAKE_C_FLAGS=...` numa pasta `build-asan`) e rode-os.
3. Rode `cppcheck --enable=all` e `clang-tidy` (T11) na biblioteca e corrija o que for defeito.

**Experimento 4 — Isolar o hardware (≈ 3 h).** Escreva um módulo `led` que recebe o endereço de um "registrador" de saída: `void led_inicia(volatile uint16_t *registrador)`, `led_liga(uint8_t n)`, `led_desliga(uint8_t n)`, `led_desliga_todos(void)` (LEDs 1 a 16 nos bits 0 a 15). No teste, passe o endereço de uma variável `uint16_t leds_virtuais` e confira os bits com `TEST_ASSERT_EQUAL_HEX16`. Teste ligar, desligar, ligar vários, LED fora da faixa (1..16) e que `led_inicia` desliga todos (Grenning, cap. 3 e 4). Esse código usa as máscaras do T05 e roda igual no microcontrolador, com o endereço do registrador real.

**Experimento 5 — Cobertura (≈ 2 h).** Gere a cobertura de `buffer_circular.c` e de `led.c` com gcov (ou gcovr). Meta: 100 % de linhas e de desvios na biblioteca. Para cada linha `#####` ou desvio não tomado, escreva o teste que falta ou justifique no README por que não vale a pena. Guarde o resumo (`gcov -b` ou `gcovr --txt`).

**Experimento 6 — Publicação (≈ 5 h).** Complete o README: o que é a biblioteca e para que serve num firmware; a API com uma tabela (função, parâmetros, retorno, comportamento no cheio/vazio); um exemplo de uso; como compilar e rodar os testes (comandos exatos); a saída do `ctest`; a cobertura; as decisões (por que recusar no cheio, por que sem `malloc`, uso com interrupção: um produtor e um consumidor, e o que mais seria preciso para ser seguro com interrupções — T03); a versão do Unity e as licenças. Opcional: um *workflow* do GitHub Actions que roda `cmake`, `ctest` e mostra o selo "passing" no README. Peça a alguém (ou a si mesmo daqui a uma semana) para clonar e rodar os testes só lendo o README.

### Evidência
Registre no jogo:
1. **Link do repositório** no GitHub com código, testes, `CMakeLists.txt`, README e histórico de commits mostrando o ciclo do TDD (commits pequenos).
2. **Saída do `ctest --output-on-failure`** com todos os testes passando (texto ou captura de tela), e o número de testes.
3. **Resumo da cobertura** (linhas e desvios de `buffer_circular.c` e `led.c`).
4. **Tabela dos defeitos plantados** (Experimento 3): defeito, teste que o pegou, mensagem do Unity.
5. **Descrição** (5–10 frases): o caso de teste mais difícil de acertar, um defeito que o TDD revelou antes de você perceber, o que a cobertura mostrou que faltava e como você usaria esta biblioteca na interrupção da UART no A1.

## Pratique
1. Escreva o teste `test_quantidade_acompanha_operacoes`, que confere `bc_quantidade` depois de 3 `coloca` e 1 `retira`.
2. Uma asserção falha: `test.c:31:test_x:FAIL: Expected 0x2A Was 0x2B`. Que macro produziu essa mensagem? Qual era o valor esperado em decimal?
3. Num buffer de capacidade 4 vazio: coloca 1, 2, 3, 4, 5; retira 2 vezes; coloca 6 e 7; retira tudo. Quais valores saem na última retirada, em ordem? Quantas chamadas de `bc_coloca` devolveram `false`?
4. Uma implementação sem contador usa "cheio quando `(cauda + 1) % N == cabeca`". Com N = 8, quantos elementos cabem?
5. Por que o `setUp` reinicializa o buffer antes de cada teste, em vez de um único `bc_inicia` no `main`?
6. Escreva o teste vermelho para "colocar no cheio não altera o conteúdo". Qual é o código mínimo que o faz passar?
7. Uma função `int classifica(int t)` tem `if (t < 0) return -1; if (t > 100) return 1; return 0;`. Os testes chamam `classifica(50)` e `classifica(-5)`. Qual a cobertura de linhas e de desvios? Que teste falta?
8. Escreva `gpio_fake.c` para uma interface `void gpio_escreve(uint8_t pino, bool nivel)` e um teste de um módulo `pisca` que alterna o pino a cada chamada de `pisca_tick()`.
9. Por que testes com `assert` são frágeis num build Release, e por que as asserções do Unity não têm esse problema?
10. Liste três comportamentos do buffer circular que **não** dá para testar só com testes unitários no PC.

## Armadilhas comuns
- Escrever todo o código e só depois os testes (e escrever testes que confirmam o que o código faz, não o que deveria fazer).
- Não ver o teste falhar primeiro — um teste que nunca falhou pode não testar nada.
- Testes que dependem da ordem ou do estado deixado por outro teste (use o `setUp`).
- Testar só o "caminho feliz" e esquecer vazio, cheio, volta do índice e argumentos inválidos.
- Inverter esperado e obtido nas asserções (a mensagem fica enganosa).
- Testar campos internos da struct (`b.inicio`) em vez do comportamento pela API — o teste quebra a cada refatoração.
- Código de hardware misturado com a lógica: impossível testar no PC.
- Perseguir 100 % de cobertura com testes sem asserções.
- Medir cobertura com `-O2`, ou esquecer `--coverage` no link.
- Subir `build/`, `*.gcda` e `*.gcno` para o repositório.

## Gabarito
1. `bc_coloca` ×3, `bc_retira` ×1, `TEST_ASSERT_EQUAL_UINT32(2, bc_quantidade(&b));` (e confira também depois de cada operação, se quiser).
2. `TEST_ASSERT_EQUAL_HEX8` (ou outra `_HEX`); esperado 0x2A = 42.
3. Saem 3, 4, 6, 7; uma chamada devolveu `false` (o 5, com o buffer cheio).
4. 7 (N − 1): uma posição fica sempre vazia para distinguir cheio de vazio.
5. Para cada teste começar do mesmo estado conhecido, independente da ordem e das falhas dos outros.
6. Teste: encha, tente colocar 99 (deve dar `false`), retire tudo e confira a sequência original. Código mínimo: `if (bc_cheio(b)) return false;` no início de `bc_coloca`.
7. Linhas: 5 de 6 (≈ 83 %; `return 1;` nunca executa). Desvios: 3 de 4 (75 %; `t > 100` nunca foi verdadeiro). Falta `classifica(150)` — e, para as bordas, `classifica(0)`, `classifica(100)` e `classifica(101)`.
8. `static bool nivel[32]; void gpio_escreve(uint8_t p, bool n) { nivel[p] = n; } bool gpio_fake_le(uint8_t p) { return nivel[p]; }`; o teste chama `pisca_tick()` duas vezes e confere `true` e depois `false`.
9. `-DNDEBUG` remove os `assert` (o teste "passa" sem verificar nada); as macros do Unity não dependem de `NDEBUG`.
10. Concorrência real com a interrupção (condições de corrida), temporização (o buffer encher na velocidade real da UART) e o comportamento com o compilador e a otimização do MCU (largura de `size_t`, alinhamento) — isso se verifica na placa, no A1.
