# M0.7.T02 — Git e GitHub

## Ao final você consegue
- Criar um repositório e registrar mudanças com o ciclo add/commit, inspecionando o estado com status, log e diff.
- Criar, trocar e mesclar branches, prevendo o resultado do merge e resolvendo conflitos.
- Sincronizar com repositórios remotos (clone, fetch, pull, push) e colaborar no GitHub com issues e pull requests.

## Resumo
**1. As três áreas.** O Git guarda fotografias (*commits*) do projeto. Entre você e o histórico existem três lugares:
- **Diretório de trabalho**: os arquivos que você edita.
- **Área de preparação** (*staging*, *index*): o que vai entrar no **próximo** commit. `git add arquivo` copia para cá a versão **daquele momento**.
- **Repositório** (`.git/`): os commits.

Configuração única: `git config --global user.name "Matheus"`, `git config --global user.email "..."` e `git config --global init.defaultBranch main`.

Ciclo diário:
```bash
git init                     # (ou git clone URL)
git status                   # o que mudou, o que está preparado
git diff                     # linhas alteradas e AINDA não preparadas
git add main.c README.md     # prepara
git diff --staged            # o que vai entrar no commit
git commit -m "Ajusta pino do LED para GPIO4"
git log --oneline --graph    # histórico resumido
```
Um arquivo novo é **não rastreado** até o primeiro `git add`. `git commit -a` prepara automaticamente os arquivos já **rastreados** que foram modificados — nunca os novos. Se você edita um arquivo **depois** do `add`, o commit leva a versão preparada; a edição nova continua "modificada" no `status`.

**2. Branches e merge.** Um branch é só um ponteiro para um commit. `git switch -c feature/sensor` cria e troca; `git switch main` volta (os arquivos do diretório de trabalho mudam para refletir o branch). Para trazer o trabalho de volta: estando em `main`, `git merge feature/sensor`.
- **Fast-forward**: se `main` não andou desde que o branch foi criado, o Git só avança o ponteiro — nenhum commit novo é criado.
- **Merge de três vias**: se os dois andaram, o Git cria um **commit de merge** (com dois pais).
- **Conflito**: os dois branches mudaram as mesmas linhas. O Git para e marca o arquivo:
```
<<<<<<< HEAD
#define LED_PIN 4
=======
#define LED_PIN 5
>>>>>>> feature/sensor
```
Entre `<<<<<<< HEAD` e `=======` está a versão do branch em que você está (onde rodou o merge); entre `=======` e `>>>>>>>`, a do branch que está chegando. Resolva editando (deixe a versão certa e apague os marcadores), depois `git add arquivo` e `git commit` (ou `git merge --continue`). `git merge --abort` desiste e volta ao estado anterior.

**3. Remotos e GitHub.** `git clone URL` copia o repositório e cria o remoto `origin`. `git push` envia seus commits; `git fetch` baixa os commits do remoto **sem mexer** nos seus arquivos; `git pull` = `fetch` + integrar (merge, ou rebase se configurado). Se o `push` é recusado (*rejected, non-fast-forward*), o remoto tem commits que você não tem: faça `git pull`, resolva conflitos se houver, teste e faça `push` de novo. `git push --force` reescreve o histórico do remoto e apaga o trabalho dos outros — não use em branch compartilhado.
- Autenticação no GitHub por terminal: chave SSH (`ssh-keygen`, cadastre a chave pública no GitHub) ou o `gh auth login` do GitHub CLI. Senha da conta não serve mais para `git push` por HTTPS.
- **Issue**: um registro de problema, tarefa ou ideia, com número (#12), discussão e rótulos.
- **Pull request (PR)**: pedido para mesclar um branch em outro, com revisão linha a linha, comentários e verificações. Escrever `Closes #12` (ou `Fixes #12`) na descrição faz a issue fechar automaticamente quando o PR for mesclado no branch padrão. Quem não tem permissão de escrita trabalha num **fork** e abre o PR a partir dele.

**4. O que não versionar.** O `.gitignore` lista padrões que o Git não deve rastrear: `*.log` (em qualquer pasta), `build/` (pastas `build` em qualquer nível), `.venv/`, `__pycache__/`, segredos (`.env`, chaves). Ele **só afeta arquivos ainda não rastreados**: se o arquivo já foi commitado, rode `git rm --cached arquivo` (tira do índice, mantém no disco) e faça commit. Senha que foi para um repositório público deve ser considerada vazada: troque a senha.

**5. Boas mensagens.** Linha de assunto curta (≈ 50 caracteres), no imperativo ("Corrige", "Adiciona"), dizendo **o que muda**; linha em branco; corpo explicando **por que**. Um commit = uma mudança lógica. Ruim: `ajustes`, `wip`, `funciona agora`. Bom: `Corrige leitura do ADC saturando acima de 3,1 V`.

**6. Desfazer com segurança.**
| Situação | Comando |
|---|---|
| Descartar edição não preparada de um arquivo | `git restore arquivo` (perde a edição!) |
| Tirar da área de preparação | `git restore --staged arquivo` |
| Corrigir a mensagem ou esquecer um arquivo no **último** commit, ainda não enviado | `git commit --amend` (substitui o último commit) |
| Desfazer um commit que **já foi enviado** | `git revert <hash>` (cria um commit novo que inverte o antigo) |
`git reset --hard` e `--amend` reescrevem histórico: só em commits que ninguém mais tem.

## Pratique
Use um repositório de teste: `mkdir ~/treino-git && cd ~/treino-git && git init`.
1. Crie `README.md` e `main.c`; faça o primeiro commit só com o README. Veja o `git status` antes e depois.
2. Edite `main.c`, rode `git diff`; prepare; rode `git diff` e `git diff --staged` e explique a diferença.
3. Prepare uma edição, edite de novo o mesmo arquivo e faça commit. Qual versão entrou? Confira com `git show`.
4. Crie `feature/led`, faça dois commits, volte para `main` e faça o merge. Foi fast-forward? Confira com `git log --oneline --graph`.
5. Provoque um conflito: em `main`, mude `#define LED_PIN 2` para 4 e faça commit; num branch criado antes disso, mude para 5 e faça commit. Faça o merge, resolva e finalize.
6. Crie um `.gitignore` com `*.log` e `build/`; crie `debug.log`, `build/fw.bin` e `logs/serial.log` e veja o `git status`. Use `git check-ignore -v logs/serial.log`.
7. Commite `config.log` **antes** de pô-lo no `.gitignore`. Depois adicione o padrão: o Git parou de rastreá-lo? Corrija com `git rm --cached`.
8. Faça um commit com mensagem errada e corrija com `--amend`. Faça outro commit e desfaça-o com `git revert`. Compare os dois no `git log`.
9. Crie um repositório no GitHub, ligue com `git remote add origin ...` e faça `git push -u origin main`.
10. Abra uma issue "Documentar ligação do LED", crie um branch, faça a mudança, abra um PR com `Closes #1` na descrição e faça o merge pelo GitHub. Volte ao terminal e rode `git pull`.
11. Simule o push recusado: edite o README pelo site do GitHub e, sem dar pull, faça um commit local e tente `git push`. Resolva.
12. Reescreva três mensagens ruins (`ajustes`, `teste`, `agora vai`) para commits imaginários do seu projeto de IoT.

## Armadilhas comuns
- Achar que `git commit -a` inclui arquivos novos (só os já rastreados).
- Editar depois do `git add` e achar que a edição nova foi no commit.
- Commitar marcadores de conflito (`<<<<<<<`) sem perceber: rode `git diff --staged` antes do commit de merge.
- Pôr no `.gitignore` um arquivo já rastreado e achar que ele saiu do repositório.
- `git push --force` em branch compartilhado, ou `--amend` num commit já enviado.
- Commitar senha, token ou `.env`; apagar no commit seguinte **não** remove do histórico.
- Branch de vida longa que nunca é mesclado: quanto mais tempo, mais conflitos.

## Gabarito
1. Antes do commit, os dois aparecem como não rastreados; depois, só `main.c`.
2. `git diff` mostra o que mudou e **não** foi preparado; `--staged`, o que foi preparado e ainda não commitado. Depois do `add`, o primeiro fica vazio.
3. A versão preparada (a do `add`); a segunda edição continua como "modificado".
4. Sim, se `main` não teve commits novos: o ponteiro só avançou, sem commit de merge.
5. Edite deixando o valor correto, apague os marcadores, `git add main.c`, `git commit`.
6. Os três ficam ignorados (`*.log` vale em qualquer pasta; `build/` ignora a pasta inteira). O `check-ignore -v` mostra a linha do `.gitignore` responsável.
7. Não; o `.gitignore` não age sobre arquivos rastreados. `git rm --cached config.log` + commit.
8. `--amend` substitui o último commit (o hash muda, o antigo some do log); `revert` mantém o original e cria um commit novo que o inverte.
9. `git remote -v` deve mostrar `origin`; o `-u` liga o branch local ao remoto.
10. Ao mesclar o PR, a issue #1 fecha sozinha; o `git pull` traz o commit de merge.
11. `git pull` (integra o commit do site), resolva se houver conflito e `git push`.
12. Ex.: "Corrige debounce do botão de reset", "Adiciona teste de leitura do sensor DHT22", "Reduz intervalo de envio MQTT para 30 s".
