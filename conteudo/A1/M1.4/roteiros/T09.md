## Resumo
**1. A arquitetura.** O núcleo Cortex-M tem lógica de depuração própria (CoreSight), acessada por um **DAP** (*Debug Access Port*):
```text
 PC ── USB ── sonda (ST-Link) ── SWDIO/SWCLK ──► DP (SW-DP ou JTAG-DP; no STM32, SWJ-DP = os dois)
                                                   └► AP (AHB-AP) ──► barramento do chip: flash, SRAM, periféricos,
                                                                       e os componentes de depuração na PPB:
                                                                       SCS/DHCSR (parar, passo a passo), FPB (breakpoints),
                                                                       DWT (watchpoints, CYCCNT), ITM (printf rápido) → TPIU → SWO
```
- O AHB-AP lê e escreve memória **com a CPU rodando** (é assim que o depurador mostra variáveis "ao vivo" e que o RTT funciona).
- **SWD** usa 2 fios: **SWDIO** (dados, bidirecional) e **SWCLK** (clock). Opcionais: **NRST** (reset do chip, para *connect under reset*) e **SWO** (saída de trace do ITM, em PB3 no F103/F4).
- **JTAG** usa TCK, TMS, TDI, TDO e nTRST: 4–5 fios, cadeia de vários chips; no STM32 só é útil para *boundary scan* ou sondas antigas.
- No STM32, PA13 = SWDIO/TMS, PA14 = SWCLK/TCK, PA15 = TDI, PB3 = TDO/SWO, PB4 = nTRST (T03).

**Ligação.**

| Sinal | ST-Link V2 (clone) | Blue Pill (conector de 4 pinos) | Nucleo |
|---|---|---|---|
| SWDIO | SWDIO | DIO (PA13) | já ligado ao ST-LINK embutido |
| SWCLK | SWCLK | CLK (PA14) | já ligado |
| GND | GND | GND | já ligado |
| 3,3 V | 3.3V | 3.3 (alimenta a placa, **sem** USB ligado ao mesmo tempo) | — |
| NRST | RST | pino R da placa (opcional; necessário para *connect under reset*) | já ligado |
| SWO | — (clones não trazem) | PB3 | PB3, via ponte de solda (veja o UM1724) |

**2. OpenOCD + GDB.** O OpenOCD conversa com a sonda e oferece um servidor GDB (porta 3333) e um console telnet (4444).
```text
$ openocd -f interface/stlink.cfg -f target/stm32f1x.cfg          # Nucleo-F4: -f board/st_nucleo_f4.cfg
  ... Info : stm32f1x.cpu: hardware has 6 breakpoints, 4 watchpoints
  ... Info : Listening on port 3333 for gdb connections

$ arm-none-eabi-gdb build/firmware.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt          # comando repassado ao OpenOCD: reset e para no vetor de reset
(gdb) load                        # grava a flash com as seções do .elf
(gdb) break main
(gdb) continue
(gdb) next                        # próxima linha, sem entrar em funções
(gdb) step                        # entra na função
(gdb) finish                      # roda até sair da função atual e mostra o retorno
(gdb) bt                          # pilha de chamadas
(gdb) info registers              # r0–r12, sp, lr, pc, xPSR
(gdb) p ticks                     # valor de uma variável
(gdb) x/7wx 0x40011000            # 7 palavras em hexa a partir do GPIOC (CRL..LCKR)
(gdb) set var ticks = 0           # escreve na RAM do alvo
(gdb) set *(unsigned*)0x40011010 = 1<<29    # BSRR: BR13 — acende o LED da Blue Pill pelo depurador
(gdb) monitor reset run
```
- **Blue Pill com chip clone** (CKS32/CS32): o OpenOCD reclama de *UNEXPECTED idcode 0x2ba01477* (o original é 0x1ba01477). Use `openocd -f interface/stlink.cfg -c "set CPUTAPID 0x2ba01477" -f target/stm32f1x.cfg`.
- Gravar sem GDB: `openocd -f interface/stlink.cfg -f target/stm32f1x.cfg -c "program build/firmware.elf verify reset exit"`.
- Velocidade: `adapter speed 4000` (kHz). Fios longos e protoboard pedem velocidades menores.
- **VS Code**: a extensão Cortex-Debug lê um `launch.json` com `"servertype": "openocd"`, `"configFiles"` e `"svdFile"` (o arquivo **SVD** do CMSIS, que faz o painel mostrar os registradores dos periféricos por nome e campo). É o mesmo OpenOCD + GDB por baixo.

**3. Breakpoints e watchpoints.**
- **Breakpoint de software**: o depurador troca a instrução por `bkpt`. Só funciona em **RAM**: a flash não pode ser reescrita a cada breakpoint.
- **Breakpoint de hardware** (FPB, *Flash Patch and Breakpoint*): comparadores de endereço no núcleo. No Cortex-M3/M4: **6 comparadores de instrução** (e 2 de literais); no M0/M0+: até 4. O GDB pede um a cada `break` em código na flash (o OpenOCD escolhe hardware automaticamente lá); `hbreak` força hardware. Passou do limite, o `continue` falha com erro de recurso.
- **Watchpoint** (DWT, *Data Watchpoint and Trace*): comparadores de endereço de **dados**. M3/M4: **4** (M0+: 2). `watch var` (escrita), `rwatch` (leitura), `awatch` (ambos). O CPU para logo **depois** da instrução que acessou — veja o PC anterior na desmontagem. Ideal para achar quem corrompe uma variável.
- `__BKPT(0)` no código para a CPU no depurador (útil em `assert`). **Sem depurador ligado, `bkpt` vira HardFault** — remova ou condicione em `CoreDebug->DHCSR & C_DEBUGEN`.
- Periféricos continuam rodando enquanto a CPU está parada (o timer conta, a UART perde bytes, o watchdog dispara). O `DBGMCU_CR` (F1) e os `DBGMCU_APBx_FZ` (F4) congelam timers e watchdogs durante a parada.

**4. O contador de ciclos (DWT_CYCCNT).** Um contador de 32 bits que soma 1 a cada ciclo de HCLK. Medir trechos de código sem osciloscópio:
```c
#include "stm32f1xx.h"

static inline void ciclos_liga(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* habilita DWT e ITM */
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;
}

volatile uint32_t ciclos_medidos;

static uint32_t soma(const uint16_t *v, uint32_t n)
{
    uint32_t s = 0;
    while (n--) s += *v++;
    return s;
}

int main(void)
{
    static uint16_t dados[256];
    ciclos_liga();
    uint32_t t0 = DWT->CYCCNT;
    volatile uint32_t r = soma(dados, 256);
    ciclos_medidos = DWT->CYCCNT - t0;   /* subtração sem sinal: funciona mesmo com 1 estouro */
    (void)r;
    for (;;) { }
}
```
O contador estoura a cada 2³² ciclos (≈ 59,7 s a 72 MHz). A subtração em `uint32_t` dá o resultado certo se o intervalo medido for menor que um estouro. Leia `ciclos_medidos` no GDB (`p ciclos_medidos`).

**5. Mensagens do firmware: três caminhos.**

| | Semihosting | ITM/SWO | RTT |
|---|---|---|---|
| Como funciona | `bkpt 0xAB`: a CPU **para**, o depurador executa a chamada (escrever, ler arquivo) e retoma | o ITM escreve num FIFO; o TPIU serializa no pino SWO (estilo UART) | buffer circular na RAM; a sonda lê pelo AHB-AP |
| Velocidade | muito lenta (ms por chamada) | rápida (MHz no SWO) | rápida, sem pino extra |
| Pinos | SWD | SWD + **SWO** (PB3) | SWD |
| Sem depurador | **HardFault** (o `bkpt` não tem quem atenda) | segue rodando (o ITM descarta) | segue rodando |
| OpenOCD | `monitor arm semihosting enable` | TPIU/`itm port 0 on` | `rtt setup`, `rtt start`, `rtt server start` |

**Exemplo (printf pelo ITM).** A biblioteca newlib chama `_write` para cada `printf`; basta redirecioná-la:
```c
#include "stm32f1xx.h"
#include <stdio.h>

int _write(int fd, const char *buf, int len)
{
    (void)fd;
    for (int i = 0; i < len; i++)
        ITM_SendChar((uint32_t)buf[i]);   /* CMSIS: espera o FIFO da porta 0 e escreve */
    return len;
}

int main(void)
{
    for (unsigned n = 0; ; n++) {
        printf("n = %u\r\n", n);
        for (volatile uint32_t i = 0; i < 800000; i++) { }
    }
}
```
No OpenOCD 0.12: `stm32f1x.tpiu configure -protocol uart -traceclk 72000000 -pin-freq 2000000 -output swo.log`, `stm32f1x.tpiu enable` e `itm port 0 on` (a sintaxe mudou entre versões: confira o manual da sua). O `-traceclk` precisa ser o HCLK real (T02). O `ITM_SendChar` não faz nada se o depurador não habilitou o ITM, então o firmware não trava sem a sonda.

**6. Recuperar a placa "morta".** O OpenOCD diz *Error: init mode failed (unable to connect to the target)*. Causas e saídas:
1. **SWD reconfigurado pelo firmware** (SWJ_CFG = 100, PA13/PA14 como GPIO, chip em *Stop/Standby*): o firmware desliga o SWD em microssegundos depois do reset. Saída: **connect under reset** — com o NRST ligado, `-c "reset_config srst_only connect_assert_srst"`; o depurador conecta com o chip **segurando o reset** e o para antes da primeira instrução. Sem fio de NRST: segure o botão de reset, inicie o OpenOCD e solte logo depois.
2. Mesma causa, outra saída: **BOOT0 = 1** e reset. O chip roda o bootloader de sistema, que não mexe no SWD; conecte e apague a flash (`stm32f1x mass_erase 0` ou `flash erase_sector`). Volte BOOT0 para 0.
3. **Proteção de leitura** (RDP): com RDP nível 1, o depurador conecta mas não lê a flash. `stm32f1x unlock 0` (F1) ou o STM32CubeProgrammer removem a proteção **apagando a flash inteira**; desligue e religue a alimentação. No F4 existe o **nível 2, irreversível**: o depurador é desligado para sempre. Nunca grave option bytes do F4 sem ler duas vezes.
4. **Chip clone** com IDCODE diferente (seção 2), ou fiação: confira 3,3 V e GND primeiro.

**7. Identificar o chip pelo depurador.** `DBGMCU_IDCODE` (0xE004_2000) traz o DEV_ID (0x410 = F103 *medium density*; 0x433 = F401xD/E; 0x431 = F411) e a revisão. O registrador de tamanho da flash (F_SIZE, em 0x1FFF_F7E0 no F1, em KB) diz quanta flash o chip declara — numa Blue Pill, `x/hx 0x1FFFF7E0` costuma mostrar 0x0040 (64 KB), mesmo em chips que têm 128 KB físicos.

### Passo a passo
**Experimento 1 — Ligar e identificar (≈ 1,5 h).**
1. Ligue o ST-Link à Blue Pill pela tabela (alimentação só pelo ST-Link) e rode o OpenOCD. Anote as linhas de *Info* (IDCODE, número de breakpoints e watchpoints, tensão).
2. No telnet (`telnet localhost 4444`) ou no GDB: `mdw 0xE0042000` (DBGMCU_IDCODE) e `mdh 0x1FFFF7E0` (F_SIZE). Decodifique DEV_ID, REV_ID e o tamanho da flash.
3. Na Nucleo, faça o mesmo com o `board/st_nucleo_f4.cfg` e o F_SIZE em 0x1FFF_7A22.

**Experimento 2 — Uma sessão de GDB completa (≈ 3 h).**
1. Compile o firmware do T03 (botão e LED) com `-g -O0` e depois com `-g -Os`. Grave com `load`.
2. `break main`, `continue`, `next` até a configuração do GPIO. Antes e depois de cada escrita em CRH, faça `x/wx 0x40011004`.
3. Com a CPU parada, acenda o LED escrevendo no BSRR pelo GDB. Depois, com a CPU rodando (`continue` e Ctrl+C), mude uma variável global e veja o efeito.
4. Ponha um breakpoint numa função chamada a partir de outra, use `bt`, `up`, `info locals`, `finish`. Compare a experiência com `-O0` e `-Os` (variáveis *optimized out*, linhas que pulam).
5. Repita no VS Code com Cortex-Debug e o SVD: abra o painel de periféricos e ache o GPIOC.

**Experimento 3 — Breakpoints, watchpoints e ciclos (≈ 3 h).**
1. Coloque 7 breakpoints em linhas diferentes do código na flash e dê `continue`. Anote a mensagem. Apague um e repita.
2. Escreva um bug de propósito: um vetor `int v[8]` e um laço que escreve até `v[8]`, com a variável `contador` declarada logo depois. Use `watch contador` para achar a instrução que a corrompe. Anote PC e linha.
3. Meça com o `DWT_CYCCNT` a função `soma` do Resumo com 256 elementos em `-O0`, `-Os` e `-O2`, com a flash em 0 WS (24 MHz) e 2 WS (72 MHz). Monte a tabela de ciclos por elemento.
4. Confira o CYCCNT com o osciloscópio: ligue um pino antes da função e desligue depois; compare o tempo medido com ciclos/f_HCLK.

**Experimento 4 — Três printf (≈ 2,5 h).**
1. **Semihosting**: compile com `--specs=rdimon.specs`, chame `initialise_monitor_handles()` no início do `main` e dê `monitor arm semihosting enable` antes do `continue`. Veja a saída no console do OpenOCD.
2. Desligue o depurador e reinicie a placa: o que acontece? (Pista: T11.)
3. **ITM/SWO** (Nucleo): grave o exemplo do Resumo e capture a saída com os comandos de TPIU. **RTT**: adicione os arquivos do SEGGER RTT (licença BSD), use `SEGGER_RTT_printf` e, no OpenOCD, `rtt setup 0x20000000 0x5000 "SEGGER RTT"`, `rtt start`, `rtt server start 9090 0`; conecte com `nc localhost 9090`.
4. Meça com o CYCCNT o custo de imprimir a mesma linha de 20 caracteres em cada método e monte a tabela.

**Experimento 5 — Brickar e recuperar (≈ 2 h).**
1. Grave um firmware que, logo no início, escreve SWJ_CFG = 100 (JTAG e SWD desligados) e pisca o LED. Confirme que o OpenOCD não conecta mais.
2. Recupere por **connect under reset** (fio NRST e `reset_config srst_only connect_assert_srst`) e grave o pisca normal.
3. Repita o passo 1 e recupere agora por **BOOT0 = 1** + `stm32f1x mass_erase 0`.
4. (Opcional, só F1) Ative a proteção de leitura com `stm32f1x lock 0`, desligue e religue a placa, tente ler a flash com `mdw 0x08000000` e depois remova com `stm32f1x unlock 0`. **Não faça isso no F4.**

## Armadilhas comuns
- Alimentar a Blue Pill pelo ST-Link e pelo USB ao mesmo tempo.
- Esquecer o `-g`: o GDB não acha linhas nem variáveis.
- Depurar em `-O2` e estranhar linhas fora de ordem: comece em `-Og` ou `-O0`.
- Deixar semihosting ou `__BKPT` no firmware de produção.
- Achar que a CPU parada para tudo: timers, UART, DMA e watchdog continuam (use o DBGMCU para congelá-los).
- Usar o SWO com o `traceclk` errado e ver lixo.
- Reconfigurar PA13/PA14 no início do `main` e perder a depuração.
- Gravar option bytes do F4 com RDP nível 2.
- Brigar com o OpenOCD por causa do IDCODE de um clone sem ler a mensagem de erro.

## Gabarito
1. Três: SWDIO, SWCLK e GND (a alimentação vem do USB). Para *connect under reset*, quatro: mais o NRST.
2. Para inserir o `bkpt`, o depurador precisa reescrever a instrução na memória; a flash só é apagada por página e gravada por meia palavra, e isso não pode ser feito a cada breakpoint. Por isso a flash usa os comparadores do FPB.
3. O M4 tem 6 comparadores de instrução: o GDB/OpenOCD não consegue inserir todos e o `continue` falha com erro de recursos de breakpoint de hardware.
4. 2³² / 72·10⁶ ≈ 59,65 s; a 100 MHz, ≈ 42,95 s.
5. (0x0000_0100 − 0xFFFF_FF00) mod 2³² = 0x200 = 512 ciclos.
6. Sem depurador, o `bkpt 0xAB` do semihosting não tem quem o atenda e vira HardFault.
7. DEV_ID = 0x410 (F103 *medium density*), REV_ID = 0x2003 (revisões "Y", "1", "2" ou "X" do silício, que compartilham esse código na tabela do RM0008).
8. `{"type": "cortex-debug", "request": "launch", "servertype": "openocd", "executable": "build/firmware.elf", "configFiles": ["interface/stlink.cfg", "target/stm32f1x.cfg"], "svdFile": "STM32F103.svd"}` dentro de `configurations`.
