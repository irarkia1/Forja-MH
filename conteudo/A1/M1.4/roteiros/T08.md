# M1.4.T08 — HAL × LL × registrador

> Tempo previsto: ~12,5 h — ≈ 3,5 h de leitura (manuais da HAL e da LL, código-fonte), ≈ 3 h reescrevendo periféricos nas três camadas, ≈ 4 h medindo tamanho e ciclos, ≈ 2 h de revisão. Você passou o módulo inteiro escrevendo registradores à mão. Na indústria, a maioria dos projetos STM32 começa no **STM32CubeMX** e usa a **HAL**. Este tópico fecha o círculo: entender o que a HAL faz por baixo (agora você consegue ler o código dela), quanto ela custa e quando vale a pena usá-la, a LL ou o registrador — e como misturar as três sem armadilhas. É o equivalente, no STM32, ao M1.2.T08 (biblioteca Arduino × registrador).

## Ao final você consegue
- Descrever a arquitetura do STM32Cube (CubeMX, HAL, LL, BSP e middleware) e o fluxo de um driver HAL (handle, Init, MspInit, callbacks e HAL_GetTick).
- Escrever o mesmo recurso em HAL, em LL e por registrador, e ler o código-fonte da HAL para descobrir que registradores ela toca.
- Medir e comparar o custo em flash, RAM e ciclos das três abordagens com arm-none-eabi-size, o arquivo .map e o DWT_CYCCNT.
- Escolher a abordagem por critério (portabilidade, desempenho, manutenção, prazo) e misturar HAL, LL e registrador sem conflitos (SysTick, callbacks, HAL_Delay em interrupção).

## Resumo
**1. O ecossistema STM32Cube.**
```text
 STM32CubeMX (gráfico)  ──gera──►  main.c, stm32f1xx_hal_msp.c, stm32f1xx_it.c, SystemClock_Config(), MX_xxx_Init()
                                     │
 Pacote STM32CubeF1 ────────────────┤
   ├─ Middleware: USB Device, FatFS, FreeRTOS, LwIP...
   ├─ BSP: LEDs, botões e sensores das placas da ST (Nucleo, Discovery)
   ├─ HAL (stm32f1xx_hal_*.c): APIs portáveis entre famílias, com handle, estado, timeout, callbacks
   ├─ LL  (stm32f1xx_ll_*.h):  funções static inline, ~1 registrador cada; init opcional (USE_FULL_LL_DRIVER)
   └─ CMSIS: cabeçalho do dispositivo, core_cm3.h, startup, system (T01)
```
- O CubeMX gera o código de inicialização (clock, pinos, periféricos) e deixa regiões `/* USER CODE BEGIN … */ … /* USER CODE END … */`. **Só o que está dentro dessas regiões sobrevive** a uma nova geração.
- Para cada periférico, o CubeMX deixa escolher HAL ou LL (*Project Manager → Advanced Settings*).

**2. Como um driver HAL funciona.**
- **Handle**: uma struct por instância (`UART_HandleTypeDef huart1`) com `Instance` (ponteiro para os registradores), `Init` (configuração), estado (`gState`, `RxState`), código de erro e ponteiros de buffer.
- **`HAL_UART_Init(&huart1)`**: confere os parâmetros, chama **`HAL_UART_MspInit()`** — função `__weak` que **você** (ou o CubeMX, no `stm32f1xx_hal_msp.c`) implementa para o que depende da placa: clocks, pinos, NVIC, DMA — e só então escreve os registradores do periférico.
- Três modelos de E/S: **polling** (`HAL_UART_Transmit(&h, buf, n, timeout)`: bloqueia), **interrupção** (`HAL_UART_Transmit_IT`) e **DMA** (`HAL_UART_Transmit_DMA`). Nos dois últimos, a rotina de interrupção gerada chama `HAL_UART_IRQHandler(&huart1)`, que trata as flags e chama **callbacks** `__weak` como `HAL_UART_TxCpltCallback()` e `HAL_UART_RxCpltCallback()`, que você sobrescreve.
- Retorno `HAL_StatusTypeDef`: `HAL_OK`, `HAL_ERROR`, `HAL_BUSY`, `HAL_TIMEOUT`. **Sempre teste.**
- **Base de tempo**: `HAL_Init()` configura o **SysTick** a 1 ms com prioridade `TICK_INT_PRIORITY` (0x0F no modelo de configuração do F1); o `SysTick_Handler` chama `HAL_IncTick()`, e `HAL_GetTick()`/`HAL_Delay()`/todos os *timeouts* dependem dele. `HAL_Delay(n)` soma um tick para garantir **pelo menos** *n* ms.

**3. O mesmo recurso nas três camadas.** Pisca do PC13 + envio de uma mensagem pela USART1 (PA9), F103 a 8 MHz (HSI).

*HAL:*
```c
#include "stm32f1xx_hal.h"

UART_HandleTypeDef huart1;

void HAL_UART_MspInit(UART_HandleTypeDef *h)            /* chamada por HAL_UART_Init */
{
    if (h->Instance == USART1) {
        __HAL_RCC_USART1_CLK_ENABLE();
        __HAL_RCC_GPIOA_CLK_ENABLE();
        GPIO_InitTypeDef g = { .Pin = GPIO_PIN_9, .Mode = GPIO_MODE_AF_PP, .Speed = GPIO_SPEED_FREQ_HIGH };
        HAL_GPIO_Init(GPIOA, &g);
    }
}

void app_hal(void)
{
    HAL_Init();                                          /* SysTick de 1 ms, prioridade do tick */
    __HAL_RCC_GPIOC_CLK_ENABLE();
    GPIO_InitTypeDef led = { .Pin = GPIO_PIN_13, .Mode = GPIO_MODE_OUTPUT_PP,
                             .Pull = GPIO_NOPULL, .Speed = GPIO_SPEED_FREQ_LOW };
    HAL_GPIO_Init(GPIOC, &led);

    huart1.Instance = USART1;
    huart1.Init = (UART_InitTypeDef){ .BaudRate = 115200, .WordLength = UART_WORDLENGTH_8B,
        .StopBits = UART_STOPBITS_1, .Parity = UART_PARITY_NONE, .Mode = UART_MODE_TX,
        .HwFlowCtl = UART_HWCONTROL_NONE, .OverSampling = UART_OVERSAMPLING_16 };
    if (HAL_UART_Init(&huart1) != HAL_OK) { for (;;) { } }

    static const uint8_t msg[] = "ola\r\n";
    for (;;) {
        HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);
        HAL_UART_Transmit(&huart1, msg, sizeof msg - 1, 10);   /* bloqueia até 10 ms */
        HAL_Delay(500);
    }
}
```

*LL:*
```c
#include "stm32f1xx_ll_bus.h"
#include "stm32f1xx_ll_gpio.h"
#include "stm32f1xx_ll_usart.h"
#include "stm32f1xx_ll_utils.h"

void app_ll(void)
{
    LL_Init1msTick(8000000);                             /* SysTick sem interrupção, para LL_mDelay */
    LL_APB2_GRP1_EnableClock(LL_APB2_GRP1_PERIPH_GPIOA | LL_APB2_GRP1_PERIPH_GPIOC | LL_APB2_GRP1_PERIPH_USART1);

    LL_GPIO_SetPinMode(GPIOC, LL_GPIO_PIN_13, LL_GPIO_MODE_OUTPUT);
    LL_GPIO_SetPinOutputType(GPIOC, LL_GPIO_PIN_13, LL_GPIO_OUTPUT_PUSHPULL);
    LL_GPIO_SetPinSpeed(GPIOC, LL_GPIO_PIN_13, LL_GPIO_SPEED_FREQ_LOW);
    LL_GPIO_SetPinMode(GPIOA, LL_GPIO_PIN_9, LL_GPIO_MODE_ALTERNATE);
    LL_GPIO_SetPinSpeed(GPIOA, LL_GPIO_PIN_9, LL_GPIO_SPEED_FREQ_HIGH);

    LL_USART_SetBaudRate(USART1, 8000000, 115200);
    LL_USART_SetTransferDirection(USART1, LL_USART_DIRECTION_TX);
    LL_USART_Enable(USART1);

    for (;;) {
        LL_GPIO_TogglePin(GPIOC, LL_GPIO_PIN_13);
        for (const char *p = "ola\r\n"; *p; p++) {
            while (!LL_USART_IsActiveFlag_TXE(USART1)) { }
            LL_USART_TransmitData8(USART1, (uint8_t)*p);
        }
        LL_mDelay(500);
    }
}
```

*Registrador:*
```c
#include "stm32f1xx.h"

static volatile uint32_t ms;
void SysTick_Handler(void) { ms++; }

void app_reg(void)
{
    SysTick_Config(8000);                                /* 1 ms a 8 MHz */
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_IOPCEN | RCC_APB2ENR_USART1EN;
    GPIOC->CRH = (GPIOC->CRH & ~(0xFu << 20)) | (0x2u << 20);  /* PC13 saída PP 2 MHz */
    GPIOA->CRH = (GPIOA->CRH & ~(0xFu << 4))  | (0xBu << 4);   /* PA9 AF PP 50 MHz */
    USART1->BRR = 69;                                    /* 8 MHz / 115200 = 69,4 → 69 (erro +0,6 %) */
    USART1->CR1 = USART_CR1_UE | USART_CR1_TE;

    for (;;) {
        GPIOC->BSRR = (GPIOC->ODR & GPIO_ODR_ODR13) ? GPIO_BSRR_BR13 : GPIO_BSRR_BS13;
        for (const char *p = "ola\r\n"; *p; p++) {
            while (!(USART1->SR & USART_SR_TXE)) { }
            USART1->DR = (uint8_t)*p;
        }
        uint32_t t0 = ms;
        while (ms - t0 < 500) { }
    }
}
```

**4. Ler a HAL: o que ela faz por baixo.** Abra os fontes e confira:
- `HAL_GPIO_Init()` percorre os 16 bits da máscara de pinos e, para cada pino marcado, monta o nibble MODE/CNF e o escreve no CRL ou CRH (no F1); se o modo for de interrupção, ainda configura AFIO_EXTICR e os registradores do EXTI. São **424 bytes** de código no F1 (medido com o GCC 14.2, `-Os`).
- `HAL_GPIO_TogglePin()` na versão atual lê o ODR e escreve **no BSRR** (liga os que estavam desligados e desliga os que estavam ligados, numa escrita só) — 6 instruções. Versões antigas faziam `ODR ^= pin`, não atômico. Conferir no código é a única forma de saber.
- `HAL_UART_Transmit()` faz, para cada byte, uma espera de `TXE` **com timeout** baseado em `HAL_GetTick()`, além de travar o handle (`__HAL_LOCK`) e atualizar o estado — por isso é mais lenta que o laço por registrador, mas não trava o sistema para sempre se o periférico não responder.
- Na LL, `LL_GPIO_TogglePin()` e `LL_USART_TransmitData8()` são `static inline` de uma linha: depois de compiladas com `-Os`, são **o mesmo código** do registrador.

**5. Medir o custo.** Pisca do PC13 com espera de 500 ms (sem UART), F103, GCC 14.2 `-Os -ffunction-sections -Wl,--gc-sections`, medido para este roteiro:

| Versão | `.text` total | Descontado o programa vazio (584 B: vetores + startup) |
|---|---|---|
| Registrador + SysTick | 808 B | **224 B** |
| LL (`LL_Init1msTick` + `LL_mDelay`) | 936 B | **352 B** |
| HAL (`HAL_Init` + `HAL_GPIO_Init` + `HAL_Delay`) | 1588 B | **1004 B** |

Em valores absolutos, 1 KB a mais não pesa em 64 KB de flash; o que pesa é **multiplicar** isso por UART, I2C, SPI, DMA e ADC em HAL (dezenas de KB num projeto real) e o **tempo** de cada chamada no caminho crítico (uma rotina de interrupção a 100 kHz). Ferramentas:
- `arm-none-eabi-size firmware.elf` (total), `arm-none-eabi-nm --size-sort -S firmware.elf` (maiores símbolos), o arquivo `.map` (`-Wl,-Map=firmware.map`: de que objeto veio cada função), e o `DWT_CYCCNT` (T09) em volta de cada chamada.

**6. Escolher e misturar.**

| Critério | HAL | LL | Registrador |
|---|---|---|---|
| Portabilidade entre famílias | alta (mesma API em F1, F4, G4…) | média | baixa |
| Tamanho e velocidade | pior | ≈ registrador | melhor |
| Legibilidade e manutenção | boa (nomes, estados) | boa | depende de você |
| Recursos complexos (USB, Ethernet, SD) | pronto | — | inviável sem muito tempo |
| Erros escondidos | *timeouts*, estados, *locks* que você não vê | poucos | todos seus |

Regra prática da indústria: **CubeMX + HAL para inicializar e para periféricos complexos; LL ou registrador nos caminhos críticos** (rotinas de interrupção rápidas, laços de controle). Armadilhas da mistura:
- **`HAL_Delay()` dentro de uma rotina de interrupção** com prioridade igual ou maior (numericamente menor ou igual) que a do SysTick: o tick nunca incrementa, a espera nunca termina. A HAL coloca o SysTick em 15 — **qualquer** interrupção de prioridade 0 a 15 trava. Mesma coisa para os *timeouts* das funções bloqueantes chamadas dentro de interrupções.
- **Mexer no SysTick** (com `SysTick_Config` próprio) quebra o `HAL_GetTick()`. Com um RTOS (M1.7), o CubeMX manda escolher outro timer (TIM6, por exemplo) como *timebase* da HAL.
- **Registrador por baixo de um handle HAL**: escrever direto no `USART1->CR1` depois do `HAL_UART_Init` funciona, mas o `huart1.gState` não sabe; a próxima chamada HAL pode desfazer sua mudança ou recusar com `HAL_BUSY`. Prefira as macros da HAL (`__HAL_UART_ENABLE_IT(&huart1, UART_IT_IDLE)`) ou assuma o periférico inteiro.
- **Callbacks**: rodam **dentro da interrupção**. Nada de `HAL_Delay`, `printf` lento ou espera.
- **Regenerar o código no CubeMX** apaga o que estiver fora das regiões USER CODE.

## Pratique
1. No `stm32f1xx_hal_gpio.c`, encontre a linha em que `HAL_GPIO_Init` escreve no CRL/CRH. Que variável guarda o nibble?
2. Por que a HAL precisa do `HAL_UART_MspInit` separado do `HAL_UART_Init`?
3. Calcule o BRR do exemplo por registrador para 115 200 bit/s com PCLK2 = 72 MHz e com 8 MHz. Qual o erro de cada um?
4. Uma rotina de EXTI com prioridade 5 chama `HAL_Delay(10)`. O que acontece, e por quê?
5. Abra o `.map` de um projeto HAL e liste as cinco maiores funções. Alguma você não chamou diretamente?
6. Reescreva o `HAL_GPIO_TogglePin` em LL e em registrador e compare a desmontagem dos três.
7. Para um produto com USB CDC, ADC a 200 kHz com DMA e uma malha de controle de 20 kHz, que camada você usaria em cada parte?

## Armadilhas comuns
- Usar a HAL sem ler o que ela faz e culpar o hardware quando algo dá errado.
- Escrever código fora das regiões USER CODE e perdê-lo ao regenerar.
- Ignorar o `HAL_StatusTypeDef` de retorno.
- `HAL_Delay` ou funções bloqueantes da HAL dentro de interrupções e callbacks.
- Reconfigurar o SysTick e quebrar a base de tempo da HAL.
- Misturar escrita direta em registradores com um handle HAL sem atualizar o estado.
- Comparar tamanhos sem descontar a parte fixa (vetores, startup) ou sem `--gc-sections`.
- Concluir "HAL é lenta, nunca uso" ou "registrador é coisa do passado": a resposta depende do periférico e do caminho crítico.

## Gabarito
1. No F1, `HAL_GPIO_Init` monta `config` (MODE + CNF) e usa `MODIFY_REG(*configregister, ((GPIO_CRL_MODE0 | GPIO_CRL_CNF0) << registeroffset), (config << registeroffset))`; `configregister` aponta para CRL ou CRH conforme o pino.
2. Porque o `HAL_UART_Init` é portável e não sabe a placa: que pinos, que remapeamento, que prioridade e que canal de DMA. O `MspInit` (`__weak`) é o ponto em que o projeto informa isso.
3. 72 MHz: 625 (erro 0 %). 8 MHz: 69,44 → 69 → 115 942 bit/s (+0,64 %), dentro da tolerância; o F1 aceita fração (USARTDIV = 4,3125 → BRR = 0x45 = 69).
4. Trava: o SysTick tem prioridade 15 e não interrompe a rotina de prioridade 5; `uwTick` não muda e `HAL_Delay` espera para sempre.
5. Normalmente `HAL_GPIO_Init`, `HAL_RCC_ClockConfig`, `HAL_RCC_OscConfig`, `HAL_UART_Transmit` e funções de inicialização do tick ou da biblioteca C, que entram por dependência.
7. USB CDC: HAL/middleware (complexo, não crítico em tempo). ADC com DMA: inicialização HAL ou LL, processamento das metades no seu código. Malha de 20 kHz: rotina de interrupção em LL/registrador, medida com `DWT_CYCCNT`.
