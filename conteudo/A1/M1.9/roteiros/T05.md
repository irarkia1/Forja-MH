## Resumo
**1. A modulação LoRa.** LoRa é uma modulação de **espalhamento espectral por chirp** (CSS) da Semtech. Um **chirp** é um tom que varre linearmente toda a largura de banda (BW) em um tempo de símbolo. O dado está no **ponto de partida** da varredura: com **fator de espalhamento** SF, há 2^SF pontos possíveis, então cada símbolo carrega **SF bits**.
- **Tempo de símbolo**: **T_sym = 2^SF / BW**. Em BW 125 kHz: SF7 = 1,024 ms; SF10 = 8,192 ms; SF12 = 32,768 ms. Cada passo de SF **dobra** o símbolo e leva só 1 bit a mais: a taxa cai quase pela metade.
- **Taxa de codificação** (CR): FEC de 4/5 a 4/8. LoRaWAN usa **4/5**.
- **Taxa de bits** (*LoRa Bit Rate*): **R_b = SF × (BW / 2^SF) × 4/(4 + CR)**, com CR = 1 para 4/5. SF7/125 kHz: 7 × 122,07 × 0,8 = **5469 bit/s**; SF12/125 kHz: **293 bit/s**.
- **Sensibilidade** (T08): −174 + 10·log₁₀(BW) + NF + SNR_min, com SNR_min de −7,5 dB (SF7) a −20 dB (SF12), em passos de 2,5 dB. Com NF = 6 dB e 125 kHz: −124,5 dBm (SF7) a **−137 dBm** (SF12). Cada passo de SF compra 2,5 dB e custa o dobro de tempo no ar.
- **Quase ortogonalidade**: sinais com SFs diferentes no mesmo canal interferem pouco; o gateway demodula vários SFs ao mesmo tempo. Dois sinais no mesmo SF e canal colidem, e o mais forte (por alguns dB) sobrevive: o **efeito de captura**.
- **Larguras de banda**: 125, 250 e 500 kHz. Mais banda, mais taxa, menos sensibilidade (+3 dB de ruído a cada dobro).

**2. O tempo no ar** (AN1200.22, *Time on Air*; datasheet SX1276, *Time on air*). O pacote tem preâmbulo (n_pre símbolos programáveis + 4,25 de sincronização) e payload:

- T_pre = (n_pre + 4,25) × T_sym
- n_payload = 8 + max( ⌈(8·PL − 4·SF + 28 + 16·CRC − 20·IH) / (4·(SF − 2·DE))⌉ × (CR + 4), 0 )
- T_pacote = T_pre + n_payload × T_sym

com PL = bytes do payload físico (no LoRaWAN, o PHYPayload inteiro), CRC = 1 (uplink LoRaWAN), IH = 0 (cabeçalho explícito), CR = 1 (4/5) e **DE = 1** (*Low Data Rate Optimize*) quando T_sym > 16 ms, ou seja, SF11 e SF12 em 125 kHz. O LoRaWAN usa preâmbulo de 8 símbolos.

**Exemplo resolvido 1 (SF9, 12 bytes de aplicação).** PL = 12 + 13 de overhead LoRaWAN (seção 4) = 25 bytes; T_sym = 512/125 000 = 4,096 ms; DE = 0.
- T_pre = 12,25 × 4,096 = 50,18 ms.
- Numerador: 8 × 25 − 36 + 28 + 16 = 208; ⌈208 / 36⌉ = ⌈5,78⌉ = 6; 6 × 5 = 30; n_payload = 38.
- T_payload = 38 × 4,096 = 155,65 ms. Total = **205,8 ms**.

Um calculador em C (`gcc -std=c11 -Wall -Wextra -Werror -O2 lora_airtime.c -lm`), conferido contra uma implementação independente em Python:

```c
/* lora_airtime.c — tempo no ar LoRa pela fórmula da Semtech (AN1200.22 / datasheet SX1276) */
#include <math.h>
#include <stdio.h>

/* pl: bytes do PHYPayload; cr: 1..4 para 4/5..4/8; ih: 1 = cabeçalho implícito; crc: 1 = com CRC */
static double toa_ms(int pl, int sf, double bw_hz, int cr, int preambulo, int ih, int crc)
{
    double tsym = pow(2, sf) / bw_hz * 1000.0;               /* ms */
    int de = tsym > 16.0;                                     /* low data rate optimize */
    double tpre = (preambulo + 4.25) * tsym;
    double num = 8.0 * pl - 4.0 * sf + 28 + 16 * crc - 20 * ih;
    double n = ceil(num / (4.0 * (sf - 2 * de))) * (cr + 4);
    if (n < 0) n = 0;
    return tpre + (8 + n) * tsym;
}

int main(void)
{
    const int app = 4;                         /* 4 bytes de dados de aplicação */
    const int pl = 13 + app;                   /* MHDR 1 + FHDR 7 + FPort 1 + MIC 4 = 13 */
    printf("payload de aplicação %d B, PHYPayload %d B, BW 125 kHz, CR 4/5, preâmbulo 8\n", app, pl);
    printf(" SF   Tsym(ms)  tempo no ar(ms)  msgs/dia na FUP da TTN (30 s)\n");
    for (int sf = 7; sf <= 12; sf++) {
        double t = toa_ms(pl, sf, 125e3, 1, 8, 0, 1);
        printf("%3d %9.3f %14.1f %16d\n", sf, pow(2, sf) / 125.0, t, (int)(30000.0 / t));
    }
    return 0;
}
```

Tempo no ar é **energia** (o SX1276 consome ~29 mA transmitindo a +13/14 dBm pela saída RFO e ~120 mA a +20 dBm pelo PA_BOOST), é **ocupação do canal** (mais colisões para todos) e é **cota** (seção 6). Um nó que pode usar SF7 e usa SF12 gasta 25 vezes mais bateria por mensagem.

**3. A arquitetura do LoRaWAN.** Uma **estrela de estrelas**:
- **Dispositivo final** (*end device*): o seu nó. Transmite quando quer (ALOHA puro, sem escutar antes), em canais sorteados.
- **Gateway**: um concentrador (SX1301/SX1302/SX1303) que escuta **8 canais e todos os SFs ao mesmo tempo** e repassa **tudo** o que ouve, sem decifrar, ao servidor de rede por IP (Wi-Fi, Ethernet, celular), pelo protocolo UDP da Semtech (porta 1700) ou pelo *LoRa Basics Station* (WebSocket com TLS). O dispositivo **não se associa** a um gateway: vários podem ouvir a mesma mensagem.
- **Network Server** (NS): elimina duplicatas, confere o MIC e o contador, roda o **ADR**, escolhe por qual gateway enviar o downlink e responde aos comandos MAC.
- **Join Server** (JS): guarda a AppKey e atende o join (OTAA).
- **Application Server** (AS): decifra o payload com a AppSKey e entrega à sua aplicação (na TTN: integrações MQTT, webhooks, armazenamento).
Na TTN, NS, JS e AS são a *The Things Stack*; a comunidade fornece os gateways.

**Classes** (*LoRaWAN Classes*):
- **Classe A** (obrigatória, a de bateria): depois de **cada uplink**, abre duas janelas curtas de recepção: **RX1** a 1 s (RECEIVE_DELAY1) e **RX2** a 2 s; no join, 5 s e 6 s. Fora delas, o servidor **não alcança** o dispositivo: um comando espera o próximo uplink.
- **Classe B**: além da A, abre **ping slots** periódicos, sincronizados por beacons dos gateways (a cada 128 s). Latência de downlink controlada, consumo moderado. Pouco usada.
- **Classe C**: receptor **sempre ligado**, exceto quando transmite. Downlink quase imediato; consumo de RX contínuo (~10 mA no SX1276): para aparelhos na tomada (atuadores, iluminação pública).

**4. O quadro** (*MAC Message Formats*):

```
PHYPayload = MHDR (1) | MACPayload | MIC (4)
MACPayload = FHDR | FPort (1) | FRMPayload (cifrado)
FHDR       = DevAddr (4) | FCtrl (1) | FCnt (2) | FOpts (0–15)
```

- **MHDR**: tipo da mensagem (MType nos 3 bits altos: join-request, join-accept, unconfirmed/confirmed data up/down).
- **DevAddr**: endereço de 32 bits da sessão, atribuído pela rede (não é o DevEUI).
- **FCtrl**: bits ADR, ADRACKReq, ACK e o tamanho de FOpts (comandos MAC "de carona").
- **FCnt**: contador de quadros; vão 16 bits no ar, a rede guarda 32. Proteção contra **replay**: quadro com contador repetido ou menor é descartado.
- **FPort**: 1–223 para a aplicação; 0 = só comandos MAC.
- **MIC**: AES-CMAC de 4 bytes com a chave de rede, sobre o quadro todo: prova que veio de quem tem a chave e não foi alterado.
- **Overhead mínimo**: 1 + 7 + 1 + 4 = **13 bytes**. Para 4 bytes de dado, 17 no ar.
- Valores multibyte são **little-endian** (o DevAddr 0x260B1234 vai como `34 12 0B 26`).

Cifra (LoRaWAN 1.0.x): o FRMPayload vai cifrado com **AppSKey** (AES-128 em modo contador), que só o servidor de aplicação conhece; o MIC usa a **NwkSKey**. A rede autentica, mas não lê os seus dados. (O LoRaWAN 1.1 divide a chave de rede em três; a TTN e a maioria dos dispositivos usam 1.0.3/1.0.4.)

Um decodificador dos campos de cabeçalho, para os quadros que você vai ver no console do gateway (`gcc -std=c11 -Wall -Wextra -Werror -O2 lorawan_quadro.c`):

```c
/* lorawan_quadro.c — decodifica os campos de cabeçalho de um PHYPayload LoRaWAN 1.0.x de dados */
#include <ctype.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static const char *TIPOS[8] = { "Join-request", "Join-accept", "Unconfirmed Data Up",
                                "Unconfirmed Data Down", "Confirmed Data Up",
                                "Confirmed Data Down", "RFU", "Proprietary" };

static int hex_para_bytes(const char *hex, uint8_t *out, int max)
{
    int n = 0;
    while (hex[0] && hex[1] && n < max) {
        if (!isxdigit((unsigned char)hex[0]) || !isxdigit((unsigned char)hex[1])) return -1;
        sscanf(hex, "%2hhx", &out[n++]);
        hex += 2;
    }
    return hex[0] ? -1 : n;
}

int main(int argc, char **argv)
{
    const char *hex = argc > 1 ? argv[1] : "4034120B26802A0001A1B2C3D411223344";
    uint8_t q[256];
    int n = hex_para_bytes(hex, q, sizeof q);
    if (n < 12) { fprintf(stderr, "quadro curto ou hex inválido\n"); return 1; }

    int mtype = q[0] >> 5;                                    /* MHDR: MType nos 3 bits altos */
    printf("MHDR    0x%02X  %s, Major %d\n", q[0], TIPOS[mtype], q[0] & 0x03);
    if (mtype < 2 || mtype > 5) { printf("(não é quadro de dados)\n"); return 0; }

    /* campos multibyte do LoRaWAN são little-endian */
    uint32_t devaddr = (uint32_t)q[1] | (uint32_t)q[2] << 8 | (uint32_t)q[3] << 16 | (uint32_t)q[4] << 24;
    uint8_t fctrl = q[5];
    uint16_t fcnt = (uint16_t)(q[6] | q[7] << 8);
    int foptslen = fctrl & 0x0F;
    int uplink = (mtype == 2 || mtype == 4);
    printf("DevAddr %08X\n", (unsigned)devaddr);
    printf("FCtrl   0x%02X  ADR=%d %s=%d ACK=%d FOptsLen=%d\n", fctrl, fctrl >> 7 & 1,
           uplink ? "ADRACKReq" : "RFU", fctrl >> 6 & 1, fctrl >> 5 & 1, foptslen);
    printf("FCnt    %u (16 bits baixos do contador)\n", fcnt);

    int pos = 8 + foptslen;                                   /* depois do FHDR */
    int fim = n - 4;                                          /* MIC: 4 últimos bytes */
    if (pos > fim) { fprintf(stderr, "FOpts maior que o quadro\n"); return 1; }
    if (pos < fim) {
        printf("FPort   %d%s\n", q[pos], q[pos] == 0 ? " (comandos MAC, cifrados com NwkSKey)" : "");
        printf("FRMPayload %d bytes (cifrado com %s)\n", fim - pos - 1, q[pos] ? "AppSKey" : "NwkSKey");
    } else {
        printf("sem FPort nem FRMPayload\n");
    }
    printf("MIC     %02X%02X%02X%02X\n", q[fim], q[fim + 1], q[fim + 2], q[fim + 3]);
    printf("overhead LoRaWAN: %d de %d bytes\n", n - (pos < fim ? fim - pos - 1 : 0), n);
    return 0;
}
```

Para conferir também o MIC e decifrar o payload, use a biblioteca **lora-packet** (npm) ou o decodificador online da TTN Community, passando as chaves de sessão do console; nunca cole chaves de produção em sites de terceiros.

**ADR** (*Adaptive Data Rate*). O servidor olha a SNR dos últimos uplinks (tipicamente 20) e calcula a folga: margem = SNR_máx − SNR_mín(SF atual) − margem de instalação (10 dB no algoritmo recomendado da Semtech; a TTN usa um valor próprio). Cada 3 dB de folga permitem **um passo**: primeiro reduzir o SF até SF7, depois reduzir a potência. O servidor manda um **LinkADRReq**. Do lado do nó, se ficar `ADR_ACK_LIMIT` (64) uplinks sem ouvir nada da rede, ele pede resposta (ADRACKReq) e, sem resposta, **sobe o SF** sozinho (*Retransmissions backoff*), para não ficar mudo depois de mudar de lugar. ADR é para nós **parados**; nó móvel deve fixar um SF conservador ou usar ADR do lado do dispositivo.

**Exemplo resolvido 2 (ADR).** Um nó em SF12 tem SNR máxima de 2 dB nos últimos 20 uplinks. SNR mínima do SF12: −20 dB. Margem = 2 − (−20) − 10 = 12 dB → 12/3 = **4 passos**: SF12 → **SF8**. O tempo no ar do pacote de 17 bytes cai de 1318,9 ms para 92,7 ms: **14 vezes** menos energia por mensagem.

**5. O plano AU915 no Brasil** (RP002-1.0.4, *AU915-928MHz ISM Band*). A faixa brasileira de 915–928 MHz permite usar o plano australiano (M0.3.T06). O plano tem:
- **Uplink**: 64 canais de 125 kHz, de **915,2 MHz** em passos de **200 kHz** (canal n: 915,2 + 0,2·n MHz; DR0 a DR5 = SF12 a SF7), e 8 canais de 500 kHz a partir de 915,9 MHz em passos de 1,6 MHz (DR6 = SF8/500 kHz).
- **Downlink**: 8 canais de 500 kHz a partir de **923,3 MHz** em passos de **600 kHz**. Na RX1, o canal é o do uplink módulo 8 e a taxa sai de uma tabela (uplink DR0 → DR8 = SF12/500 kHz …). **RX2** padrão: 923,3 MHz, DR8.
- **Sub-bandas**: grupos de 8 canais de 125 kHz. Gateways comuns escutam só 8 canais; a **TTN usa a sub-banda 2** (canais 8 a 15, 916,8 a 918,2 MHz, mais o canal de 500 kHz 65, em 917,5 MHz). No console da TTN, o plano se chama *Australia 915-928 MHz, FSB 2 (used by TTN)*. Um nó que sorteia entre os 64 canais erra 7 em cada 8 transmissões: configure a sub-banda.
- **EIRP máximo** padrão de 30 dBm.
- **Dwell time**: o plano prevê o limite de **400 ms** por transmissão (*UplinkDwellTime*, ajustável pela rede com *TxParamSetupReq*); a LMIC usada no laboratório começa com ele **ativo** no AU915. Com 400 ms, **SF12 e SF11 não servem para uplink em 125 kHz** (até o menor quadro, de 13 bytes, leva 577,5 ms em SF11) e o DR2 (SF10) fica limitado a 11 bytes de aplicação (24 bytes no ar: 370,7 ms). Confira o que a sua rede configura e a tabela *Maximum Payload Size* da versão do RP002 que ela usa.

**Exemplo resolvido 3 (canais).** Um uplink no canal 10 sai em 915,2 + 0,2 × 10 = **917,2 MHz**. A resposta em RX1 vem no canal de downlink 10 mod 8 = 2: 923,3 + 0,6 × 2 = **924,5 MHz**, em 500 kHz.

**6. OTAA, ABP e as regras de uso.**

**OTAA** (*Over-the-Air Activation*, recomendado). O dispositivo vem com **DevEUI** (64 bits, identidade), **JoinEUI** (antigo AppEUI, 64 bits, o join server) e **AppKey** (128 bits, segredo raiz, única por dispositivo). Ele envia um **Join-request** (JoinEUI, DevEUI e **DevNonce**, com MIC pela AppKey); o join server responde com um **Join-accept** cifrado (JoinNonce, NetID, **DevAddr**, parâmetros de RX e, no AU915, a máscara de canais). Os dois lados derivam **NwkSKey** e **AppSKey** novas. No 1.0.4, o DevNonce é um **contador** que nunca se repete: guarde-o em memória não volátil, senão a rede recusa os joins depois de um reset. Vantagens: chaves de sessão novas a cada join, rede pode mudar (DevAddr não é fixo), roaming.

**ABP** (*Activation by Personalization*). DevAddr, NwkSKey e AppSKey vêm gravados de fábrica; não há join. Parece mais simples e é uma armadilha: os **contadores de quadro** precisam sobreviver a resets e trocas de bateria (senão a rede descarta tudo como replay até o contador passar do último valor visto), as chaves nunca mudam e o dispositivo fica preso a uma rede. Desligar a verificação de contador no servidor "resolve" abrindo a porta ao replay. Use OTAA; ABP só em casos muito específicos.

**Duty cycle.** Na Europa (EU868), a regulamentação limita o tempo de transmissão em cada sub-banda, tipicamente **1%**: depois de transmitir T, o rádio fica 99·T calado naquela sub-banda. Um pacote de 1318,9 ms em SF12 impõe ≥ 131,9 s entre inícios de transmissão. No Brasil, a regra da Anatel é de outro tipo (potência, número de canais e permanência), e o AU915 não impõe duty cycle de 1%; quem limita na prática é a rede.

**Política de uso justo da TTN** (*Fair Use Policy*): na rede comunitária, cada dispositivo pode usar até **30 s de tempo no ar de uplink por dia** e receber no máximo **10 downlinks por dia** (incluindo confirmações). Daí a última coluna da tabela da seção 2: com 4 bytes em SF10, 90 mensagens por dia (uma a cada 16 min); em SF7, 583. Por isso: payload binário e pequeno (nada de JSON no rádio), **unconfirmed** como padrão e ADR ligado para nós fixos.

**Payload formatter.** Na TTN, uma função JavaScript transforma os bytes em campos. Para o payload do laboratório (temperatura int16 em 0,01 °C e bateria uint16 em mV, big-endian), testada com Node.js:

```js
function decodeUplink(input) {
  if (input.fPort !== 1 || input.bytes.length !== 4) {
    return { errors: ["formato desconhecido na porta " + input.fPort] };
  }
  var b = input.bytes;
  var t = (b[0] << 8) | b[1];
  if (t & 0x8000) t -= 0x10000;            // int16 com sinal
  var mv = (b[2] << 8) | b[3];
  return {
    data: { temperatura_c: t / 100, bateria_v: mv / 1000 },
    warnings: mv < 3300 ? ["bateria fraca"] : [],
    errors: []
  };
}
```

`09 2E 0E 80` → `{"temperatura_c":23.5,"bateria_v":3.712}`; `FF 38 0C 80` → −2 °C, 3,2 V e o aviso de bateria fraca.

**7. O nó com ESP32.** O rádio é um **SX1276** (módulo RFM95W, ou placas como LilyGO LoRa32 e Heltec V2, **na versão de 915 MHz**) ligado por SPI (M1.5) e dois pinos de interrupção (DIO0: fim de TX/RX; DIO1: tempo esgotado de RX). A pilha LoRaWAN roda no ESP32: a **ttn-esp32**, componente ESP-IDF sobre a LMIC da MCCI, que faz join, janelas RX1/RX2, ADR, contadores e guarda chaves e sessão na NVS. Configure no `menuconfig` (*Components → The Things Network*) a região **Australia (915 MHz)** e o rádio **SX1276/77/78/79**. Compilado no ESP-IDF v5.5 para o ESP32 com a ttn-esp32 no diretório `components/`:

```c
/* no_lorawan.c — nó LoRaWAN classe A com a ttn-esp32: SX1276, AU915 sub-banda 2, OTAA, uplink e downlink */
#include <stdint.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"
#include "driver/spi_master.h"
#include "esp_log.h"
#include "ttn.h"

static const char *TAG = "lorawan";

/* ESP32-DevKitC + módulo RFM95W (SX1276, versão 915 MHz) ligados por fios: ajuste à sua placa */
#define LORA_SPI   SPI2_HOST
#define PINO_SCLK  18
#define PINO_MISO  19
#define PINO_MOSI  23
#define PINO_NSS   5
#define PINO_RST   14
#define PINO_DIO0  26
#define PINO_DIO1  33

/* copiados do console da TTN; num produto, gravados por AT na fábrica (ttn_start_provisioning_task) */
#define DEV_EUI  "70B3D57ED0000000"
#define JOIN_EUI "0000000000000000"
#define APP_KEY  "00000000000000000000000000000000"

static volatile uint32_t intervalo_s = 900;      /* 15 min: cabe na FUP da TTN até SF10 (seção 6) */

/* downlink na porta 10 com 2 bytes = novo intervalo em segundos (big-endian) */
static void ao_downlink(const uint8_t *msg, size_t n, ttn_port_t porta)
{
    if (porta == 10 && n == 2) {
        uint32_t s = (uint32_t)msg[0] << 8 | msg[1];
        if (s >= 300 && s <= 3600) intervalo_s = s;     /* valida antes de obedecer */
        ESP_LOGI(TAG, "downlink: intervalo agora %lu s", (unsigned long)intervalo_s);
    }
}

static const char *NOME_SF[] = { "-", "FSK", "SF7", "SF8", "SF9", "SF10", "SF11", "SF12" };

static void tarefa_envio(void *arg)
{
    for (uint16_t n = 0;; n++) {
        int16_t t = 2350 + n % 10;                       /* 0,01 °C: aqui entra o sensor do M1.8 */
        uint16_t mv = 3712;                              /* tensão da bateria */
        uint8_t carga[4] = { (uint8_t)(t >> 8), (uint8_t)t, (uint8_t)(mv >> 8), (uint8_t)mv };

        ttn_response_code_t r = ttn_transmit_message(carga, sizeof carga, 1, false);
        ttn_rf_settings_t rf = ttn_tx_settings();
        ESP_LOGI(TAG, "uplink %u %s: %s, %lu Hz", n,
                 r == TTN_SUCCESSFUL_TRANSMISSION ? "enviado" : "falhou",
                 NOME_SF[rf.spreading_factor], (unsigned long)rf.frequency);
        vTaskDelay(pdMS_TO_TICKS(intervalo_s * 1000));
    }
}

void no_lorawan_iniciar(void)
{
    /* nvs_flash_init() já foi chamado: a biblioteca guarda as chaves e a sessão na NVS */
    ESP_ERROR_CHECK(gpio_install_isr_service(ESP_INTR_FLAG_IRAM));
    spi_bus_config_t bus = {
        .miso_io_num = PINO_MISO, .mosi_io_num = PINO_MOSI, .sclk_io_num = PINO_SCLK,
        .quadwp_io_num = -1, .quadhd_io_num = -1,
    };
    ESP_ERROR_CHECK(spi_bus_initialize(LORA_SPI, &bus, SPI_DMA_DISABLED));

    ttn_init();
    ttn_configure_pins(LORA_SPI, PINO_NSS, TTN_NOT_CONNECTED, PINO_RST, PINO_DIO0, PINO_DIO1);
    ttn_set_subband(2);                                  /* TTN no AU915: canais 8–15 e 65 */
    ttn_provision(DEV_EUI, JOIN_EUI, APP_KEY);           /* grava na NVS (uma vez basta) */
    ttn_on_message(ao_downlink);

    ESP_LOGI(TAG, "join OTAA...");
    if (!ttn_join()) {
        ESP_LOGE(TAG, "join falhou: confira chaves, plano de frequência e cobertura");
        return;
    }
    ESP_LOGI(TAG, "join aceito");
    xTaskCreate(tarefa_envio, "lorawan", 4096, NULL, 3, NULL);
}
```

Notas:
- Payload **binário** de 4 bytes; o formatter da seção 6 o decodifica.
- O downlink é **validado** antes de ser obedecido: um comando é dado vindo de fora (T09).
- Para bateria, troque o laço por deep sleep: `ttn_wait_for_idle()` e `ttn_prepare_for_deep_sleep()` antes de dormir e `ttn_resume_after_deep_sleep()` ao acordar, que preservam a sessão e os contadores sem novo join (exemplo `deep_sleep_in_c` da biblioteca).
- A ttn-esp32 suporta **SX127x**. Para o **SX126x** (SX1262 da Heltec V3 e de módulos recentes, mais eficiente), as opções em ESP-IDF são a **RadioLib** (C++, com camada de hardware para ESP-IDF) ou a *LoRaMac-node* da Semtech portada; outra via é um **modem AT** com a pilha LoRaWAN embutida (Wio-E5/LoRa-E5, com STM32WLE5; RAK3172), em que o ESP32 só manda comandos como `AT+JOIN` e `AT+MSGHEX` pela UART (o T06 mostra como escrever um driver AT robusto).

## Laboratório
### Material
- **Trilha com rádio (recomendada)**:
  - ESP32-DevKitC (ou C3/S3) com módulo **RFM95W 915 MHz** (SX1276) ligado por fios (SPI, NSS, RST, DIO0, DIO1, 3,3 V e GND), ou uma placa integrada **LilyGO LoRa32 / Heltec WiFi LoRa 32 V2** em 915 MHz. Confira a frequência na etiqueta: módulos de 433 e 868 MHz são vendidos lado a lado e não funcionam aqui.
  - **Antena de 915 MHz** com o conector certo (u.FL/SMA). **Nunca transmita sem antena**: a potência refletida pode danificar o PA.
  - Cobertura TTN: consulte o mapa em ttnmapper.org e a lista de gateways da comunidade na sua cidade. Sem cobertura, um gateway próprio **homologado na Anatel** em AU915 (The Things Indoor Gateway na versão AU915, RAK WisGate Edge Lite 2 ou Raspberry Pi com concentrador SX1302), registrado na sua conta da TTN. Gateways de canal único não são compatíveis com LoRaWAN de verdade e não devem ser usados na TTN.
  - Conta gratuita na **The Things Network** (The Things Stack Community Edition), PC com ESP-IDF v5.x.
  - Alternativa ao SX1276: um **modem AT** LoRaWAN (Wio-E5 ou RAK3172) ligado à UART do ESP32; a parte de pilha fica no modem e o seu firmware manda comandos AT.
  - Opcional: multímetro em série (ou o medidor do M1.11) para medir a corrente de TX e RX.
- **Trilha sem rádio** (se não houver placa ou cobertura):
  - Os programas `lora_airtime.c` e `lorawan_quadro.c` deste roteiro e uma implementação sua do tempo no ar em Python ou planilha.
  - O console da TTN com um dispositivo registrado e o recurso **Simulate uplink** (aba *Messaging*), que injeta um uplink com o FPort e os bytes que você escolher e passa pelo payload formatter e pelas integrações.
  - **ChirpStack** em Docker com o **chirpstack-simulator** (simula dispositivos e gateway e gera tráfego LoRaWAN real, com join e uplinks cifrados) e o **Wireshark** capturando a interface Docker na porta UDP 1700: os quadros do protocolo de encaminhamento da Semtech, com o PHYPayload em base64 dentro do JSON.

### Passo a passo
**Experimento 1 — Contas antes do rádio (≈ 3 h).**
1. Implemente a fórmula do tempo no ar numa linguagem diferente do C (Python ou planilha) e confira contra o `lora_airtime.c` para PL de 13, 17, 25 e 51 bytes em SF7 a SF12. Os valores devem bater ao décimo de ms.
2. Para o seu caso (escolha um: estação de umidade do solo a 2 km do gateway, hidrômetro em caixa de concreto a 500 m, rastreador de gado), monte o orçamento de enlace do T08, escolha o menor SF com 15 dB de margem e calcule: tempo no ar, mensagens por dia na FUP da TTN, carga por mensagem (corrente de TX × tempo no ar, mais as duas janelas de RX) e autonomia de uma bateria de 2400 mAh.
3. Verifique se o seu SF é permitido com o dwell time de 400 ms e quantos bytes cabem.

**Experimento 2 — Registro na TTN (≈ 2 h).**
1. Crie uma aplicação e um dispositivo com **entrada manual**: plano *Australia 915-928 MHz, FSB 2 (used by TTN)*, versão LoRaWAN 1.0.3 ou 1.0.4, OTAA; gere DevEUI e AppKey (JoinEUI pode ser zeros). Escolha o cluster que o console sugerir para o Brasil.
2. Cole o payload formatter da seção 6 e teste com **Simulate uplink** (`092E0E80` na porta 1). Na trilha sem rádio, simule também bytes fora do formato e uma bateria fraca.
3. Crie uma integração (MQTT ou webhook para um serviço de teste) e veja o JSON que a TTN entrega: o M1.10 parte daqui.

**Experimento 3 — O nó no ar (≈ 5 h).**
1. Monte o hardware e o projeto com a ttn-esp32 e o `no_lorawan.c` (região AU915, SX1276, sub-banda 2). Para teste, use intervalo de 5 min.
2. Faça o join e registre no console (*Live data*) o Join-request, o Join-accept e os primeiros uplinks: **SF, frequência, RSSI, SNR, gateway(s), tempo no ar** informado pelo console e o FCnt.
3. Compare o tempo no ar do console com o do seu cálculo. Confira que as frequências estão entre 916,8 e 918,2 MHz.
4. Agende um **downlink** na porta 10 (`0258` = 600 s) e observe quando ele chega (só depois do próximo uplink: classe A). Envie também um valor inválido e veja o firmware ignorá-lo.
5. Desligue o ADR, fixe SF7, SF9 e SF12 (`ttn_set_adr_enabled(false)` e `ttn_set_data_rate(TTN_DR_AU915_SF…)`; lembre do dwell time) e compare RSSI, SNR e tempo no ar.
6. Reinicie a placa e veja: há novo join? O FCnt recomeça? Implemente o ciclo com deep sleep e confira que a sessão continua.

**Experimento 4 — Alcance (≈ 3 h).**
1. Com o nó em SF fixo, faça medições em pelo menos 6 pontos a distâncias diferentes do gateway (ou use o app TTN Mapper), anotando RSSI, SNR e se o pacote chegou.
2. Ajuste o expoente n do modelo log-distância (T08) aos seus pontos e compare com o espaço livre.
3. Ponha a antena do nó dentro de uma caixa metálica, junto ao corpo e a 2 m de altura. Registre a variação.

**Experimento 5 — Dentro do quadro (≈ 3 h).**
1. Copie o PHYPayload (base64 → hex) de um uplink no console do gateway (ou da captura na porta 1700, na trilha ChirpStack) e decodifique com o `lorawan_quadro.c`. Confira DevAddr, FCnt e FPort com o console.
2. Com as chaves de sessão do seu dispositivo de **teste**, confira o MIC e decifre o payload com a lora-packet.
3. Explique por que o gateway, que repassou o quadro, não consegue ler a temperatura.

### Evidência
Registre no jogo:
1. **Tabela de tempo no ar**: os seus valores × `lora_airtime.c` × o que o console mostrou (pelo menos 3 SFs).
2. **Orçamento** do seu caso (Experimento 1.2): enlace, SF escolhido, margem, mensagens por dia, autonomia.
3. **Capturas do console** da TTN: join, uplinks decodificados pelo formatter com RSSI, SNR, SF e frequência, e o downlink recebido (ou, na trilha sem rádio, o Simulate uplink e a captura do ChirpStack).
4. **Tabela de alcance** (Experimento 4) com o expoente n ajustado, ou, sem rádio, a análise de um quadro capturado.
5. **Logs** do monitor do ESP32 (join, uplinks, downlink, retomada depois do deep sleep).
6. **Código** (link do repositório), sem chaves no repositório.
7. **Descrição** (5–10 frases): qual SF o seu caso exige e quanto isso custa em bateria e em cota; o que aconteceria com ABP num reset; o que foi feito com rádio e o que foi simulado.

## Pratique
1. Calcule T_sym e R_b para SF8 e SF11 em 125 kHz, CR 4/5.
2. Calcule à mão o tempo no ar de um PHYPayload de 20 bytes em SF7 e em SF12 (125 kHz, CR 4/5, preâmbulo 8).
3. Por que dobrar o SF dá só 2,5 dB a mais de sensibilidade e custa o dobro de tempo?
4. Um nó classe A envia um uplink às 10:00:00,0. Quando abrem as janelas RX1 e RX2? Quando o servidor pode mandar um comando que acabou de chegar às 10:00:05?
5. Quais campos do quadro a rede lê e quais ela não consegue ler? Por quê?
6. Em que frequência sai um uplink no canal 13 do AU915? E a RX1 correspondente?
7. Com 10 bytes de aplicação em SF9, quantos uplinks por dia cabem na FUP da TTN?
8. Na Europa, com duty cycle de 1%, qual o intervalo mínimo entre uplinks de 1 s de tempo no ar?
9. Um lote de sensores ABP voltou de uma troca de bateria e nenhum aparece mais no servidor. Explique e corrija.
10. O ADR mandou o nó para SF7. Ele foi levado a um porão e sumiu. O que acontece depois?

## Armadilhas comuns
- Comprar rádio de 868 ou 433 MHz para usar no Brasil.
- Transmitir sem antena.
- Esquecer a sub-banda 2 no AU915 e perder a maioria dos uplinks.
- Usar SF12 "para garantir": 25 vezes mais energia e cota que SF7, e proibido com dwell time de 400 ms.
- Mandar JSON ou texto pelo rádio em vez de bytes.
- Pedir confirmação (confirmed uplink) em toda mensagem: gasta os 10 downlinks diários e energia.
- Achar que o servidor pode falar com um nó classe A a qualquer hora.
- ABP com contadores que voltam a zero; desligar a verificação de contador.
- Não guardar o DevNonce ou a sessão e fazer join a cada boot.
- ADR em nó móvel.
- Chaves de dispositivo no repositório ou iguais em todos os aparelhos.
- Gateway de canal único na TTN; gateway sem homologação.
- Comparar o tempo no ar do seu cálculo com o console sem conferir o PL completo (13 bytes de overhead).

## Gabarito
1. SF8: T_sym = 256/125 000 = 2,048 ms; R_b = 8 × 488,3 × 0,8 = 3125 bit/s. SF11: T_sym = 16,384 ms; R_b = 11 × 61,04 × 0,8 = 537 bit/s.
2. SF7: T_pre = 12,25 × 1,024 = 12,54 ms; ⌈(160 − 28 + 28 + 16)/28⌉ = ⌈6,29⌉ = 7 → 35 + 8 = 43 símbolos = 44,03 ms; total 56,6 ms. SF12 (DE = 1): T_pre = 401,4 ms; ⌈(160 − 48 + 44)/40⌉ = ⌈3,9⌉ = 4 → 20 + 8 = 28 símbolos = 917,5 ms; total 1318,9 ms.
3. O símbolo dobra de duração e passa a carregar só 1 bit a mais: a taxa quase cai pela metade. O ganho de processamento é a energia acumulada no dobro de tempo: 10·log₁₀(2) ≈ 3 dB teóricos, ~2,5 dB na tabela da Semtech.
4. RX1 às 10:00:01,0 e RX2 às 10:00:02,0. O comando que chega às 10:00:05 só pode descer depois do próximo uplink.
5. A rede lê o cabeçalho (MHDR, DevAddr, FCtrl, FCnt, FPort, FOpts) e confere o MIC com a NwkSKey. O FRMPayload está cifrado com a AppSKey, que só o servidor de aplicação tem.
6. 915,2 + 0,2 × 13 = 917,8 MHz. RX1 no canal de downlink 13 mod 8 = 5: 923,3 + 3,0 = 926,3 MHz.
7. PL = 23 bytes; em SF9, ⌈(184 − 36 + 44)/36⌉ = ⌈5,33⌉ = 6 → 38 símbolos, o mesmo que para 25 bytes: 205,8 ms; 30 000 / 205,8 = 145 uplinks por dia.
8. 1 s / 0,01 = 100 s entre inícios (99 s de silêncio depois de cada transmissão de 1 s).
9. Os contadores de quadro voltaram a zero; a rede descarta os quadros como replay até o contador passar do último valor recebido. Correção: guardar o FCnt em memória não volátil (ou migrar para OTAA, com novo join e contadores novos). Desligar a verificação de contador só esconde o problema.
10. Sem ouvir a rede, depois de ADR_ACK_LIMIT uplinks o nó passa a pedir resposta (ADRACKReq) e, sem resposta por mais ADR_ACK_DELAY uplinks, sobe a potência e o SF passo a passo até voltar a ser ouvido.
