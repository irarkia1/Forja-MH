# M1.3.T09 — Startup, vetor de interrupções e linker script

> Entre ligar a placa e a primeira linha do `main` acontece muita coisa que o Arduino e o CubeIDE escondem: o núcleo lê o ponteiro de pilha e o endereço de reset da tabela de vetores, um código de startup copia as variáveis inicializadas para a SRAM e zera as outras, e o linker script decidiu, na compilação, onde cada byte mora. Este tópico junta memória (T04), mapa (T05) e exceções (T06) para que você consiga escrever esse caminho do zero — e consertá-lo quando o firmware "não chega ao main".

## Ao final você consegue
- Descrever a sequência de reset do Cortex-M (SP inicial no endereço 0x0, vetor de reset no 0x4, bit Thumb) e do AVR (vetor de reset no endereço 0 com JMP).
- Explicar o que o código de startup faz antes do main: copiar .data da flash para a SRAM, zerar .bss, chamar SystemInit e os construtores.
- Ler um linker script mínimo (MEMORY, SECTIONS, > RAM AT> FLASH, símbolos de início e fim de seção) e calcular o uso de flash e SRAM a partir da saída de size.
- Montar a tabela de vetores em C (atributos section e weak, alias para Default_Handler) e calcular o deslocamento e o conteúdo de cada entrada.

## Resumo
**1. O reset do Cortex-M.** Ao sair do reset, o núcleo faz duas leituras e mais nada:
1. Lê a palavra no endereço **0x0000_0000** e a coloca no **MSP** (pilha inicial).
2. Lê a palavra em **0x0000_0004** — o **vetor de reset** — e a coloca no **PC**. O bit 0 dessa palavra precisa ser 1 (estado Thumb); o endereço real é o valor com o bit 0 zerado. Com o bit 0 em 0, o núcleo falha na primeira instrução.

No STM32 com BOOT0 = 0, a flash (0x0800_0000) aparece espelhada em 0x0000_0000, então essas leituras pegam o começo da flash. Depois do reset, o **VTOR** (`SCB->VTOR`, em 0xE000_ED08) diz onde está a tabela; mudá-lo é o que permite um bootloader e uma aplicação terem tabelas próprias.

**Exemplo 1 (tabela real).** Um firmware mínimo para STM32F103 (flash de 64 KB, SRAM de 20 KB), compilado e ligado com o linker script deste tópico (no teste feito para este roteiro, com clang e lld; com o gcc os endereços das funções mudam um pouco), tem nas primeiras palavras da flash: `0x2000_5000` (topo da SRAM = MSP inicial), `0x0800_0059` (Reset_Handler em 0x0800_0058, com o bit Thumb), `0x0800_00AF`, `0x0800_00AF` (NMI e HardFault apontando para o mesmo Default_Handler)… e na posição 15 (deslocamento 0x3C) o SysTick_Handler escrito pelo usuário.

**2. O reset do AVR.** O ATmega328P começa em PC = 0x0000 (ou na seção de boot, se o fuse BOOTRST estiver programado). A tabela de vetores é feita de **instruções**: 26 vetores, cada um um `jmp` de 2 palavras (4 bytes) — 104 bytes, de 0x0000 a 0x0067. Saída real do `avr-objdump -d` (avr-gcc 14, `-Os`):
```
00000000 <__vectors>:
   0:	0c 94 34 00 	jmp	0x68	; 0x68 <__ctors_end>
   4:	0c 94 3e 00 	jmp	0x7c	; 0x7c <__bad_interrupt>
   ...
00000068 <__ctors_end>:
  68:	11 24       	eor	r1, r1          ; r1 = 0 (o avr-gcc conta com isso)
  6a:	1f be       	out	0x3f, r1        ; SREG = 0
  6c:	cf ef       	ldi	r28, 0xFF
  6e:	d8 e0       	ldi	r29, 0x08
  70:	de bf       	out	0x3e, r29       ; SPH = 0x08
  72:	cd bf       	out	0x3d, r28       ; SPL = 0xFF → SP = 0x08FF (fim da SRAM)
  74:	0e 94 5f 00 	call	0xbe            ; main
0000007c <__bad_interrupt>:
  7c:	0c 94 00 00 	jmp	0               ; interrupção sem tratador → volta ao reset
```
No AVR, ao contrário do Cortex-M, quem inicializa o SP é o software. Repare no `jmp 0x68` codificado como `34 00`: o campo de endereço conta **palavras** (0x34 × 2 = 0x68). Como este programa não tem `.data` nem `.bss`, o avr-libc nem inclui as rotinas de cópia.

**3. O código de startup (Cortex-M).** O `Reset_Handler` típico (o da ST está em assembly, mas cabe em C):
```c
extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;   // vêm do linker script
void Reset_Handler(void)
{
    uint32_t *src = &_sidata, *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;      // 1. copia .data: flash → SRAM
    for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;   // 2. zera .bss
    SystemInit();                                // 3. clock, FPU (CPACR no M4F), VTOR
    __libc_init_array();                         // 4. construtores C++ e funções de init
    main();                                      // 5.
    for (;;) {}                                  // se o main retornar
}
```
- **.data**: variáveis com valor inicial (`int x = 5;`). O 5 precisa sobreviver sem energia → fica na flash; a variável precisa ser alterável → mora na SRAM. O startup copia.
- **.bss**: variáveis sem inicializador ou inicializadas com zero. Não ocupam flash; o startup zera.
- Os arquivos da ST chamam `SystemInit` antes da cópia em algumas versões e depois em outras: a ordem entre esses passos varia, mas **tudo** acontece antes do `main`.
- O tempo do startup conta: zerar 8 KB de `.bss` a 8 MHz (clock do HSI, antes do PLL) leva centenas de microssegundos.

**4. O linker script.** Diz ao linker onde cada seção mora:
```
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);        /* 0x20005000: topo da pilha */

SECTIONS
{
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH      /* tabela no início da flash */
  .text   : { *(.text*) *(.rodata*) . = ALIGN(4); } > FLASH
  _sidata = LOADADDR(.data);                           /* onde a cópia de .data está na flash */
  .data   : { _sdata = .; *(.data*) . = ALIGN(4); _edata = .; } > RAM AT> FLASH
  .bss    : { _sbss = .; *(.bss*) *(COMMON) . = ALIGN(4); _ebss = .; } > RAM
}
```
- **VMA** (endereço de execução) × **LMA** (endereço de carga). `> RAM AT> FLASH` significa: o código acessa `.data` na SRAM (VMA), mas o conteúdo inicial é gravado na flash (LMA). Para `.text`, VMA = LMA.
- **KEEP** impede que `--gc-sections` descarte a tabela de vetores (ninguém a "chama").
- Os símbolos (`_sdata`, `_ebss`…) não ocupam memória: são endereços que o startup usa com `&`.

**5. Lendo o `size`.** `arm-none-eabi-size firmware.elf`:
```
   text    data     bss     dec     hex filename
  12480     136    2344   14960    3a70 firmware.elf
```
- **Flash** usada = text + data = 12 480 + 136 = **12 616 bytes** (o `text` do `size` já inclui vetores e `.rodata`; o `data` entra porque a cópia inicial fica na flash).
- **SRAM estática** = data + bss = 136 + 2344 = **2480 bytes**. O resto (20 480 − 2480 = 18 000 bytes) fica para pilha e heap — e o `size` não mostra quanto a pilha vai usar.

**6. A tabela de vetores em C.**
```c
void Default_Handler(void) { for (;;) {} }        // trava num lugar fácil de achar no depurador
void NMI_Handler(void)       __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
void SysTick_Handler(void)   __attribute__((weak, alias("Default_Handler")));
void TIM2_IRQHandler(void)   __attribute__((weak, alias("Default_Handler")));

__attribute__((section(".isr_vector"), used))
void (*const vetor[])(void) = {
    (void (*)(void))&_estack,   // 0x00  MSP inicial
    Reset_Handler,              // 0x04  exceção 1
    NMI_Handler,                // 0x08  exceção 2
    HardFault_Handler,          // 0x0C  exceção 3
    [15] = SysTick_Handler,     // 0x3C  exceção 15
    [16 + 28] = TIM2_IRQHandler // 0xB0  IRQ 28
};
```
- **`section(".isr_vector")`** põe o vetor na seção que o linker script coloca no início da flash; **`used`** evita que o compilador o descarte.
- **`weak` + `alias`**: todo tratador começa como apelido fraco do `Default_Handler`. Se você escrever `void TIM2_IRQHandler(void) { … }` em qualquer arquivo, essa definição forte vence e o linker usa a sua. Se errar o nome (`TIM2_IRQhandler`), nada avisa: a interrupção cai no `Default_Handler` e o programa "trava".
- **Conteúdo** de cada entrada: o endereço da função com o bit 0 em 1, que o compilador e o linker põem automaticamente para funções Thumb.
- **Deslocamento** da exceção *n*: 4 × n (T06). O tamanho da tabela é 4 × (16 + número de IRQs do chip).

## Pratique
Se não tiver `arm-none-eabi-gcc`, faça os exercícios 1–3 no papel e o 4 com `avr-gcc`.
1. Crie um projeto com `startup.c`, `main.c` e `link.ld` como os deste roteiro, compile com `arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostdlib -T link.ld` e confira com `arm-none-eabi-objdump -h` a VMA e a LMA de `.data`.
2. Rode `arm-none-eabi-objdump -s -j .isr_vector firmware.elf` e interprete as duas primeiras palavras (lembre-se do *little-endian*).
3. Gere o mapa com `-Wl,-Map=firmware.map` e encontre onde ficou cada variável global.
4. Compile para o ATmega328P um programa com `int x = 5;` e `int buf[10];` e procure `__do_copy_data` e `__do_clear_bss` no `avr-objdump -d`.
5. A partir de `text = 30 120`, `data = 412`, `bss = 6 980`, calcule a flash e a SRAM usadas num STM32F103C8 (64 KB de flash e 20 KB de SRAM) e quanto sobra para a pilha.
6. Escreva o nome errado de um tratador de propósito, dispare a interrupção e encontre no depurador onde o programa parou.
7. Um bootloader ocupa os primeiros 16 KB da flash. Que valores a aplicação deve usar em `ORIGIN` da flash e em `SCB->VTOR`?

## Armadilhas comuns
- Esquecer `KEEP` na tabela de vetores e ver o linker removê-la com `--gc-sections`: o chip não dá boot.
- Pôr o `.data` só em `> RAM`, sem `AT> FLASH`: os valores iniciais não vão para a flash e as variáveis começam com lixo.
- Assumir que variáveis globais começam zeradas num startup escrito à mão que esqueceu o laço do `.bss`.
- Errar o nome de um tratador: o `weak` esconde o erro e a interrupção cai no `Default_Handler`.
- Somar só o `text` para saber se cabe na flash, esquecendo o `data`.
- Achar que a SRAM livre informada pelo `size` é a pilha disponível de verdade: falta descontar o heap e o pior caso das chamadas e interrupções.
- Mudar a origem da aplicação para depois do bootloader e esquecer de ajustar o `VTOR`: as interrupções saltam para a tabela do bootloader.
