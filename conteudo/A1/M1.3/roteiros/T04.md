# M1.3.T04 — Memórias: Flash, SRAM, EEPROM, registradores de periférico

> Um MCU tem pelo menos quatro tipos de "memória", cada um com regras próprias: a flash guarda o programa e sobrevive sem energia, mas só se apaga em blocos e cansa; a SRAM é rápida e esquece tudo; a EEPROM guarda configurações byte a byte, devagar; e os registradores de periférico parecem memória, mas cada leitura ou escrita **faz algo** no hardware. Escolher errado gasta flash, corrompe dados de calibração ou trava o firmware.

## Ao final você consegue

- Comparar flash, SRAM, EEPROM e registradores quanto a volatilidade, velocidade, durabilidade, granularidade de escrita e apagamento e uso típico (.text, .data, .bss, pilha).
- Calcular capacidades de memória, larguras de endereço e faixas de endereços em hexadecimal.
- Acessar registradores de periférico mapeados em memória em C (ponteiro volatile, struct de registradores, deslocamentos) e explicar os efeitos colaterais de leitura e escrita.

## Resumo
**1. Von Neumann, Harvard e Harvard modificada.**
- **Von Neumann**: uma única memória (e um único barramento) para instruções e dados. Simples; mas busca e acesso a dados disputam o mesmo caminho (hazard estrutural, T03).
- **Harvard**: memórias e barramentos separados, com **espaços de endereçamento separados**. O endereço 0x0100 da flash e o 0x0100 da SRAM são coisas diferentes.
- **Harvard modificada**: barramentos separados por dentro, mas **um só mapa de endereços** visto pelo programa. É o Cortex-M: os barramentos I-Code e D-Code buscam instruções e dados em paralelo, mas um ponteiro C alcança tanto a flash (0x0800_0000) quanto a SRAM (0x2000_0000).

**No AVR (Harvard)**, o C não "vê" a flash com ponteiros comuns: `ld`/`st` acessam o espaço de dados; para ler a flash é preciso a instrução `lpm` (*load program memory*). Consequência prática:
```c
const char msg[] = "Forja M&H: maquina acordada!!!";          // vai para .data: ocupa flash E SRAM
const char msg2[] PROGMEM = "Forja M&H: maquina acordada!!!"; // fica só na flash
char c = pgm_read_byte(&msg2[i]);                              // gera lpm
```
Medido com `avr-size` (ATmega328P, `-Os`): sem PROGMEM, *data* = 32 bytes (a cópia da string na SRAM, que o startup copia da flash no reset); com PROGMEM, *data* = 0. Num chip com 2 KB de SRAM, textos de menu sem PROGMEM esgotam a memória rapidamente. **No Cortex-M**, `const` já basta: o vetor fica em `.rodata`, na flash, e é lido direto.

**2. Os tipos de memória.**

| | Flash | SRAM | EEPROM | Registrador de periférico |
|---|---|---|---|---|
| Sem energia | mantém | perde | mantém | volta ao valor de reset |
| Leitura | rápida (com wait states acima de certo clock) | 1 ciclo | lenta-moderada | 1 a poucos ciclos |
| Escrita | só 1 → 0; para voltar a 1, **apaga** a página/setor inteiro | byte a byte, ilimitada | byte a byte (apaga e grava o byte), ~3,3 ms por byte no ATmega328P | ilimitada, com efeitos |
| Durabilidade | ~10 000 ciclos de apagamento (ATmega328P, STM32F103) | ilimitada | ~100 000 ciclos (ATmega328P) | ilimitada |
| Uso | código (.text), constantes (.rodata), valores iniciais de .data | .data, .bss, heap, pilha | calibração, configuração, contadores | controlar o hardware |

- A flash apagada lê **0xFF** (todos os bits em 1); gravar só pode baixar bits. Por isso reescrever um byte exige apagar a página toda (1 KB no STM32F103 de média densidade, 2 KB nos de alta densidade).
- A maioria dos STM32 não tem EEPROM: a ST oferece **emulação em flash** (AN2594), alternando páginas e espalhando o desgaste.
- **Nivelamento de desgaste** (*wear leveling*): em vez de gravar sempre no mesmo endereço, avance por uma área maior; cada célula é gravada menos vezes.

**Exemplo 1 (vida útil).** Um contador gravado a cada 10 minutos sempre no mesmo byte da EEPROM (100 000 ciclos) dura 100 000 × 10 min = 10⁶ min ≈ **694 dias** — menos de 2 anos. Espalhando por 64 posições em rodízio, cada byte é gravado 64 vezes menos: ≈ 122 anos.

**3. Contas de endereço.**
- Com *n* bits de endereço, alcançam-se 2ⁿ posições. 64 KiB = 2¹⁶ → 16 bits; 512 KiB = 2¹⁹ → 19 bits.
- Último endereço = início + tamanho − 1. SRAM de 20 KB a partir de 0x2000_0000: 20 × 1024 = 20 480 = 0x5000 → última posição **0x2000_4FFF**.
- AVR: 32 KB de flash organizados em palavras de 16 bits = 16 384 palavras = 2¹⁴ → PC de 14 bits.
- Página de flash de um endereço: (endereço − início) ÷ tamanho da página. Com páginas de 1 KB, 0x0800_4C00 → 0x4C00 ÷ 0x400 = **página 19**.

**Exemplo 2 (mapa de dados do ATmega328P).** O espaço de dados (endereços de byte) é dividido em:

| Faixa | Conteúdo |
|---|---|
| 0x0000–0x001F | os 32 registradores R0–R31 |
| 0x0020–0x005F | 64 registradores de E/S (acessíveis também por `in`/`out` como 0x00–0x3F) |
| 0x0060–0x00FF | 160 registradores de E/S estendidos (só com `ld`/`st`/`lds`/`sts`) |
| 0x0100–0x08FF | 2048 bytes de SRAM |

PORTB fica no endereço de dados 0x25 = endereço de E/S 0x05 (0x25 − 0x20).

**4. Registradores de periférico mapeados em memória.** Cada periférico ocupa uma faixa de endereços; cada registrador fica num **deslocamento** a partir da base. Em C:
```c
#include <stdint.h>
#define GPIOC_ODR (*(volatile uint32_t *)0x4001100Cu)   // um registrador

typedef struct {                 // STM32F103, RM0008: GPIO
    volatile uint32_t CRL;       // 0x00
    volatile uint32_t CRH;       // 0x04
    volatile uint32_t IDR;       // 0x08
    volatile uint32_t ODR;       // 0x0C
    volatile uint32_t BSRR;      // 0x10
    volatile uint32_t BRR;       // 0x14
    volatile uint32_t LCKR;      // 0x18
} GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)0x40010800u)
#define GPIOC ((GPIO_TypeDef *)0x40011000u)

GPIOC->BSRR = 1u << 13;          // liga PC13, sem ler nada
```
- **`volatile`** é obrigatório: sem ele, o compilador pode eliminar leituras repetidas (`while (!(USART1->SR & RXNE))` vira laço infinito) ou juntar escritas.
- **Efeitos colaterais**: um registrador não é uma variável.
  - *Leitura que limpa*: no USART do STM32F1, ler o SR e depois o DR limpa flags de erro; ler o DR consome o byte recebido. Inspecionar esses registradores no depurador pode "roubar" dados.
  - *Escrita de 1 para limpar* (*write-1-to-clear*): em registradores de pendência, como o `EXTI_PR`, escrever 1 limpa o bit e escrever 0 não faz nada. Um `|=` ali limpa **todas** as pendências ligadas.
  - *Só escrita*: o `BSRR` lê como 0. Os bits 0–15 ligam pinos e os bits 16–31 desligam, numa escrita só — atômico, sem leitura-modificação-escrita.
  - *Bits reservados*: mantenha o valor de reset; não escreva lixo neles.

**Exemplo 3 (BSRR).** Ligar PC13 e desligar PC14 numa única escrita: `GPIOC->BSRR = (1u << 13) | (1u << (14 + 16));` = 0x0000_2000 | 0x4000_0000 = **0x4000_2000**.

## Pratique
1. Compile, com `avr-gcc -mmcu=atmega328p -Os`, um programa que envia uma string pela UART com e sem PROGMEM. Compare `avr-size` e procure `lpm` no `avr-objdump -d`.
2. Quantos bits de endereço são necessários para 128 KiB? E para 20 KiB (arredonde para cima)?
3. Uma flash de 64 KB começa em 0x0800_0000. Qual o último endereço? Em que página (de 1 KB) está 0x0800_A3F0?
4. Escreva a struct `GPIO_TypeDef` e confira com `offsetof` (no PC) que o BSRR está no deslocamento 0x10.
5. Calcule o valor de BSRR para ligar PA0 e PA1 e desligar PA5 numa escrita.
6. Um registro de 8 bytes é gravado a cada minuto numa área de 2 KB de flash com 10 000 ciclos, apagando a área quando enche. Quanto tempo até o desgaste?
7. Leia no RM0008 a descrição do `USART_SR` e anote quais bits são limpos por sequência de leitura.
8. Por que uma variável global `int contador;` não ocupa flash, mas `int contador = 5;` ocupa flash e SRAM?

## Armadilhas comuns
- Declarar tabelas e textos grandes no AVR sem PROGMEM e esgotar os 2 KB de SRAM.
- Ler uma variável PROGMEM com ponteiro comum no AVR: o código compila e lê lixo da SRAM no mesmo endereço.
- Gravar na flash sem apagar e esperar que os bits voltem a 1.
- Gravar configurações na EEPROM a cada mudança mínima (ou num laço) e gastar a durabilidade em dias.
- Esquecer o `volatile` em ponteiros para registradores.
- Usar `|=` num registrador de "escrever 1 para limpar" e limpar flags que outra parte do código ainda ia tratar.
- Confundir endereço de E/S (0x05) com endereço de dados (0x25) no AVR.
- Contar o último endereço como início + tamanho (sem o − 1).
