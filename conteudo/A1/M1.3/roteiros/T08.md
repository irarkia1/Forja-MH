# M1.3.T08 — Assembly básico

> Você não vai escrever firmware em assembly. Vai **ler** assembly: para entender um HardFault, conferir se o compilador fez o que você pediu com `volatile`, medir quantos ciclos tem uma rotina de interrupção ou descobrir por que o código não cabe na flash. No M0.6 você viu `objdump` e `gcc -S` no PC; aqui o alvo é o Cortex-M (Thumb-2), com o AVR ao lado para comparação.

## Ao final você consegue
- Ler a listagem de objdump -d (endereço, bytes de máquina, mnemônico e operandos) e relacioná-la ao código C compilado com -O0 e -O2.
- Seguir instruções Thumb-2 de movimentação, aritmética, lógica, load/store e desvio (mov, add, sub, and, orr, lsl, ldr, str, cmp, b, bl, bx) prevendo os registradores e as flags.
- Aplicar a convenção de chamada AAPCS (argumentos em r0–r3, retorno em r0, registradores preservados, push e pop de lr) para ler prólogos e epílogos de funções.
- Reconhecer em assembly ARM e AVR os padrões de laço, if/else, acesso a vetor e escrita de leitura-modificação-escrita em registrador de periférico.

## Resumo
**1. Como ler uma linha do objdump.** `arm-none-eabi-objdump -d firmware.elf` mostra:
```
080001ac <soma>:
 80001ac:	4408      	add	r0, r1
 80001ae:	4770      	bx	lr
```
- `80001ac`: endereço na flash; `<soma>`: o símbolo que começa ali.
- `4408`: o código de máquina. No Thumb, o objdump mostra meias-palavras de 16 bits (uma para instruções de 16 bits, duas para as de 32 bits, como `f043 0320`). Na memória, *little-endian*, os bytes ficam `08 44`.
- `add r0, r1`: mnemônico e operandos. Destino primeiro: r0 = r0 + r1.
- Use `-S` para intercalar o código C (precisa de `-g`) e `-C` para nomes de C++.

**2. -O0 × -O2.** A mesma função `int soma(int a, int b) { return a + b; }`:
```
-O0 (saída típica do arm-none-eabi-gcc)        -O2
 push   {r7}                                    add  r0, r1
 sub    sp, #12                                 bx   lr
 add    r7, sp, #0
 str    r0, [r7, #4]      @ a vai para a pilha
 str    r1, [r7, #0]      @ b vai para a pilha
 ldr    r2, [r7, #4]
 ldr    r3, [r7, #0]
 add    r3, r2
 mov    r0, r3
 adds   r7, #12
 mov    sp, r7
 ldr.w  r7, [sp], #4
 bx     lr
```
Em `-O0`, cada variável ganha um endereço na pilha e é lida e escrita a cada uso — ótimo para o depurador, péssimo para desempenho. Em `-O2`, tudo fica em registradores. A saída exata varia com a versão do compilador; o padrão, não.

**3. As instruções que você mais vai ver (Thumb-2).**

| Grupo | Exemplos | Efeito |
|---|---|---|
| Movimentação | `movs r0, #5`, `mov r3, r0`, `movw`/`movt` | copia constante ou registrador; `movw`+`movt` montam 32 bits |
| Aritmética | `adds r0, r1, r2`, `subs r0, #1`, `mul`, `sdiv`/`udiv` | o `s` no fim (`adds`) atualiza as flags |
| Lógica e bits | `ands`, `orrs`, `eors`, `bics` (AND NOT), `lsls`, `lsrs`, `asrs` | máscaras do M0.6 em hardware |
| Load/store | `ldr`, `ldrb`, `ldrh`, `str`, `strb`, `strh`, `push`, `pop` | `ldrb` lê 1 byte; `push {r4, lr}` empilha |
| Comparação | `cmp r0, r1`, `tst r0, #4` | `cmp` = `subs` sem guardar; `tst` = `ands` sem guardar |
| Desvio | `b`, `beq`/`bne`, `bgt`/`blt` (com sinal), `bhi`/`blo` (sem sinal), `bl`, `bx lr`, `cbz` | `bl` salva o retorno no LR; `bx lr` retorna |

Condições: `eq` (Z = 1), `ne` (Z = 0), `hs`/`cs` (C = 1, ≥ sem sinal), `lo`/`cc` (C = 0, < sem sinal), `hi` (> sem sinal), `ge`, `lt`, `gt`, `le` (com sinal, usam N e V). O compilador escolhe entre `bhi` e `bgt` pelo **tipo** da variável: `unsigned` gera as condições sem sinal.

**Exemplo 1 (traço com laço).**
```asm
    movs r0, #0
    movs r1, #5
laco:
    adds r0, r0, r1
    subs r1, r1, #1
    bne  laco
```
r0 acumula 5 + 4 + 3 + 2 + 1 = **15**. O `subs` põe Z = 1 quando r1 chega a 0, e o `bne` deixa de desviar. Contar para baixo até zero economiza um `cmp` — o compilador faz isso sempre que pode.

**4. A convenção de chamada (AAPCS).** É o acordo que permite que funções compiladas separadamente (o seu código, a HAL, a libc) se chamem.
- **Argumentos**: os quatro primeiros em **r0, r1, r2, r3**; os demais vão na pilha.
- **Retorno**: em **r0** (64 bits: r0 e r1).
- **r0–r3 e r12** podem ser destruídos pela função chamada (*caller-saved*). **r4–r11** precisam ser devolvidos intactos (*callee-saved*): se a função os usa, salva com `push` no começo e restaura com `pop` no fim.
- **LR**: o `bl` grava nele o endereço de retorno. Uma função que chama outra (não-folha) precisa salvar o LR antes, senão perde o caminho de volta. Padrão: `push {r4, lr}` … `pop {r4, pc}` — o `pop` direto no PC já é o retorno.
- **SP** alinhado a 8 bytes nas chamadas públicas (por isso o gcc às vezes empilha um registrador "a mais").

**5. Padrões que se repetem.**

*Vetor e laço* (`int32_t soma_array(const int32_t *v, int n)`, `-O2`):
```
080001b0 <soma_array>:
 80001b0:	2900      	cmp	r1, #0
 80001b2:	dd09      	ble.n	80001c8 <soma_array+0x18>   @ n <= 0: retorna 0
 80001b4:	4603      	mov	r3, r0                       @ r3 = ponteiro
 80001b6:	eb00 0181 	add.w	r1, r0, r1, lsl #2           @ r1 = fim = v + n*4
 80001ba:	2000      	movs	r0, #0                       @ s = 0
 80001bc:	f853 2b04 	ldr.w	r2, [r3], #4                 @ r2 = *p; p++
 80001c0:	428b      	cmp	r3, r1
 80001c2:	4410      	add	r0, r2                       @ s += r2
 80001c4:	d1fa      	bne.n	80001bc <soma_array+0xc>
 80001c6:	4770      	bx	lr
 80001c8:	2000      	movs	r0, #0
 80001ca:	4770      	bx	lr
```
O `lsl #2` (× 4) denuncia elementos de 4 bytes; o pós-incremento `[r3], #4` percorre o vetor. O compilador transformou o índice `i` num ponteiro que anda até o fim.

**Exemplo 2 (decodificando um desvio).** `d1fa` em 0x80001C4 é `bne` com deslocamento de 8 bits 0xFA = −6, multiplicado por 2 (instruções têm 2 bytes): −12. A base é o PC = endereço + 4 = 0x80001C8. Destino: 0x80001C8 − 12 = **0x80001BC**, o início do laço.

*Registrador de periférico* (`GPIOA->ODR |= 1u << 5;`, leitura-modificação-escrita):
```
 80001cc:	4a02      	ldr	r2, [pc, #8]     @ r2 = 0x40020014 (literal pool)
 80001ce:	6813      	ldr	r3, [r2, #0]     @ lê
 80001d0:	f043 0320 	orr.w	r3, r3, #32      @ modifica
 80001d4:	6013      	str	r3, [r2, #0]     @ escreve
 80001d6:	4770      	bx	lr
 80001d8:	40020014 	.word	0x40020014
```
Três instruções separadas: uma interrupção entre o `ldr` e o `str` que mexa no mesmo registrador terá a alteração perdida. É por isso que o STM32 tem o `BSRR` (T04).

*If/else no AVR* (`uint8_t maior(uint8_t a, uint8_t b)`, `avr-gcc -Os`, saída real):
```
0000009a <maior>:
  9a:	86 17       	cp	r24, r22        ; compara a (r24) com b (r22)
  9c:	08 f4       	brcc	.+2      	; a >= b: pula o mov e retorna a
  9e:	86 2f       	mov	r24, r22        ; senão, resultado = b
  a0:	08 95       	ret
```
No avr-gcc, o 1º argumento de 8 bits chega em r24, o 2º em r22, e o retorno sai em r24. r1 é sempre zero e r0 é temporário.

*Somar 32 bits no AVR* — `add r22, r18` / `adc r23, r19` / `adc r24, r20` / `adc r25, r21`: quatro instruções encadeando o carry (T01).

*Registrador de E/S no AVR*: `PORTB |= 1 << PB5;` vira **uma** instrução, `sbi 0x05, 5`, atômica. Com dois bits (`PORTB |= 0x30;`), vira `in r24, 0x05` / `ori r24, 0x30` / `out 0x05, r24` — de novo leitura-modificação-escrita.

## Pratique
Se não tiver `arm-none-eabi-gcc`, use o Compiler Explorer (godbolt.org). Para o AVR, o `avr-gcc` dos pacotes da distribuição basta.
1. Compile `soma` com `-O0` e com `-O2` (`arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c`) e desmonte com `arm-none-eabi-objdump -d`. Conte as instruções de cada versão.
2. Siga o Exemplo 1 trocando `movs r1, #5` por `movs r1, #8`. Qual o valor final de r0?
3. Em `soma_array`, por que o compilador comparou `r3` com `r1` em vez de comparar `i` com `n`?
4. Decodifique o desvio `dd09` em 0x80001B2 (condição `le`, deslocamento de 8 bits) e confira o destino com a listagem.
5. Escreva uma função C com 6 parâmetros `int` que retorna a soma deles. Desmonte e localize onde os parâmetros 5 e 6 são lidos.
6. Escreva uma função que chama outra e confira que ela começa com `push {..., lr}` e termina com `pop {..., pc}`.
7. Compile no AVR `uint32_t soma32(uint32_t a, uint32_t b)` e confira os registradores dos argumentos e do retorno.
8. Compile `PORTB |= (1 << 5);` e `PORTB |= 0x30;` com `avr-gcc -Os` e explique por que uma vira `sbi` e a outra não.
9. Troque `int` por `unsigned` numa comparação `if (a > b)` em ARM e veja `bgt` virar `bhi`.

## Armadilhas comuns
- Ler os operandos na ordem errada: no ARM e no AVR o destino vem **primeiro** (`add r0, r1` é r0 = r0 + r1).
- Esquecer o `s`: `add` não altera as flags; `adds` altera. Um `bne` depois de `add` testa flags antigas.
- Calcular o destino de um desvio Thumb a partir do endereço da instrução: a base é o endereço + 4.
- Achar que `-O0` mostra "o código de verdade": o firmware de produção roda com `-O2`/`-Os`, que pode eliminar variáveis, reordenar e juntar código.
- Achar que o compilador "sumiu" com uma leitura de registrador: sem `volatile`, ele pode mesmo (M0.6.T03).
- Usar r4–r11 numa rotina em assembly sem salvá-los: o código C que chamou perde valores sem aviso.
- Confundir `bgt` (com sinal) com `bhi` (sem sinal) ao ler uma comparação.
