# M1.12.T04 — Dashboard e alertas

> Tópico de **elite** (projeto). Tempo previsto: ~25 h — ≈ 4 h de estudo (Telegraf `mqtt_consumer` e `json_v2`, modelo de dados e tarefas do InfluxDB, painéis e *alerting* do Grafana), ≈ 3 h de projeto (perguntas do painel, regras, procedimento de resposta), ≈ 14 h de laboratório (pilha em Docker Compose, contagem de sequência, dashboard, regras, ensaios de latência, estação muda), ≈ 4 h de verificação e relatório. Quarta etapa: as mensagens viram **histórico, painel e notificação**. A cadeia é Mosquitto → Telegraf → InfluxDB → Grafana → celular, e cada elo acrescenta tempo e um jeito de perder dados. A etapa tem duas provas: **nenhuma medida se perde** (contada pelo número de sequência, RNF-05) e **o alerta chega em menos de 60 s** (medido, RNF-03). A pilha inteira deste roteiro foi executada em Docker (Mosquitto 2.0.20, Telegraf 1.32, InfluxDB 2.7, Grafana 11.3) com a estação simulada do T03: as regras e o painel foram provisionados por arquivo, a consulta de entrega e a tarefa de downsampling rodaram no InfluxDB, e a latência do alerta foi medida de ponta a ponta com um receptor de webhook. Dois problemas apareceram nos ensaios e estão no texto, porque são os que você também vai encontrar.

## Ao final você consegue
- Montar o caminho dos dados do broker ao banco de séries temporais (Telegraf, InfluxDB, retenção e downsampling) em Docker Compose e provar pela contagem dos números de sequência que nenhuma medida se perde.
- Construir no Grafana um dashboard de operação (séries, valor atual, bateria, RSSI, idade do último dado) e justificar cada painel pela pergunta que ele responde.
- Projetar regras de alerta (limiar com histerese, período pendente, estação muda, bateria baixa, tratamento de ausência de dados) com pontos de contato, políticas de notificação e anotações com o procedimento de resposta.
- Medir a latência fim a fim do alerta somando as etapas do dispositivo à notificação, comparar com o critério de aceite e ajustar os intervalos que dominam o tempo.

**2. Do broker ao banco: o Telegraf.** Três decisões estão neste arquivo:
- **O carimbo é o da medida**: cada item de `m` vira um ponto com `timestamp_key = "t"`. Um lote que chega 30 min depois (ou 4 h, depois de uma queda) cai no lugar certo do gráfico.
- **Sessão persistente com QoS 1**: se o Telegraf reiniciar, o broker guarda o que chegou nesse intervalo e entrega quando ele voltar. Sem isso, cada reinício do coletor é uma lacuna.
- **Saída rápida para os alertas**: o `flush_interval` padrão de 10 s é aceitável para as medidas, mas soma até 10 s ao alerta. Uma segunda saída só para a medição `alerta`, com `flush_interval = "1s"`, tira esse tempo do caminho crítico.
```toml
# telegraf.conf — MQTT → InfluxDB. Lotes com o carimbo de cada medida; alertas com saída rápida.
[agent]
  interval = "10s"
  flush_interval = "10s"
  omit_hostname = true

# Saída geral: medidas e saúde, gravadas a cada 10 s
[[outputs.influxdb_v2]]
  urls = ["http://influxdb:8086"]
  token = "${INFLUX_TOKEN}"
  organization = "forja"
  bucket = "estacoes"
  namedrop = ["alerta"]

# Saída só dos alertas, gravada a cada 1 s: o alerta não espera o flush de 10 s
[[outputs.influxdb_v2]]
  urls = ["http://influxdb:8086"]
  token = "${INFLUX_TOKEN}"
  organization = "forja"
  bucket = "estacoes"
  namepass = ["alerta"]
  flush_interval = "1s"

[[inputs.mqtt_consumer]]
  servers = ["tcp://mosquitto:1883"]     # porta interna da rede do Docker
  topics = ["forja/estacao/+/lote"]
  qos = 1
  client_id = "telegraf-lote"
  persistent_session = true              # com QoS 1: o broker guarda o que chegar com o Telegraf fora
  username = "telegraf"
  password = "${MQTT_TELEGRAF_SENHA}"
  topic_tag = ""
  data_format = "json_v2"
  [[inputs.mqtt_consumer.topic_parsing]]
    topic = "forja/estacao/+/lote"
    tags = "_/_/estacao/_"
  # Cada item de "m" vira um ponto com o carimbo da medida
  [[inputs.mqtt_consumer.json_v2]]
    measurement_name = "ambiente"
    [[inputs.mqtt_consumer.json_v2.object]]
      path = "m"
      timestamp_key = "t"
      timestamp_format = "unix"
      [inputs.mqtt_consumer.json_v2.object.fields]
        T = "float"
        U = "float"
        s = "int"
  # Saúde da estação, com o carimbo da chegada
  [[inputs.mqtt_consumer.json_v2]]
    measurement_name = "saude"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "vbat"
      type = "int"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "rssi"
      type = "int"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "perd"
      type = "int"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "boot"
      type = "int"

[[inputs.mqtt_consumer]]
  servers = ["tcp://mosquitto:1883"]
  topics = ["forja/estacao/+/alerta"]
  qos = 1
  client_id = "telegraf-alerta"
  persistent_session = true
  username = "telegraf"
  password = "${MQTT_TELEGRAF_SENHA}"
  topic_tag = ""
  data_format = "json_v2"
  [[inputs.mqtt_consumer.topic_parsing]]
    topic = "forja/estacao/+/alerta"
    tags = "_/_/estacao/_"
  [[inputs.mqtt_consumer.json_v2]]
    measurement_name = "alerta"
    timestamp_path = "t"
    timestamp_format = "unix"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "T"
      type = "float"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "ativo"
      type = "int"
```
**Modelo de dados.** No InfluxDB, um ponto é **medição + tags + carimbo**; os campos são os valores. `estacao` é tag (vem do tópico, pelo `topic_parsing`); `T`, `U` e `s` são campos. Escrever de novo o mesmo ponto **sobrescreve** — é o que torna as duplicatas do QoS 1 inofensivas (T03). O mesmo mecanismo morde quem mede mais rápido que a resolução do carimbo: com a estação simulada medindo a cada 0,2 s e carimbo em segundos, 13 medidas viraram **3 pontos** no banco, e a consulta de entrega abaixo mostrou 33 %. Na estação real (300 s entre medidas) o segundo basta; num sensor rápido, carimbe em milissegundos.

**Retenção e downsampling.** O bucket `estacoes` guarda o dado bruto por 400 dias. Para os anos seguintes, uma tarefa do InfluxDB grava médias horárias em `estacoes_1h` (retenção de 5 anos). O detalhe que só este projeto tem: o **`offset` de 35 min**. O lote chega até 30 min depois da medida; uma tarefa que fechasse a hora no minuto 0 gravaria médias incompletas. O `offset` atrasa a execução sem mudar a janela. (Um reenvio depois de horas sem rede ainda escapa: reprocesse a janela, se precisar.)
```
// media_1h.flux — downsampling: médias horárias em outro bucket, guardadas por 5 anos.
// offset de 35 min: o lote chega até 30 min depois da medida; sem isso, a hora fecharia incompleta.
option task = {name: "media_1h", every: 1h, offset: 35m}

from(bucket: "estacoes")
    |> range(start: -task.every)
    |> filter(fn: (r) => r._measurement == "ambiente" and (r._field == "T" or r._field == "U"))
    |> aggregateWindow(every: 1h, fn: mean, createEmpty: false)
    |> to(bucket: "estacoes_1h", org: "forja")
```
Ordem de grandeza do armazenamento: por estação e por dia, 288 medidas × 3 campos + 48 lotes × 4 campos de saúde = 1056 valores; em 400 dias, ~420 mil valores — nada para o InfluxDB.

**3. Provar que nada se perde (RNF-05).** A estação numera cada medida; o banco conta quantos números distintos existem entre o menor e o maior do período. Esta consulta foi executada no InfluxDB 2.7 (com uma estação simulada de 18 medidas, deu 100 %; com a que colidia carimbos, 33 %):
```
from(bucket: "estacoes")
  |> range(start: -7d)
  |> filter(fn: (r) => r._measurement == "ambiente" and r._field == "s")
  |> group(columns: ["estacao"])
  |> reduce(identity: {n: 0, mn: 2147483647, mx: -1},
            fn: (r, accumulator) => ({n: accumulator.n + 1,
              mn: if r._value < accumulator.mn then r._value else accumulator.mn,
              mx: if r._value > accumulator.mx then r._value else accumulator.mx}))
  |> map(fn: (r) => ({estacao: r.estacao, n: r.n, mn: r.mn, mx: r.mx,
                      _value: 100.0 * float(v: r.n) / float(v: r.mx - r.mn + 1)}))
```
A conta vale **dentro de um boot** (um power-on zera a sequência; separe pelos carimbos ou pelo campo `boot` da saúde). Lacunas que batem com o `perd` da estação são perdas **explicadas** (buffer cheio); as outras são perdas **silenciosas** — ACL do MQTT 3.1.1, Telegraf fora sem sessão persistente, erro de parser — e são as que o ensaio de 7 dias precisa caçar.

**4. O dashboard: um painel por pergunta.** Um painel que não responde a uma pergunta de quem opera é decoração. O painel de referência (provisionado por arquivo JSON, gerado por script, no repositório):

| Painel | Tipo | Pergunta que responde |
|---|---|---|
| Temperatura (linha do limiar em vermelho) | série temporal | está dentro da faixa? quando saiu? |
| Idade do último lote (verde até 35 min, vermelho acima de 65) | valor | a estação está viva? |
| Bateria (vermelho abaixo de 3,45 V) | valor | quanto falta para trocar? |
| Umidade relativa | série temporal | há risco de condensação? |
| RSSI | série temporal | o enlace piorou (mais tempo de rádio, mais consumo)? |
| Tensão da bateria em 30 dias | série temporal | a descarga segue a projeção do T05? |
| Entrega no período (verde ≥ 99 %) | valor | o RNF-05 está sendo cumprido? |

A "idade do último lote" é o painel mais útil e o mais esquecido: um gráfico de temperatura "bonito" pode estar parado há dois dias. Consulta:
```
from(bucket: "estacoes")
  |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
  |> filter(fn: (r) => r._measurement == "saude" and r._field == "vbat")
  |> group(columns: ["estacao"])
  |> last()
  |> map(fn: (r) => ({r with _value: float(v: uint(v: now()) - uint(v: r._time)) / 60000000000.0}))
  |> keep(columns: ["_time", "_value", "estacao"])
```

**5. Regras de alerta.** Princípios, antes do arquivo:
- **Alerte sintomas que exigem ação**, com um procedimento escrito (o `runbook_url` da anotação aponta para `docs/procedimentos.md`). Um alerta que ninguém sabe o que fazer com ele vira ruído, e o ruído ensina a ignorar todos.
- **Histerese no dispositivo, período pendente no servidor**: a estação já só publica ao cruzar o limiar e só "normaliza" 0,5 °C abaixo; por isso a regra de temperatura tem `for: 0s`. Um **período pendente** (`for`) filtra picos, mas **soma** ao tempo do alerta — na variante C (câmara fria), um `for` de 10 min é o que impede a porta aberta de virar alarme, e o requisito de latência tem de ser escrito sabendo disso.
- **Ausência de dados é decidida por regra**: "sem alerta nas últimas 24 h" é `OK`; "sem lote há 65 min" é **alerta** (estação muda); "sem tensão de bateria" não é assunto da regra de bateria. A regra "estação muda" usa a **idade** do último dado, com o rótulo da estação; um simples "sem dados" (*No Data*) perderia o rótulo e não diria **qual** estação calou.
- **Bateria baixa com período pendente** de 1 h: um pulso de rádio derruba a tensão por milissegundos; a troca de bateria não é urgente.
- **Rótulos para rotear** (`severidade`) e **anotações para explicar** (`summary`, `runbook_url`).


**Ponto de contato.** No projeto, **Telegram** (um bot criado pelo BotFather; o token e o *chat id* vão no `.env`, nunca no arquivo versionado) ou **e-mail** (exige o `[smtp]` do Grafana configurado — o primeiro teste deste roteiro falhou com "*SMTP not configured*" no ponto de contato padrão). Para medir, um **webhook** para um receptor de 10 linhas que anota a hora de chegada:
```python
# receptor.py — recebe o webhook do Grafana e registra a hora de chegada (para medir a latência).
# Uso: python3 receptor.py 18000 >> chegadas.csv
import http.server, json, sys, time

class R(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        corpo = json.loads(self.rfile.read(int(self.headers['Content-Length'])))
        for a in corpo.get('alerts', []):
            print(f"{time.time():.3f},{a['status']},{a['labels'].get('alertname')},{a['labels'].get('estacao')}", flush=True)
        self.send_response(200); self.end_headers()
    def log_message(self, *a):
        pass

http.server.HTTPServer(('0.0.0.0', int(sys.argv[1])), R).serve_forever()
```

**Problema 1 encontrado: "input data must be a wide series but got type long".** Na primeira subida, as três regras ficaram em *Error*: a consulta Flux devolvia, além de `_time`, `_value` e `estacao`, as colunas `_start`, `_stop`, `_field` e `_measurement`, e o Grafana tratou o resultado como série "longa". O `|> keep(columns: ["_time", "_value", "estacao"])` no fim de cada consulta resolveu. Confira a saúde das regras depois de cada mudança (Alerting → Alert rules, ou a API `/api/prometheus/grafana/api/v1/rules`), não só a aparência do painel.

**6. A latência do alerta, medida.** O orçamento do T01 previa ~57 s no pior caso, com o *group wait* de 30 s como maior parcela. Os ensaios usaram a estação simulada (que publica o alerta na hora em que mede acima de 30 °C e registra esse instante) e o receptor de webhook; a latência é a diferença entre os dois relógios, na mesma máquina. A estação real acrescenta o tempo de rádio do T03 (1–3 s).

Resultados (Telegraf com saída de 1 s para os alertas, regra avaliada a cada 10 s, `for: 0s`; latência do PUBLISH do alerta à chegada do webhook; ensaios de ~2 min, cada um com 60 s acima do limiar):

**Problema 2 encontrado: o alerta que nunca chegou.** Com a política padrão, **dois de três** episódios de temperatura alta não geraram notificação — só o "resolvido" final. Não é falha do Grafana: é o agrupamento funcionando como foi configurado. A política de notificação agrupa por regra e estação; depois da primeira notificação, o grupo só manda novidades a cada *group interval* (5 min por padrão). Um episódio curto que começa e termina nessa janela some. Para alertas críticos: *group wait* curto (5 s), *group interval* curto (10 s a 1 min), e ensaios **espaçados** e **repetidos** — os dois casos.

Decomposição do pior caso medido com a política ajustada (20,3 s): até ~1 s do flush do Telegraf + até 10 s da avaliação da regra + até 10 s do *group interval* (ou 5 s de *group wait*) + entrega local (ms). Somando o rádio da estação real (até 3 s, T03) e a entrega de um Telegram (1–2 s), o pior caso fica por volta de 25 s: o RNF-03 (60 s) passa com folga, e o maior termo restante é o intervalo de avaliação da regra.

**7. A alternativa sem banco no caminho.** Mesmo com tudo ajustado, o alerta passa por Telegraf, banco, avaliação periódica e agrupamento. Um **assinante MQTT dedicado** (um script em Python com paho-mqtt, ou um fluxo no Node-RED) que assina `forja/estacao/+/alerta` e chama a API do Telegram notifica em ~1 s depois do PUBLISH — à custa de mais um serviço para manter e de duplicar a lógica de roteamento. É o ADR-006 do T01: decida com os números medidos aqui. Plataformas como o ThingsBoard (M1.10.T07) juntam banco, painel e regras num só serviço, com outros compromissos.

## Pratique
1. Por que o Telegraf usa o campo `t` de cada medida como carimbo, e não a hora de chegada da mensagem?
2. O que acontece com as medidas publicadas enquanto o Telegraf está reiniciando, com e sem `persistent_session`?
3. A estação simulada mediu 13 vezes em 2,6 s e o banco guardou 3 pontos. Por quê? Isso acontece com a estação real?
4. Uma tarefa de downsampling horária roda no minuto 0 de cada hora. Por que ela grava médias erradas neste projeto, e como o `offset` resolve?
5. Por que a regra "estação muda" usa a idade do último dado, e não o estado *No Data*?
6. Some o pior caso do caminho do alerta com: rádio 3 s, flush do Telegraf de 1 s, avaliação a cada 10 s, período pendente 0, *group wait* 5 s, entrega 2 s. Atende a 60 s?
7. Nos ensaios, um segundo alerta da mesma estação, poucos minutos depois do primeiro, nunca foi notificado. Explique pelo *group interval*.
8. Na câmara fria (variante C), por que o período pendente de 10 min é desejável, e o que ele obriga a mudar no requisito de latência?
9. Que painel você olharia primeiro para saber se a estação parou de mandar dados, e por que o gráfico de temperatura não serve para isso?

## Armadilhas comuns
- Carimbar as medidas com a hora de chegada: lotes e reenvios aparecem todos "agora".
- Telegraf sem sessão persistente (ou com QoS 0): cada reinício é uma lacuna invisível.
- Carimbo em segundos para medidas mais rápidas que 1 Hz: pontos sobrescritos.
- Downsampling sem `offset` com dados que chegam atrasados.
- Painel bonito sem a idade do último dado: a estação morta parece viva.
- Regra em *Error* sem ninguém ver (consulta Flux com colunas a mais).
- Alerta por "No Data" que não diz qual estação calou.
- Período pendente e *group wait* nos valores padrão, sem somar ao requisito de latência.
- Medir a latência com ensaios seguidos da mesma estação, que caem no grupo já existente e não mostram o *group wait* (ou, ao contrário, nunca notificam).
- Alertas sem procedimento; e-mail como ponto de contato sem SMTP configurado.
- Token do banco ou do bot no arquivo versionado.

## Gabarito
1. Porque o lote reúne medidas de até 30 min (ou horas, num reenvio): com a hora de chegada, todas cairiam no mesmo instante e o gráfico perderia o que aconteceu entre elas.
2. Com `persistent_session = true` e QoS 1, o broker guarda as mensagens da assinatura do Telegraf e as entrega quando ele reconecta: nada se perde. Sem sessão persistente, o broker esquece a assinatura quando o Telegraf cai, e o que chega nesse intervalo é descartado para ele.
3. O carimbo é em segundos e várias medidas caíram no mesmo segundo: mesma medição, mesmas tags e mesmo carimbo = mesmo ponto, sobrescrito. Na estação real, as medidas estão a 300 s umas das outras: não acontece.
4. No minuto 0, os lotes com medidas da última meia hora ainda não chegaram (chegam até 30 min depois): a média da hora sai com metade dos dados. O `offset` de 35 min atrasa a execução mantendo a janela, e a tarefa roda quando os dados já estão no banco.
5. Quando a consulta não devolve nada, o Grafana não tem o rótulo `estacao` e o alerta *No Data* não diz qual estação calou. Calculando a idade do último dado de cada estação, a série existe por estação e o alerta sai com o nome dela.
6. 3 + 1 + 10 + 0 + 5 + 2 = **21 s**: atende com folga.
7. Depois da primeira notificação, o grupo (mesma regra, mesma estação) continua existindo, e novas mudanças só são enviadas a cada *group interval* (5 min no padrão). Se o segundo alerta começa e termina dentro dessa janela, quando chega a vez de notificar o estado já é "resolvido", e só o "resolvido" é enviado.
8. Abrir a porta faz a temperatura subir alguns minutos sem risco ao produto; o período pendente só dispara se a condição durar 10 min. O requisito de latência passa a ser contado a partir de 10 min acima do limiar, e isso tem de estar escrito no RNF.
9. A **idade do último lote**: ela cresce quando a estação para. O gráfico de temperatura só mostra os pontos que existem; uma linha parada há dois dias pode passar despercebida.
