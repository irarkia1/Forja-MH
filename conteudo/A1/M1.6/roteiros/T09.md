## Resumo
**1. Partições de OTA.** A OTA exige (*OTA Process Overview*) pelo menos **dois slots de aplicação** (`ota_0` e `ota_1`) e uma partição **`otadata`** (tipo `data`, subtipo `ota`, de **0x2000 bytes**: dois setores, gravados alternadamente com um contador, para que uma queda de energia no meio da escrita nunca deixe a escolha corrompida). A `factory` é opcional:
- **Com `factory`** (tabela pronta *Factory app, two OTA definitions*): a versão de fábrica fica sempre disponível e nunca é sobrescrita pela OTA; custa uma partição a mais.
- **Sem `factory`**: o primeiro firmware vai na `ota_0`; sobra mais espaço para os dois slots. É o que este roteiro usa:
```csv
# Nome,   Tipo, Subtipo, Offset, Tamanho, Flags
nvs,      data, nvs,     ,       0x4000,
otadata,  data, ota,     ,       0x2000,
phy_init, data, phy,     ,       0x1000,
ota_0,    app,  ota_0,   ,       1920K,
ota_1,    app,  ota_1,   ,       1920K,
```
Numa flash de 4 MB: `nvs` em 0x9000, `otadata` em 0xD000, `phy_init` em 0xF000, `ota_0` em **0x10000**, `ota_1` em **0x1F0000** (0x10000 + 1920 × 1024 = 0x10000 + 0x1E0000), terminando em 0x3D0000; sobram 192 KB (para um `coredump`, por exemplo).

**2. O ciclo de atualização.**
1. A aplicação em execução (digamos, na `ota_0`) descobre que há versão nova.
2. Abre a **partição livre** (a que não está rodando: `esp_ota_get_next_update_partition`), apaga e grava a imagem nova em blocos, à medida que ela chega pela rede (`esp_ota_begin`, `esp_ota_write`).
3. No fim (`esp_ota_end`), a imagem é **verificada** (formato, checksum, SHA-256 e, se configurado, assinatura).
4. `esp_ota_set_boot_partition` grava na `otadata` que o próximo boot é na `ota_1`.
5. `esp_restart()`. O bootloader lê a `otadata` e carrega a `ota_1`.
Durante todo o download, a versão antiga continua intacta e em execução: uma queda de rede ou de energia antes do passo 4 só desperdiça o download.

**3. HTTPS OTA.** O componente `esp_https_ota` faz os passos 2 a 4 sobre um `esp_http_client`. Na forma mais simples, `esp_https_ota(&cfg)` faz tudo de uma vez. A **API avançada** (`esp_https_ota_begin`, `esp_https_ota_get_img_desc`, `esp_https_ota_perform`, `esp_https_ota_finish`) permite olhar o cabeçalho da imagem **antes** de baixar o resto — para comparar a versão, por exemplo. Exemplo resolvido (baseado em `advanced_https_ota` e `native_ota_example`), executado no QEMU:
```c
#include <string.h>
#include <inttypes.h>
#include "esp_check.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"
#include "esp_system.h"
#include "esp_ota_ops.h"
#include "esp_app_desc.h"
#include "esp_https_ota.h"
#include "esp_http_client.h"
#include "nvs_flash.h"
#include "esp_netif.h"
#include "esp_event.h"
#include "protocol_examples_common.h"   /* example_connect(): Wi-Fi ou Ethernet, pelo menuconfig */

static const char *TAG = "ota";
extern const char cert_pem_ini[] asm("_binary_ca_cert_pem_start");   /* EMBED_TXTFILES */

#define URL_FIRMWARE "https://10.0.2.2:8070/forja.bin"   /* 10.0.2.2 = o PC visto de dentro do QEMU */

static bool autoteste(void)
{
    /* No produto: conectou na rede? falou com o servidor? sensores respondem? */
    return true;
}

static void confirmar_ou_reverter(void)
{
    const esp_partition_t *rodando = esp_ota_get_running_partition();
    esp_ota_img_states_t estado;
    if (esp_ota_get_state_partition(rodando, &estado) == ESP_OK &&
        estado == ESP_OTA_IMG_PENDING_VERIFY) {           /* primeiro boot de uma imagem nova */
        if (autoteste()) {
            ESP_LOGI(TAG, "autoteste ok: imagem confirmada");
            esp_ota_mark_app_valid_cancel_rollback();
        } else {
            ESP_LOGE(TAG, "autoteste falhou: voltando à versão anterior");
            esp_ota_mark_app_invalid_rollback_and_reboot();   /* não retorna */
        }
    }
}

static esp_err_t atualizar(void)
{
    esp_http_client_config_t http = {
        .url = URL_FIRMWARE,
        .cert_pem = cert_pem_ini,                         /* só aceita este servidor */
        .timeout_ms = 10000,
        .keep_alive_enable = true,
    };
    esp_https_ota_config_t cfg = { .http_config = &http };
    esp_https_ota_handle_t h = NULL;
    ESP_RETURN_ON_ERROR(esp_https_ota_begin(&cfg, &h), TAG, "não abriu a conexão");

    esp_app_desc_t nova;                                  /* cabeçalho da imagem remota */
    esp_err_t err = esp_https_ota_get_img_desc(h, &nova);
    const esp_app_desc_t *atual = esp_app_get_description();
    if (err == ESP_OK && strcmp(nova.version, atual->version) == 0) {
        ESP_LOGI(TAG, "servidor tem a mesma versão (%s): nada a fazer", nova.version);
        esp_https_ota_abort(h);
        return ESP_OK;
    }
    const esp_partition_t *ruim = esp_ota_get_last_invalid_partition();
    esp_app_desc_t desc_ruim;
    if (err == ESP_OK && ruim != NULL &&
        esp_ota_get_partition_description(ruim, &desc_ruim) == ESP_OK &&
        strcmp(desc_ruim.version, nova.version) == 0) {   /* já falhou aqui: não insiste */
        ESP_LOGW(TAG, "versão %s já foi rejeitada pelo rollback; ignorando", nova.version);
        esp_https_ota_abort(h);
        return ESP_OK;
    }
    ESP_LOGI(TAG, "atualizando %s -> %s", atual->version, nova.version);

    while ((err = esp_https_ota_perform(h)) == ESP_ERR_HTTPS_OTA_IN_PROGRESS) {
        /* uma rodada por bloco; dá para mostrar o progresso */
    }
    if (err != ESP_OK || !esp_https_ota_is_complete_data_received(h)) {
        ESP_LOGE(TAG, "download falhou: %s", esp_err_to_name(err));
        esp_https_ota_abort(h);
        return err;
    }
    err = esp_https_ota_finish(h);                        /* valida a imagem e troca a otadata */
    if (err == ESP_OK) {
        ESP_LOGI(TAG, "pronto; reiniciando na nova versão");
        vTaskDelay(pdMS_TO_TICKS(500));
        esp_restart();
    }
    return err;
}

void app_main(void)
{
    const esp_partition_t *p = esp_ota_get_running_partition();
    ESP_LOGI(TAG, "versão %s rodando em %s (0x%06" PRIx32 ")",
             esp_app_get_description()->version, p->label, p->address);
    confirmar_ou_reverter();

    esp_err_t err = nvs_flash_init();
    if (err == ESP_ERR_NVS_NO_FREE_PAGES || err == ESP_ERR_NVS_NEW_VERSION_FOUND) {
        ESP_ERROR_CHECK(nvs_flash_erase());
        err = nvs_flash_init();
    }
    ESP_ERROR_CHECK(err);
    ESP_ERROR_CHECK(esp_netif_init());
    ESP_ERROR_CHECK(esp_event_loop_create_default());
    ESP_ERROR_CHECK(example_connect());

    if (atualizar() != ESP_OK)
        ESP_LOGW(TAG, "OTA não concluída; tento de novo mais tarde");
}
```

**A versão.** O texto de `esp_app_get_description()->version` vem, em ordem de prioridade, da variável `PROJECT_VER` no `CMakeLists.txt`, de um arquivo `version.txt` na raiz do projeto ou do `git describe` (*App Image Format*). Aqui, `version.txt` com `1.0.0`, depois `2.0.0`. Comparar versões por igualdade de texto basta para o laboratório; num produto, compare números (1.10.0 > 1.9.0) e prefira o servidor dizendo qual versão cada aparelho deve ter.

**O certificado.** `cert_pem` contém o certificado (da CA ou autoassinado) do servidor, embutido no firmware com `EMBED_TXTFILES`. O cliente TLS só aceita um servidor que prove ter a chave correspondente: sem isso, qualquer um na rede poderia servir um firmware malicioso. Para servidores públicos, use o *certificate bundle* do ESP-IDF (`crt_bundle_attach = esp_crt_bundle_attach`). Nunca ponha `skip_cert_common_name_check` ou desligue a verificação num produto.

O subtipo 17 (0x11) é a `ota_1`. As linhas `esp_image` são a verificação da imagem gravada antes da troca. Depois do reinício, a 2.0.0 nasce em **pending verify**, passa no autoteste e é confirmada; na consulta seguinte, a versão igual é recusada sem baixar o resto.

**4. Rollback.** Com `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` (*App Rollback*), a imagem nova tem **uma única chance**:
- Gravada pela OTA, ela fica no estado **`ESP_OTA_IMG_NEW`**; no primeiro boot, o bootloader a marca como **`ESP_OTA_IMG_PENDING_VERIFY`**.
- A aplicação faz um **autoteste** e chama `esp_ota_mark_app_valid_cancel_rollback()` (estado `VALID`) ou `esp_ota_mark_app_invalid_rollback_and_reboot()` (estado `INVALID`, reinício na anterior).
- Se a imagem nova **travar, entrar em pânico ou perder energia** antes de se confirmar, o bootloader, no boot seguinte, encontra-a ainda em `PENDING_VERIFY`, marca-a como `INVALID`/`ABORTED` e volta à anterior (*Unexpected Reset*).
- Só partições OTA sofrem rollback; a `factory` não.
O que o autoteste verifica é decisão de projeto: no mínimo, que a nova versão **consegue fazer a próxima OTA** (conecta na rede e fala com o servidor). Uma versão que sobe mas não consegue mais se atualizar é o pior caso: o aparelho fica preso nela. Faça o autoteste **rápido**, para não confundir uma queda de energia comum com uma versão defeituosa.

**5. Segurança e robustez.** A OTA é a porta pela qual um atacante entra em todos os seus aparelhos de uma vez. Camadas, da mais básica à mais forte:
- **TLS com verificação do servidor** (obrigatório): garante que o firmware veio do seu servidor e não foi alterado no caminho. Não protege contra quem invadiu o servidor.
- **Assinatura da imagem**: o firmware é assinado no seu computador de build (chave privada que nunca vai para o servidor) e o aparelho confere com a chave pública. Com **Secure Boot v2**, o bootloader verifica a assinatura a cada boot, com a chave gravada em eFuse; sem ligar o Secure Boot, dá para verificar só as atualizações (`CONFIG_SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT`; *Secure OTA Updates Without Secure Boot*).
- **Anti-rollback** (`CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK`): cada imagem tem um `secure_version`; o chip guarda em eFuse o maior já aceito e recusa imagens com versão de segurança menor. Impede que o atacante reinstale uma versão antiga, com falha conhecida. Os eFuses são poucos bits, gravados de forma irreversível: aumente o `secure_version` só quando corrigir uma falha de segurança.
- **Criptografia da flash** (*Flash Encryption*): impede ler o firmware (e as credenciais da NVS, com *NVS Encryption*) de um aparelho capturado. A OTA continua funcionando: o chip cifra ao gravar.
- **Robustez**: a versão antiga só é substituída depois da imagem nova estar completa e verificada; a `otadata` tem dois setores; o rollback cobre a versão que não sobe. O que resta: o aparelho precisa ter **espaço** e **energia** para a atualização — não comece uma OTA com bateria fraca — e o servidor precisa liberar versões aos poucos (*rollout* gradual).
Secure Boot e criptografia da flash queimam eFuses **irreversivelmente**; teste-os em placas descartáveis e no modo de desenvolvimento, nunca na sua única placa. O tema volta no Ato 4 (segurança e regulamentação).

**6. Dimensionar as partições.** O binário cresce a cada versão. A imagem deste exemplo (Ethernet, HTTPS, OTA) tem **557 KB** (0x8B310 bytes); o projeto com Wi-Fi, servidor HTTP e provisionamento do T04, **~733 KB**; com BLE (T05) somado ao Wi-Fi, passa facilmente de 1 MB. Regras:
- Os dois slots têm o mesmo tamanho (qualquer versão pode cair em qualquer um).
- Deixe **folga generosa**: a tabela de partições **não pode ser mudada pela OTA** (a OTA grava aplicações, não a tabela nem o bootloader). Se o firmware não couber mais no slot, só uma regravação pela serial resolve.
- Os slots precisam começar em múltiplos de 64 KB: dois slots iguais numa flash de 4 MB, depois dos 64 KB iniciais, têm no máximo **1984 KB** cada (0x1F0000), e não 2016 KB, porque o segundo slot também precisa estar alinhado.
- Prefira módulos com 8 MB ou mais de flash se o produto vai ter Wi-Fi e BLE e uma vida longa.

**Exemplo numérico (crescimento).** Firmware de 733 KB num slot de 1920 KB, crescendo 15% por ano: cabe por n anos enquanto 733 × 1,15ⁿ ≤ 1920, ou seja, n ≤ ln(1920/733)/ln(1,15) ≈ **6,9 anos**.

**Exemplo numérico (tempo de download).** A 50 KB/s efetivos (Wi-Fi fraco, TLS, gravação na flash), os 557 KB levam ~11 s; num aparelho que acorda do deep sleep (T06), isso é uma fração relevante da bateria: atualize com bateria cheia ou quando o servidor mandar.

### Passo a passo
**Experimento 1 — O servidor e o certificado (≈ 2 h).**
1. Gere um certificado autoassinado para o endereço do servidor (no QEMU, 10.0.2.2; com placa, o IP do seu PC na rede local):
```sh
mkdir -p server_certs srv
openssl req -x509 -newkey rsa:2048 -nodes -keyout srv/key.pem -out server_certs/ca_cert.pem \
        -days 3650 -subj "/CN=10.0.2.2" -addext "subjectAltName=IP:10.0.2.2"
cp server_certs/ca_cert.pem srv/cert.pem
```
2. Escreva o servidor HTTPS mínimo (fora da pasta servida, para não publicar o próprio script):
```python
# servidor_ota.py — uso: python3 servidor_ota.py pasta_com_forja_bin_cert_e_chave
import http.server, ssl, sys, os
os.chdir(sys.argv[1])
srv = http.server.HTTPServer(("0.0.0.0", 8070), http.server.SimpleHTTPRequestHandler)
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain("cert.pem", "key.pem")
srv.socket = ctx.wrap_socket(srv.socket, server_side=True)
srv.serve_forever()
```
3. Teste com `curl -k https://127.0.0.1:8070/forja.bin -o /dev/null -w "%{size_download}\n"` (o `-k` só no teste do PC).

**Experimento 2 — A primeira atualização (≈ 4 h).**
1. Monte o projeto da seção 3 com a tabela da seção 1. Compile com `version.txt` = `2.0.0` e copie `build/forja.bin` para `srv/`. Recompile com `1.0.0`.
2. Rode (`idf.py qemu monitor`, ou `idf.py flash monitor` na placa) e acompanhe: partição em execução, download, verificação, reinício, `pending verify`, confirmação. Copie o log.
3. Leia a `otadata` antes e depois (na placa: `otatool.py --port /dev/ttyUSB0 read_otadata`; ou `parttool.py read_partition --partition-name=otadata`). O que mudou?
4. Meça o tempo total da OTA e a vazão (tamanho / tempo do download).

**Experimento 3 — Rollback (≈ 3 h).**
1. Crie uma versão 3.0.0 cujo autoteste falhe (para o teste, `return false;` no `autoteste`). Ponha-a no servidor e atualize a partir da 1.0.0. Confira a volta automática.
2. Remova a verificação de `esp_ota_get_last_invalid_partition()` e observe o laço de downloads. Ponha-a de volta.
3. Crie uma 3.0.1 que entra em **pânico** logo no início do `app_main` (antes do autoteste), por exemplo com um ponteiro nulo (T08). O rollback acontece? Qual motivo de reset aparece em cada boot?
4. Desligue `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` e repita o item 3. O que acontece com o aparelho?

**Experimento 4 — Falhas de rede e de servidor (≈ 3 h).**
1. Derrube o servidor no meio do download (Ctrl+C). O que o firmware registra? A versão antiga continua rodando? Ele tenta de novo depois?
2. Sirva um arquivo que não é firmware (renomeie um `.txt` para `forja.bin`). Em que etapa a OTA recusa?
3. Troque o certificado do servidor por outro (gere um novo par) sem atualizar o firmware. O que acontece no handshake TLS?
4. Sirva o firmware de **outro projeto** (de outro chip, por exemplo um build para ESP32-C3 num ESP32). Ele é recusado? Por quê?
5. (Placa) Desligue a energia no meio do download e no meio do primeiro boot da versão nova. Registre o que acontece no boot seguinte.

**Experimento 5 — Dimensionamento e segurança, no papel (≈ 3 h).**
1. Para o seu produto imaginário (Wi-Fi + BLE + OTA, 4 MB e 8 MB de flash), proponha a tabela de partições com `nvs`, `otadata`, `phy_init`, dois slots, `coredump` e um LittleFS. Justifique os tamanhos com o crescimento esperado.
2. Escreva o plano de segurança da OTA do produto: o que será feito agora (TLS, verificação de versão, rollback) e o que exige eFuses (Secure Boot v2, anti-rollback, criptografia da flash), com os riscos de cada um. Não queime eFuses neste laboratório.

### Evidência
Registre no jogo:
1. **Logs** completos: atualização 1.0.0 → 2.0.0, rollback da 3.0.0, laço sem a verificação de versão rejeitada (e a correção), pânico da 3.0.1.
2. **Tabela de falhas** do Experimento 4: situação, mensagem de erro, etapa em que a OTA parou, versão que ficou rodando.
3. **Medidas**: tempo de OTA, vazão, tamanho da imagem e folga do slot.
4. **Tabela de partições** proposta no Experimento 5, com as contas de offsets e alinhamentos, e o plano de segurança (meia página).
5. **Código** (link) com o certificado embutido, a comparação de versões e o autoteste.
6. **Descrição** (5–10 frases): o que o seu autoteste verifica e por quê; o que acontece se a energia cair em cada etapa; o que foi feito no QEMU e o que exigiu placa.

## Pratique
1. Por que a `otadata` tem dois setores?
2. A aplicação está na `ota_1`. Em que partição a próxima OTA vai gravar?
3. Em que momento exato a versão antiga deixa de ser a escolhida pelo bootloader?
4. Uma versão nova entra em pânico antes de chamar `esp_ota_mark_app_valid_cancel_rollback`. Com rollback habilitado, o que acontece? E sem?
5. Por que o autoteste deve incluir "conseguir falar com o servidor de OTA"?
6. Qual é o maior tamanho de dois slots iguais numa flash de 8 MB, com a tabela padrão (primeiro slot em 0x10000) e nada depois deles?
7. Um firmware de 900 KB cresce 20% ao ano num slot de 1,5 MB (1536 KB). Por quantos anos ele cabe?
8. O que o anti-rollback protege que o rollback de aplicação não protege?
9. Por que a OTA não pode mudar a tabela de partições?

## Armadilhas comuns
- Tabela sem `otadata` ou com um só slot de OTA.
- Slots pequenos demais "porque o firmware de hoje cabe".
- Desligar a verificação do certificado para "fazer funcionar" e esquecer assim.
- Esquecer o `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` ou o `esp_ota_mark_app_valid_cancel_rollback` (com rollback ligado, a versão nova é revertida no reinício seguinte).
- Autoteste lento ou que não testa a capacidade de atualizar.
- Baixar de novo, para sempre, a versão que o rollback rejeitou.
- Comparar versões como texto ("1.10.0" < "1.9.0").
- Começar a OTA com bateria fraca.
- Queimar eFuses de Secure Boot ou de criptografia na única placa, sem entender o modo de desenvolvimento.
- Achar que a OTA atualiza o bootloader e a tabela de partições.

## Gabarito
1. Para que uma queda de energia durante a gravação nunca destrua a escolha: os setores são gravados alternadamente, e um contador indica o mais recente válido.
2. Na `ota_0` (a próxima partição de atualização, a que não está rodando).
3. Quando a `otadata` é gravada apontando para a imagem nova, já verificada: dentro de `esp_https_ota_finish` (na API de baixo nível, em `esp_ota_set_boot_partition`, depois de `esp_ota_end`). Antes disso, qualquer falha mantém a versão antiga.
4. Com rollback: o bootloader, no boot seguinte, encontra a imagem ainda em `PENDING_VERIFY`, marca-a como inválida e volta à anterior. Sem rollback: a imagem nova continua sendo escolhida e o aparelho fica em laço de pânico e reinício.
5. Porque uma versão que funciona mas não consegue mais se atualizar deixa o aparelho preso nela, sem conserto remoto.
6. De 0x10000 a 0x800000 há 0x7F0000; metade é 0x3F8000, que arredondada para múltiplo de 64 KB fica 0x3F0000 = 4032 KB por slot.
7. 900 × 1,2ⁿ ≤ 1536 → n ≤ ln(1,7067)/ln(1,2) ≈ 2,9 anos.
8. Impede a instalação deliberada de uma versão antiga (com falha conhecida), mesmo assinada; o rollback de aplicação só volta à versão anterior quando a nova falha.
9. Porque a tabela e o bootloader ficam fora dos slots que a OTA grava; trocá-los com o aparelho rodando arriscaria deixá-lo sem boot. Só a regravação pela serial muda a tabela.
