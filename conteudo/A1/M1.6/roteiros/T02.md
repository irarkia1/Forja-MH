# M1.6.T02 — ESP-IDF, menuconfig, componentes

> No M1.2.T09 você montou a cadeia do AVR na mão: avr-gcc, Makefile, avrdude. O **ESP-IDF** (*Espressif IoT Development Framework*) é a mesma ideia em escala industrial: um sistema de build em CMake com centenas de componentes (Wi-Fi, TCP/IP, TLS, NVS, FreeRTOS), um sistema de configuração herdado do kernel Linux (Kconfig e menuconfig) e uma ferramenta, o `idf.py`, que orquestra tudo, do `cmake` ao `esptool`. Este tópico ensina a criar, organizar e configurar um projeto, e mostra o que acontece entre o reset e o seu `app_main`. O FreeRTOS entra só o necessário para trabalhar: tarefas, filas e o watchdog. O RTOS a fundo é o M1.7. Todo o código do módulo é para o ESP-IDF **v5.x** (testado com a v5.3).

## Ao final você consegue
- Usar o idf.py para criar, configurar, compilar, gravar e monitorar um projeto (set-target, menuconfig, build, flash, monitor, size) e explicar a estrutura de pastas de um projeto ESP-IDF.
- Organizar o firmware em componentes com CMakeLists.txt (idf_component_register, SRCS, INCLUDE_DIRS, REQUIRES e PRIV_REQUIRES) e usar o gerenciador de componentes (idf_component.yml).
- Criar opções próprias com Kconfig e explicar o papel do sdkconfig, do sdkconfig.defaults e do sdkconfig.h gerado, decidindo o que vai para o controle de versão.
- Explicar a sequência de boot até o app_main e usar o mínimo de FreeRTOS do ESP-IDF: app_main como tarefa, xTaskCreate com pilha em bytes, vTaskDelay, filas e o watchdog de tarefas.

## Resumo
**1. Instalação e o idf.py.** O ESP-IDF é um repositório git (com submódulos) mais um conjunto de ferramentas: compilador cruzado, `esptool.py`, `idf.py`, CMake, Ninja, OpenOCD e um ambiente Python. No Linux:
```sh
git clone -b v5.3.2 --recursive https://github.com/espressif/esp-idf.git ~/esp/esp-idf
cd ~/esp/esp-idf && ./install.sh esp32,esp32c3     # baixa os compiladores dos alvos
. ~/esp/esp-idf/export.sh                          # em cada terminal novo
```
O ciclo de trabalho:

| Comando | O que faz |
|---|---|
| `idf.py create-project forja` | cria um projeto mínimo |
| `idf.py set-target esp32c3` | escolhe o chip (apaga o `build/` e recria o `sdkconfig` com os padrões do alvo) |
| `idf.py menuconfig` | abre o menu de configuração (texto) e grava o `sdkconfig` |
| `idf.py build` | CMake + Ninja: compila bootloader, tabela de partições e aplicação |
| `idf.py -p /dev/ttyUSB0 flash` | grava os três binários com o `esptool.py` |
| `idf.py -p /dev/ttyUSB0 monitor` | terminal serial com decodificação de endereços (T08) |
| `idf.py flash monitor` | os dois em sequência (o mais usado) |
| `idf.py size`, `size-components`, `size-files` | quanto cada memória e cada componente ocupa |
| `idf.py fullclean` | apaga o `build/` |
| `idf.py erase-flash` | apaga a flash inteira (inclusive NVS) |
| `idf.py save-defconfig` | grava em `sdkconfig.defaults` só o que difere do padrão |

O `idf.py` é uma camada sobre o CMake; o build de verdade acontece em `build/`. Ao fim do `build`, ele imprime o comando `esptool.py` completo, com os endereços de cada binário: no ESP32, `0x1000` (bootloader), `0x8000` (tabela de partições) e `0x10000` (aplicação). Nos S3, C3 e C6 o bootloader vai em `0x0`. O T03 explica esse mapa.

**2. Estrutura de um projeto.**
```
forja/
├── CMakeLists.txt          ← projeto (3 linhas)
├── sdkconfig               ← configuração completa, gerada
├── sdkconfig.defaults      ← o que você mudou em relação ao padrão
├── partitions.csv          ← opcional, tabela própria (T03)
├── main/                   ← o componente "main"
│   ├── CMakeLists.txt
│   ├── Kconfig.projbuild   ← opções do projeto no menuconfig
│   ├── idf_component.yml   ← dependências do registro (opcional)
│   └── main.c
├── components/             ← componentes próprios do projeto
│   └── pisca/
│       ├── CMakeLists.txt
│       ├── Kconfig
│       ├── include/pisca.h
│       └── pisca.c
├── managed_components/     ← baixados pelo gerenciador (não versionar)
└── build/                  ← saída (não versionar)
```
O `CMakeLists.txt` do projeto tem sempre o mesmo esqueleto:
```cmake
cmake_minimum_required(VERSION 3.16)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(forja)
```

**3. Componentes.** Um **componente** é uma pasta com um `CMakeLists.txt` que chama `idf_component_register`. Tudo no ESP-IDF é componente: `freertos`, `esp_wifi`, `nvs_flash`, `esp_driver_gpio`. O seu código também deve ser. O build procura componentes nos componentes do ESP-IDF, em `components/` do projeto, em `managed_components/` e em `EXTRA_COMPONENT_DIRS`.

```cmake
# components/pisca/CMakeLists.txt
idf_component_register(SRCS "pisca.c"
                       INCLUDE_DIRS "include"
                       PRIV_REQUIRES esp_driver_gpio)
```
- `SRCS`: os `.c` do componente.
- `INCLUDE_DIRS`: pastas de cabeçalhos **públicos** (visíveis a quem depende do componente). `PRIV_INCLUDE_DIRS`: só para uso interno.
- `REQUIRES`: componentes de que os seus **cabeçalhos públicos** precisam. Quem depende de você herda essas dependências.
- `PRIV_REQUIRES`: componentes usados só nos `.c`. Não vazam para quem depende de você. Regra: comece com `PRIV_REQUIRES` e só promova para `REQUIRES` se um `#include` do seu `include/` exigir.

Três detalhes que causam erros de build:
- Desde a v5.0, os drivers não fazem mais parte dos requisitos comuns: quem usa `driver/gpio.h` precisa declarar a dependência. Na v5.3, os drivers foram divididos em componentes (`esp_driver_gpio`, `esp_driver_ledc`, `esp_driver_uart`…); o antigo `driver` continua existindo como agregador de compatibilidade.
- O componente **main** é especial: se não declarar `REQUIRES` nem `PRIV_REQUIRES`, ele depende automaticamente de todos os componentes. Se declarar, vale a lista.
- O erro `fatal error: driver/gpio.h: No such file or directory` quase sempre é dependência faltando no `CMakeLists.txt`, não arquivo faltando.

```c
/* components/pisca/include/pisca.h */
#pragma once
#include <stdbool.h>
#include "esp_err.h"

esp_err_t pisca_iniciar(void);
void pisca_definir(bool aceso);
```
```c
/* components/pisca/pisca.c */
#include "pisca.h"
#include "driver/gpio.h"
#include "sdkconfig.h"

esp_err_t pisca_iniciar(void)
{
    gpio_config_t cfg = {
        .pin_bit_mask = 1ULL << CONFIG_PISCA_GPIO,
        .mode = GPIO_MODE_OUTPUT,
        .pull_up_en = GPIO_PULLUP_DISABLE,
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE,
    };
    return gpio_config(&cfg);
}

void pisca_definir(bool aceso)
{
    gpio_set_level(CONFIG_PISCA_GPIO, aceso);
}
```

**O gerenciador de componentes.** Componentes publicados em *components.espressif.com* entram com um manifesto:
```sh
idf.py add-dependency "espressif/led_strip^2.5.3"
```
O comando cria ou atualiza `main/idf_component.yml`:
```yaml
dependencies:
  espressif/led_strip: "^2.5.3"
  idf: ">=5.0"
```
No próximo build, o componente é baixado para `managed_components/` e as versões resolvidas ficam em `dependencies.lock`. **Versione** o `idf_component.yml` e o `dependencies.lock` (build reproduzível); **não versione** `managed_components/`. O `^2.5.3` aceita 2.x a partir de 2.5.3, mas não 3.0 (versionamento semântico).

**4. Kconfig, menuconfig e sdkconfig.** Cada componente pode ter um arquivo `Kconfig` com opções; o `Kconfig.projbuild` aparece no menu principal. Todas as opções juntas formam o menu do `idf.py menuconfig`.
```kconfig
# main/Kconfig.projbuild
menu "Forja: configuração do projeto"

    config FORJA_PERIODO_MS
        int "Período do pisca (ms)"
        range 50 5000
        default 500
        help
            Intervalo entre duas mudanças do LED.

    config FORJA_LOG_EVENTOS
        bool "Registrar cada evento no log"
        default y

endmenu
```
```kconfig
# components/pisca/Kconfig
menu "Pisca (componente)"

    config PISCA_GPIO
        int "GPIO do LED"
        range 0 48
        default 2

endmenu
```
- O resultado do menu é o **`sdkconfig`**, um arquivo texto com **todas** as opções (mais de mil linhas): `CONFIG_FORJA_PERIODO_MS=500`.
- Do `sdkconfig`, o build gera **`build/config/sdkconfig.h`**, que o seu C inclui: `#define CONFIG_FORJA_PERIODO_MS 500`. Uma opção `bool` desligada **não é definida** no cabeçalho; por isso o teste é `#if CONFIG_FORJA_LOG_EVENTOS` ou `#ifdef`.
- O **`sdkconfig.defaults`** guarda só o que você quer diferente do padrão. Quando o `sdkconfig` não existe (clone novo, `set-target`), o build parte do padrão de cada opção e aplica o `sdkconfig.defaults`. Há também `sdkconfig.defaults.esp32c3` etc., aplicados só para aquele alvo.
- **Controle de versão**: o `sdkconfig.defaults` é o que documenta as escolhas do projeto e precisa estar no git. O `sdkconfig` completo depende da versão do ESP-IDF e do alvo; muitas equipes também o versionam, para builds idênticos, mas aí ele precisa ser revisado a cada atualização do ESP-IDF. O que não pode acontecer é a configuração existir só no seu computador.

**5. Do reset ao app_main** (*Application Startup Flow*).
1. **Primeiro estágio (ROM)**: a CPU sai do reset e executa o código da ROM. Ele lê os strapping (T01): se for modo de download, espera o `esptool` pela UART ou USB; se não, lê o **bootloader de segundo estágio** da flash (offset `0x1000` no ESP32, `0x0` nos S3/C3/C6), copia-o para a SRAM e salta para ele.
2. **Segundo estágio (bootloader do ESP-IDF, código-fonte aberto)**: lê a **tabela de partições** (offset `0x8000`), escolhe qual aplicação executar (`factory` ou a OTA indicada pela `otadata`, T03 e T09), verifica a imagem, copia os segmentos de IRAM e DRAM para a SRAM e configura a MMU para mapear os segmentos de flash (IROM/DROM). Salta para o ponto de entrada da aplicação.
3. **Inicialização da aplicação**: o código de *startup* do ESP-IDF inicializa a memória (`.bss`, `.data`), o heap, os clocks, o console e os componentes, liga o segundo núcleo (se houver) e **inicia o escalonador do FreeRTOS**.
4. O escalonador executa a **tarefa main**, que chama o seu **`app_main()`**.

Diferença importante para o AVR: o `app_main` **não é o `main` do C** nem precisa de um laço infinito. Ele é uma **tarefa do FreeRTOS** (prioridade 1, pilha de 3584 bytes por padrão, `CONFIG_ESP_MAIN_TASK_STACK_SIZE`). Se `app_main` retornar, só a tarefa main é apagada; as outras tarefas, o Wi-Fi e os timers continuam.

**6. O FreeRTOS mínimo.** O ESP-IDF já roda o FreeRTOS (uma versão SMP, para dois núcleos). Para usar o ESP-IDF você precisa de quatro coisas:
- **Tarefa**: uma função `void f(void *arg)` com laço infinito, criada com `xTaskCreate(f, "nome", pilha_em_bytes, arg, prioridade, &handle)`. **No ESP-IDF a pilha é em bytes**; no FreeRTOS original, em palavras. Número maior = prioridade maior. `xTaskCreatePinnedToCore` fixa a tarefa num núcleo.
- **Esperar**: `vTaskDelay(pdMS_TO_TICKS(500))` bloqueia a tarefa e libera a CPU. O tick padrão é de 100 Hz (`CONFIG_FREERTOS_HZ`): a resolução do `vTaskDelay` é de **10 ms** — `pdMS_TO_TICKS(5)` vira 0 ticks.
- **Fila**: `xQueueCreate(n, tamanho)`, `xQueueSend` e `xQueueReceive` passam dados entre tarefas (e de ISRs, com `xQueueSendFromISR`) com cópia e sem variável global compartilhada.
- **Watchdog de tarefas (TWDT)**: por padrão, vigia as tarefas *idle* dos núcleos com tempo limite de 5 s (`CONFIG_ESP_TASK_WDT_TIMEOUT_S`). Uma tarefa que nunca bloqueia (um `while (1)` sem `vTaskDelay`) impede a *idle* de rodar e dispara o aviso `Task watchdog got triggered` (T08). É o equivalente moderno do "não use delay bloqueante" do M1.2.T06.

**Exemplo resolvido (projeto completo de duas tarefas e uma fila).** Usa o componente `pisca` e as opções de Kconfig acima.
```c
/* main/main.c */
#include <stdbool.h>
#include <stdint.h>
#include <inttypes.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "freertos/queue.h"
#include "esp_log.h"
#include "sdkconfig.h"
#include "pisca.h"

static const char *TAG = "forja";
static QueueHandle_t fila;              /* produtor → consumidor */

static void tarefa_produtora(void *arg)
{
    uint32_t n = 0;
    for (;;) {
        n++;
        xQueueSend(fila, &n, portMAX_DELAY);           /* bloqueia se a fila encher */
        vTaskDelay(pdMS_TO_TICKS(CONFIG_FORJA_PERIODO_MS));
    }
}

static void tarefa_consumidora(void *arg)
{
    uint32_t n;
    for (;;) {
        if (xQueueReceive(fila, &n, portMAX_DELAY) == pdTRUE) {   /* dorme até chegar */
            pisca_definir(n & 1);
#if CONFIG_FORJA_LOG_EVENTOS
            ESP_LOGI(TAG, "evento %" PRIu32 ", LED %s", n, (n & 1) ? "aceso" : "apagado");
#endif
        }
    }
}

void app_main(void)                     /* já é uma tarefa do FreeRTOS */
{
    ESP_ERROR_CHECK(pisca_iniciar());
    fila = xQueueCreate(8, sizeof(uint32_t));
    configASSERT(fila != NULL);
    /* pilha em BYTES no ESP-IDF (no FreeRTOS original, em palavras) */
    xTaskCreate(tarefa_produtora, "produtora", 2048, NULL, 5, NULL);
    xTaskCreate(tarefa_consumidora, "consumidora", 3072, NULL, 4, NULL);
    ESP_LOGI(TAG, "app_main terminou; as outras tarefas continuam");
}   /* ao retornar, a tarefa main é apagada; o sistema segue rodando */
```
```cmake
# main/CMakeLists.txt
idf_component_register(SRCS "main.c"
                       INCLUDE_DIRS "."
                       PRIV_REQUIRES pisca)
```
```ini
# sdkconfig.defaults
CONFIG_FORJA_PERIODO_MS=250
CONFIG_PISCA_GPIO=2
```
Compilado com o ESP-IDF v5.3.2 para o ESP32: a imagem tem cerca de 185 KB e o build avisa que a menor partição de aplicação (1 MB) tem 82% livre. O `sdkconfig.h` gerado contém `#define CONFIG_FORJA_PERIODO_MS 250` (o valor do `sdkconfig.defaults` venceu o `default 500` do Kconfig).

Repare no `%" PRIu32 "`: nos compiladores do ESP-IDF v5, `uint32_t` é `unsigned long`, e um `%u` gera `error: format '%u' expects argument of type 'unsigned int'` (o build trata esse aviso como erro, `-Werror=format`; conferido com a v5.3.2). Acostume-se a compilar sem avisos e a usar as macros de `<inttypes.h>`.

**Exemplo numérico (tick).** Com `CONFIG_FREERTOS_HZ = 100`, `vTaskDelay(pdMS_TO_TICKS(25))` espera 2 ticks (a macro trunca: 25 × 100 / 1000 = 2,5 → 2), ou seja, **entre 10 e 20 ms**, dependendo de onde no tick a chamada aconteceu. Para atrasos curtos e precisos, use `esp_rom_delay_us` (espera ativa) ou um timer de hardware (`esp_timer`, `gptimer`).

**7. Onde está o tamanho.** `idf.py size` mostra o uso de cada memória (IRAM, DRAM, flash de código e de dados, RTC). Para o projeto acima, no ESP32: cerca de 84 KB de código em flash, 52 KB de IRAM (quase tudo do próprio ESP-IDF e do FreeRTOS) e 11 KB de DRAM estática. O `size-components` responde "quem está ocupando tanto?" — normalmente `mbedtls`, `lwip` e `esp_wifi` quando o Wi-Fi entra (T04).

## Armadilhas comuns
- Esquecer o `. export.sh` no terminal novo: `idf.py: command not found`.
- Trocar de alvo editando o `sdkconfig` na mão em vez de `idf.py set-target`.
- Dependência faltando no `CMakeLists.txt` e procurar o "arquivo que sumiu".
- Ajustar opções no menuconfig e não levá-las para o `sdkconfig.defaults`: o colega clona e compila outra coisa.
- Tratar a pilha do `xTaskCreate` como palavras (código copiado do FreeRTOS genérico): pilha quatro vezes menor que a planejada.
- `vTaskDelay` com atraso menor que um tick (vira 0 e não espera nada).
- Laço infinito sem bloquear: o watchdog de tarefas reclama e as tarefas de prioridade menor morrem de fome.
- Achar que `app_main` precisa terminar num `while (1)`.

## Gabarito
1. `build` só compila; `flash monitor` compila se preciso, grava e abre o terminal serial. O `set-target` troca compilador, padrões do `sdkconfig` e endereços: o build antigo não serve e é apagado.
2. `REQUIRES esp_driver_i2c` (o cabeçalho público expõe tipos do driver a quem incluir `sensor.h`). Se o include estiver só no `.c`, `PRIV_REQUIRES`.
3. `config FORJA_LIMIAR_C` / `int "Limiar (°C)"` / `range -40 125` / `default 30`.
4. No `sdkconfig`: `# CONFIG_FORJA_LOG_EVENTOS is not set`. No `sdkconfig.h`: nada (a macro não é definida), e `#if CONFIG_FORJA_LOG_EVENTOS` vale 0.
5. Versionar: `CMakeLists.txt`, `main/`, `components/`, `sdkconfig.defaults`, `partitions.csv`, `idf_component.yml`, `dependencies.lock` (e o `sdkconfig`, se a equipe decidir). Ignorar: `build/` e `managed_components/`.
6. 1024 bytes (não palavras): pouco para `printf` com float. Estouro de pilha e pânico (o T08 mostra a mensagem). Use 3 a 4 KB e meça com `uxTaskGetStackHighWaterMark`.
7. Nada: 5 × 100 / 1000 = 0,5 → 0 ticks; a tarefa só cede a CPU.
8. A tarefa main nunca bloqueia; a *idle* do núcleo não roda e o watchdog de tarefas avisa a cada 5 s. As tarefas de prioridade menor ou igual no mesmo núcleo deixam de rodar.
9. `0x1000` no ESP32; `0x0` no ESP32-C3.
