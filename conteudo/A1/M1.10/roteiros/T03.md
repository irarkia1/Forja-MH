# M1.10.T03 — CoAP

> O MQTT do T02 é ótimo quando o dispositivo pode manter uma conexão TCP aberta. Agora pense num medidor de água NB-IoT (M1.9.T06) que acorda uma vez por hora, manda 20 bytes e volta a dormir por PSM: abrir TCP, fazer o handshake TLS, conectar no broker e mandar um PUBLISH custa vários segundos de rádio e dezenas de pacotes. O **CoAP** (*Constrained Application Protocol*, RFC 7252) é a resposta da IETF para esse caso: o **mesmo modelo REST do HTTP** (T01) — recursos, URIs, GET/PUT/POST/DELETE, códigos de resposta — sobre **UDP**, com cabeçalho de **4 bytes**, confiabilidade opcional feita pelo próprio protocolo, **observação** de recursos (o servidor avisa quando o valor muda) e **transferência em blocos** para o que não cabe num datagrama. É a base do LwM2M, usado por operadoras para gerenciar dispositivos celulares. Você vai codificar uma mensagem à mão, ver CON e ACK passarem por um espião, medir as retransmissões e falar CoAP do ESP32 com a libcoap.

- Usar a observação de recursos da RFC 7641 e a transferência em blocos da RFC 7959 (Block1, Block2, SZX) e calcular o número de blocos e de mensagens de uma transferência.

## Resumo
**1. REST sobre UDP.** O CoAP copia do HTTP a camada de cima e troca a de baixo:
- **Recursos** em URIs `coap://host:5683/sensores/temp` (ou `coaps://host:5684/...`, com DTLS); métodos **GET** (0.01), **POST** (0.02), **PUT** (0.03), **DELETE** (0.04), com as mesmas propriedades de segurança e idempotência da RFC 9110 (a RFC 8132 acrescenta FETCH, PATCH e iPATCH).
- **Códigos de resposta** no formato `c.dd`, espelhando o HTTP: **2.01** Created, **2.02** Deleted, **2.03** Valid, **2.04** Changed, **2.05** Content; **4.00** Bad Request, **4.01** Unauthorized, **4.04** Not Found, **4.05** Method Not Allowed; **5.00** Internal Server Error, **5.03** Service Unavailable.
- **Content-Format** numérico no lugar do texto do `Content-Type`: 0 = `text/plain;charset=utf-8`, 40 = `application/link-format`, 42 = `application/octet-stream`, 50 = `application/json`, **60 = `application/cbor`** (T05).
- **Descoberta**: `GET /.well-known/core` devolve a lista de recursos no *CoRE Link Format* (`</sensores/temp>;obs,</config>`).
- **Proxies** CoAP↔HTTP são previstos: a semântica é a mesma, só a codificação muda.

Embaixo, em vez de TCP, **UDP**: sem handshake, sem conexão, um datagrama por mensagem. A confiabilidade, quando necessária, é do próprio CoAP (seção 3).

**2. O formato** (*Message Format*):

```
 0                   1                   2                   3
|Ver| T |  TKL  |      Code     |          Message ID           |
|   Token (0 a 8 bytes) ...
|   Opções ...
|1 1 1 1 1 1 1 1|    Payload ...
```

- **Ver** = 1; **T** = tipo (0 CON, 1 NON, 2 ACK, 3 RST); **TKL** = tamanho do token (0 a 8).
- **Code**: 3 bits de classe e 5 de detalhe; 0.01 = `0x01`, 2.05 = `0x45`, 4.04 = `0x84`. Código 0.00 = mensagem **vazia** (um ACK ou RST sem conteúdo: só os 4 bytes).
- **Message ID** (16 bits): casa um CON com o seu ACK e permite **descartar duplicatas**.
- **Token**: casa uma **requisição** com a sua **resposta** (mesmo que ela venha depois, em outra mensagem). Message ID é da camada de mensagens; token, da de requisição/resposta.
- **Opções** em ordem crescente de número, cada uma com um byte de **delta** (diferença para a opção anterior) e **comprimento** em 4 bits cada; 13 e 14 indicam 1 e 2 bytes extras (valor − 13 ou − 269). Opções repetidas (vários `Uri-Path`) têm delta 0. As mais usadas: If-Match 1, ETag 4, If-None-Match 5, **Observe 6**, Location-Path 8, **Uri-Path 11**, **Content-Format 12**, Max-Age 14, Uri-Query 15, Accept 17, **Block2 23**, **Block1 27**, Size2 28, Size1 60.
- **0xFF** marca o início do payload; sem payload, não há marcador.

**Exemplo resolvido 1 (GET à mão).** `GET coap://.../sensores/temp`, confirmável, Message ID 0x1234, token `AB CD`:

```
42           Ver 1, T = 0 (CON), TKL = 2           (01 00 0010)
01           Code 0.01 = GET
12 34        Message ID
AB CD        Token
B8 + 8 bytes Uri-Path "sensores": delta 11 (B), comprimento 8
04 + 4 bytes Uri-Path "temp": delta 0 (repetida), comprimento 4
```

Total: 4 + 2 + 9 + 5 = **20 bytes**. A resposta *piggybacked* (no próprio ACK): `62 45 12 34 AB CD C0 FF 32 33 2E 35` = ACK (T = 2), TKL 2, 2.05 Content, o mesmo Message ID e o mesmo token, Content-Format 0 (delta 12, comprimento 0: o valor 0 de uma opção inteira ocupa zero bytes), marcador e `23.5` — **12 bytes**. Compare com os 223 + 204 bytes do POST HTTP do T01. Conferido com o codificador abaixo, que gera os mesmos bytes que o aiocoap:

```python
#!/usr/bin/env python3
"""coap_msg.py — codifica e decodifica mensagens CoAP (RFC 7252) à mão; confere com o aiocoap."""
TIPOS = ["CON", "NON", "ACK", "RST"]
OPCOES = {6: "Observe", 11: "Uri-Path", 12: "Content-Format", 15: "Uri-Query", 23: "Block2", 27: "Block1", 60: "Size1", 28: "Size2"}

def _nib(v):
    """Nibble de delta/comprimento: 0–12 direto; 13 = +1 byte (v−13); 14 = +2 bytes (v−269)."""
    if v < 13:  return v, b""
    if v < 269: return 13, bytes([v - 13])
    return 14, (v - 269).to_bytes(2, "big")

def codificar(tipo, codigo, mid, token=b"", opcoes=(), payload=b""):
    """opcoes: lista de (número, bytes). Codigo como (classe, detalhe), ex. (0, 1) = GET."""
    out = bytearray([0x40 | tipo << 4 | len(token), codigo[0] << 5 | codigo[1]])
    out += mid.to_bytes(2, "big") + token
    anterior = 0
    for num, val in sorted(opcoes, key=lambda o: o[0]):      # opções em ordem crescente: delta
        d, dx = _nib(num - anterior)
        l, lx = _nib(len(val))
        out += bytes([d << 4 | l]) + dx + lx + val
        anterior = num
    if payload:
        out += b"\xff" + payload                              # marcador de payload
    return bytes(out)

def uint_opcao(v):
    """Opções uint: menor número de bytes, zero vira comprimento 0."""
    return v.to_bytes((v.bit_length() + 7) // 8, "big")

def decodificar(m):
    tipo, tkl = m[0] >> 4 & 3, m[0] & 0x0F
    classe, det = m[1] >> 5, m[1] & 0x1F
    mid = int.from_bytes(m[2:4], "big")
    pos = 4 + tkl
    txt = f"{TIPOS[tipo]} {classe}.{det:02d} mid=0x{mid:04X} token={m[4:pos].hex() or '-'}"
    num = 0
    while pos < len(m) and m[pos] != 0xFF:
        d, l = m[pos] >> 4, m[pos] & 0x0F
        pos += 1
        if d == 13: d = 13 + m[pos]; pos += 1
        elif d == 14: d = 269 + int.from_bytes(m[pos:pos + 2], "big"); pos += 2
        if l == 13: l = 13 + m[pos]; pos += 1
        elif l == 14: l = 269 + int.from_bytes(m[pos:pos + 2], "big"); pos += 2
        num += d
        val = m[pos:pos + l]; pos += l
        nome = OPCOES.get(num, str(num))
        if nome in ("Block1", "Block2"):
            v = int.from_bytes(val, "big") if val else 0
            txt += f" {nome}=(num={v >> 4}, M={v >> 3 & 1}, SZX={v & 7} → {2 ** ((v & 7) + 4)} B)"
        elif nome in ("Uri-Path", "Uri-Query"):
            txt += f" {nome}={val.decode()}"
        else:
            txt += f" {nome}={int.from_bytes(val, 'big') if val else 0}"
    if pos < len(m):
        txt += f" payload={len(m) - pos - 1} B"
    return txt

if __name__ == "__main__":
    import warnings; warnings.simplefilter("ignore", DeprecationWarning)
    import aiocoap
    from aiocoap.numbers.codes import Code
    from aiocoap.numbers.types import Type
    meu = codificar(0, (0, 1), 0x1234, b"\xab\xcd", [(11, b"sensores"), (11, b"temp")])
    m = aiocoap.Message(mtype=Type.CON, code=Code.GET, mid=0x1234, token=b"\xab\xcd", uri_path=("sensores", "temp"))
    print("à mão :", meu.hex(" "), f"({len(meu)} B)")
    print("aiocoap:", m.encode().hex(" "), "iguais:", meu == m.encode())
    print("  ", decodificar(meu))
    resp = codificar(2, (2, 5), 0x1234, b"\xab\xcd", [(12, uint_opcao(0))], b"23.5")
    print("resposta piggybacked:", resp.hex(" "), f"({len(resp)} B):", decodificar(resp))
    obs = codificar(0, (0, 1), 0x1235, b"\x01", [(6, uint_opcao(0)), (11, b"sensores"), (11, b"temp")])
    print("GET com Observe=0:", obs.hex(" "), f"({len(obs)} B)")
```

**3. A camada de mensagens** (*Message Semantics*).
- **CON** (*confirmable*): exige **ACK** com o mesmo Message ID. Sem ACK, o remetente **retransmite** com o **mesmo** Message ID: o primeiro tempo limite é sorteado entre **ACK_TIMEOUT** e ACK_TIMEOUT × **ACK_RANDOM_FACTOR** (2 a 3 s, com os padrões 2 s e 1,5) e **dobra** a cada tentativa, até **MAX_RETRANSMIT** = 4 retransmissões. O sorteio evita que mil sensores que perderam a mesma mensagem retransmitam juntos.
- **NON** (*non-confirmable*): sem ACK, sem retransmissão. Para leituras periódicas em que a próxima substitui a perdida.
- **ACK**: confirma um CON; pode carregar a resposta (**piggybacked**).
- **RST**: "recebi, mas não tenho contexto para isso" (por exemplo, uma notificação de uma observação que o cliente já esqueceu).
- **Deduplicação** (*Message Deduplication*): o receptor lembra os Message IDs recentes (por EXCHANGE_LIFETIME, 247 s) e, ao receber uma repetição, reenvia o mesmo ACK sem reprocessar.
- **Resposta separada**: se o servidor demora (precisa ler um sensor lento), manda primeiro um **ACK vazio** (4 bytes) para parar as retransmissões e depois a resposta num **CON** próprio, com **outro** Message ID e o **mesmo token**, que o cliente confirma com ACK.

Parâmetros derivados (*Transmission Parameters*): **MAX_TRANSMIT_SPAN** = ACK_TIMEOUT × (2^MAX_RETRANSMIT − 1) × ACK_RANDOM_FACTOR = 2 × 15 × 1,5 = **45 s** (do primeiro envio à última retransmissão, no pior caso) e **MAX_TRANSMIT_WAIT** = 2 × (2^5 − 1) × 1,5 = **93 s** (até desistir). **NSTART** = 1: no máximo uma interação pendente por servidor.

**Exemplo resolvido 2 (retransmissões medidas).** Um GET confirmável do aiocoap para um servidor que nunca responde. O "servidor mudo" só registra a hora de chegada de cada datagrama (usa o `decodificar` da seção 2):

Os cinco datagramas têm o **mesmo Message ID**: se o servidor tivesse recebido dois, processaria um só. Para um dispositivo em PSM, essa é a conta da **energia**: um servidor fora do ar pode manter o rádio acordado por até 93 s numa única leitura. Ajuste os parâmetros (a libcoap permite) ou use NON.

**4. Observação** (RFC 7641). Em vez de perguntar a cada minuto (*polling*), o cliente faz um GET com a opção **Observe = 0** (registrar). O servidor responde normalmente e, a cada mudança do recurso, manda uma **notificação** — uma resposta 2.05 com o **mesmo token** e um **número de sequência** crescente na opção Observe, para o cliente descartar notificações que chegam fora de ordem. Notificações podem ser CON ou NON; o servidor deve mandar uma CON de vez em quando (pelo menos a cada 24 h) para descobrir se o cliente ainda existe — se ele responder RST, ou não responder, a observação é removida. O cliente cancela com GET e **Observe = 1**, ou respondendo RST a uma notificação. A garantia é de **consistência eventual**: o cliente recebe o estado **mais recente**, não necessariamente todos os estados intermediários.

**5. Transferência em blocos** (RFC 7959). Um datagrama UDP grande é fragmentado no IP, e perder um fragmento perde o datagrama inteiro; numa rede 6LoWPAN, com quadros de 127 bytes, é pior. A RFC 7252 recomenda mensagens que caibam em 1152 bytes, com até 1024 de payload (*Message Size*). Para mais que isso:
- **Block2** (opção 23): a **resposta** vem em pedaços (baixar um log, uma imagem de firmware).
- **Block1** (opção 27): a **requisição** vai em pedaços (subir uma configuração grande); o servidor confirma cada bloco com **2.31 Continue**.
- O valor da opção tem **NUM** (número do bloco, até 20 bits), **M** (mais blocos?) e **SZX** (3 bits): tamanho do bloco = **2^(SZX + 4)**, de 16 (SZX 0) a **1024** bytes (SZX 6). O receptor pode pedir blocos **menores** do que os oferecidos, nunca maiores.
- **Size2**/**Size1** informam o tamanho total, para o cliente decidir se cabe.

**Exemplo resolvido 3 (blocos).** O recurso `/log` do servidor de laboratório tem 1428 bytes. Com SZX = 6 (1024 bytes): ⌈1428 / 1024⌉ = **2 blocos** (1024 + 404). Com SZX = 2 (64 bytes): ⌈1428 / 64⌉ = **23 blocos** (22 de 64 e o último de 20 bytes): **23 requisições CON e 23 ACKs = 46 datagramas**. O espião confirmou as duas trocas:

```
C→S   10 B  CON 0.01 mid=0xEF3A token=a7e9 Uri-Path=log
S→C 1034 B  ACK 2.05 mid=0xEF3A token=a7e9 Content-Format=0 Block2=(num=0, M=1, SZX=6 → 1024 B) payload=1024 B
C→S   12 B  CON 0.01 mid=0xEF3B token=a7ea Uri-Path=log Block2=(num=1, M=0, SZX=6 → 1024 B)
S→C  414 B  ACK 2.05 mid=0xEF3B token=a7ea Content-Format=0 Block2=(num=1, M=0, SZX=6 → 1024 B) payload=404 B
 ...
C→S   13 B  CON 0.01 mid=0x8F00 token=6c47 Uri-Path=log Block2=(num=22, M=0, SZX=2 → 64 B)
S→C   31 B  ACK 2.05 mid=0x8F00 token=6c47 Content-Format=0 Block2=(num=22, M=0, SZX=2 → 64 B) payload=20 B
```

Blocos pequenos custam mais mensagens e mais cabeçalho; blocos grandes arriscam fragmentação. Escolha pelo MTU do caminho.

**6. Segurança.** CoAP usa **DTLS** (TLS para datagramas) na porta **5684**, esquema `coaps://`, com três modos (*DTLS-Secured CoAP*): **PreSharedKey** (uma chave simétrica por dispositivo e uma identidade: leve, ótimo para microcontrolador; a chave tem de ser única por aparelho), **RawPublicKey** (par de chaves sem certificado) e **X.509** (certificados, como o mTLS do M1.9.T09). O handshake DTLS também custa ida e volta; para não repeti-lo a cada despertar, use retomada de sessão ou **Connection ID** (RFC 9146) quando o NAT muda a porta. A alternativa moderna é o **OSCORE** (RFC 8613), que protege a mensagem CoAP em si e atravessa proxies. Segurança a fundo fica para o M4.1.

**7. O servidor e o cliente no PC: aiocoap.** O servidor de laboratório tem um recurso observável que muda a cada 2 s, uma configuração com GET e PUT validado e um recurso grande servido em blocos (aiocoap 0.4.17):

```python
#!/usr/bin/env python3
"""servidor_coap.py — servidor CoAP de laboratório com aiocoap: leitura observável,
configuração com PUT e um recurso grande servido em blocos."""
import asyncio, json, random
import aiocoap
import aiocoap.resource as resource

class Temperatura(resource.ObservableResource):
    """GET /sensores/temp; com Observe, notifica a cada nova leitura."""
    def __init__(self):
        super().__init__()
        self.valor = 23.5
        asyncio.get_event_loop().call_later(2, self.medir)

    def medir(self):
        self.valor = round(self.valor + random.uniform(-0.3, 0.3), 1)
        self.updated_state()                        # dispara as notificações aos observadores
        asyncio.get_event_loop().call_later(2, self.medir)

    async def render_get(self, request):
        return aiocoap.Message(payload=f"{self.valor}".encode(), content_format=0)   # text/plain

class Config(resource.Resource):
    """GET e PUT /config, em JSON (Content-Format 50)."""
    def __init__(self):
        super().__init__()
        self.cfg = {"intervalo_s": 60}

    async def render_get(self, request):
        return aiocoap.Message(payload=json.dumps(self.cfg).encode(), content_format=50)

    async def render_put(self, request):
        try:
            novo = json.loads(request.payload)
            if not isinstance(novo.get("intervalo_s"), int):
                raise ValueError
        except ValueError:
            return aiocoap.Message(code=aiocoap.BAD_REQUEST, payload=b"intervalo_s inteiro")
        self.cfg.update(novo)
        return aiocoap.Message(code=aiocoap.CHANGED)

class Log(resource.Resource):
    """GET /log: 1428 bytes, maior que um datagrama confortável: vai em blocos (Block2)."""
    async def render_get(self, request):
        linhas = "".join(f"{i:04d} evento de teste da forja............\n" for i in range(34))
        return aiocoap.Message(payload=linhas.encode(), content_format=0)

async def main():
    raiz = resource.Site()
    raiz.add_resource([".well-known", "core"], resource.WKCResource(raiz.get_resources_as_linkheader))
    raiz.add_resource(["sensores", "temp"], Temperatura())
    raiz.add_resource(["config"], Config())
    raiz.add_resource(["log"], Log())
    await aiocoap.Context.create_server_context(raiz, bind=("0.0.0.0", 5683))
    await asyncio.get_running_loop().create_future()

asyncio.run(main())
```

```python
#!/usr/bin/env python3
"""espiao_coap.py — proxy UDP que mostra cada mensagem CoAP (porta 5684 → servidor na 5683)."""
import asyncio
from coap_msg import decodificar

SERVIDOR = ("127.0.0.1", 5683)

class Lado(asyncio.DatagramProtocol):
    def __init__(self, ao_receber): self.ao_receber = ao_receber
    def connection_made(self, t): self.t = t
    def datagram_received(self, d, a): self.ao_receber(d, a)

async def main():
    loop = asyncio.get_running_loop()
    cliente = {}
    def do_servidor(d, a):
        print(f"S→C {len(d):4d} B  {decodificar(d)}", flush=True)
        frente.t.sendto(d, cliente["end"])
    def do_cliente(d, a):
        cliente["end"] = a
        print(f"C→S {len(d):4d} B  {decodificar(d)}", flush=True)
        tras.t.sendto(d)
    _, frente = await loop.create_datagram_endpoint(lambda: Lado(do_cliente), local_addr=("127.0.0.1", 5684))
    _, tras = await loop.create_datagram_endpoint(lambda: Lado(do_servidor), remote_addr=SERVIDOR)
    await loop.create_future()

asyncio.run(main())
```

```c
/* forja_coap.c — cliente CoAP com libcoap (componente espressif/coap): GET confirmável
 * e PUT de configuração; com psk != NULL, usa DTLS com chave pré-compartilhada */
#include <stdbool.h>
#include <string.h>
#include "esp_log.h"
#include "lwip/inet.h"
#include "coap3/coap.h"

static const char *TAG = "forja_coap";
static volatile bool respondeu;

static coap_response_t ao_responder(coap_session_t *s, const coap_pdu_t *enviado,
                                    const coap_pdu_t *recebido, const coap_mid_t mid)
{
    size_t n;
    const uint8_t *dados;
    coap_pdu_code_t c = coap_pdu_get_code(recebido);
    coap_get_data(recebido, &n, &dados);
    ESP_LOGI(TAG, "resposta %d.%02d (mid %d): %.*s", COAP_RESPONSE_CLASS(c), c & 0x1F,
             (int)mid, (int)n, n ? (const char *)dados : "");
    respondeu = true;
    return COAP_RESPONSE_OK;
}

/* Monta e envia uma requisição CON e espera a resposta (com retransmissão da libcoap). */
static bool requisitar(coap_context_t *ctx, coap_session_t *s, coap_pdu_code_t metodo,
                       const char *p1, const char *p2, const char *corpo)
{
    coap_pdu_t *pdu = coap_pdu_init(COAP_MESSAGE_CON, metodo, coap_new_message_id(s),
                                    coap_session_max_pdu_size(s));
    if (pdu == NULL) return false;
    uint8_t token[8];
    size_t tl;
    coap_session_new_token(s, &tl, token);
    coap_add_token(pdu, tl, token);
    coap_add_option(pdu, COAP_OPTION_URI_PATH, strlen(p1), (const uint8_t *)p1);
    if (p2) coap_add_option(pdu, COAP_OPTION_URI_PATH, strlen(p2), (const uint8_t *)p2);
    if (corpo) {
        uint8_t cf[2];
        coap_add_option(pdu, COAP_OPTION_CONTENT_FORMAT,
                        coap_encode_var_safe(cf, sizeof cf, COAP_MEDIATYPE_APPLICATION_JSON), cf);
        coap_add_data(pdu, strlen(corpo), (const uint8_t *)corpo);
    }
    respondeu = false;
    if (coap_send(s, pdu) == COAP_INVALID_MID) return false;
    for (int espera = 0; !respondeu && espera < 100; espera++)   /* até ~100 s: cobre as 4 retransmissões */
        coap_io_process(ctx, 1000);
    return respondeu;
}

/* ip: servidor CoAP; psk/identidade: NULL para CoAP sem segurança (porta 5683), ou DTLS-PSK (5684). */
void forja_coap_demo(const char *ip, const char *identidade, const char *psk)
{
    coap_startup();
    coap_context_t *ctx = coap_new_context(NULL);
    coap_address_t dst;
    coap_address_init(&dst);
    dst.addr.sin.sin_family = AF_INET;
    dst.addr.sin.sin_port = htons(psk ? COAPS_DEFAULT_PORT : COAP_DEFAULT_PORT);
    inet_pton(AF_INET, ip, &dst.addr.sin.sin_addr);

    coap_session_t *s;
    if (psk) {
        coap_dtls_cpsk_t cfg = { .version = COAP_DTLS_CPSK_SETUP_VERSION };
        cfg.psk_info.identity.s = (const uint8_t *)identidade;
        cfg.psk_info.identity.length = strlen(identidade);
        cfg.psk_info.key.s = (const uint8_t *)psk;
        cfg.psk_info.key.length = strlen(psk);
        s = coap_new_client_session_psk2(ctx, NULL, &dst, COAP_PROTO_DTLS, &cfg);
    } else {
        s = coap_new_client_session(ctx, NULL, &dst, COAP_PROTO_UDP);
    }
    if (ctx == NULL || s == NULL) {
        ESP_LOGE(TAG, "não criou contexto ou sessão");
        return;
    }
    coap_register_response_handler(ctx, ao_responder);

    requisitar(ctx, s, COAP_REQUEST_CODE_GET, "sensores", "temp", NULL);
    requisitar(ctx, s, COAP_REQUEST_CODE_PUT, "config", NULL, "{\"intervalo_s\":30}");
    requisitar(ctx, s, COAP_REQUEST_CODE_GET, "config", NULL, NULL);

    coap_session_release(s);
    coap_free_context(ctx);
    coap_cleanup();
}
```

**9. CoAP, MQTT ou HTTP?**

| | HTTP/1.1 (T01) | MQTT (T02) | CoAP |
|---|---|---|---|
| Transporte | TCP (+TLS) | TCP (+TLS) | UDP (+DTLS) |
| Modelo | requisição/resposta | publicar/assinar com broker | requisição/resposta + observação |
| Cabeçalho mínimo | ~100–200 bytes de texto | 2 bytes | 4 bytes |
| Conexão | por requisição ou persistente | persistente, keepalive | nenhuma |
| Confiabilidade | do TCP | do TCP + QoS 0/1/2 | CON/ACK opcional |
| Servidor alcança o dispositivo atrás de NAT | não | sim, pela conexão aberta | só enquanto o mapeamento UDP vive |
| Muitos consumidores do mesmo dado | não | sim, nativo | proxy ou observação múltipla |
| Ferramentas e nuvem | universais | brokers e plataformas (T06, T07) | menos comuns; LwM2M nas operadoras |

Regra prática: **dispositivo dormindo, enlace caro, mensagens pequenas e esporádicas** (NB-IoT com PSM, rede 6LoWPAN/Thread) → **CoAP**, com CBOR e DTLS. **Dispositivo conectado, comandos que descem a qualquer hora, vários consumidores** → **MQTT**. **Integração web, configuração, OTA** → **HTTP**. Lembre do NAT: depois de um tempo ocioso (às vezes menos de um minuto em redes celulares), o servidor não alcança mais o dispositivo por UDP até ele falar de novo.

## Pratique

2. Decodifique `40 01 00 07 B4 74 65 6D 70`.
3. Qual é a diferença entre Message ID e token? Dê uma situação em que dois datagramas têm o mesmo Message ID e outra em que têm o mesmo token com Message IDs diferentes.
4. Com ACK_TIMEOUT 2 s, ACK_RANDOM_FACTOR 1,5 e MAX_RETRANSMIT 4, e um primeiro tempo sorteado de 2,5 s, em que instantes saem as retransmissões e quando o cliente desiste?
5. Um sensor NB-IoT manda uma leitura CON por hora. O servidor está fora do ar há um dia. Quanto tempo de rádio a mais, no pior caso, cada leitura custa? Que alternativa você usaria?
6. Quantos blocos e quantos datagramas são necessários para baixar uma imagem de 100 kB com Block2 e SZX 6? E com SZX 4?
7. Por que o cliente deve ignorar uma notificação com número de sequência menor que o da última recebida?
8. Desenhe a troca de uma resposta separada: GET CON, ACK vazio, resposta CON, ACK. Quantos bytes custam, com o GET e a resposta do Exemplo resolvido 1?

## Armadilhas comuns
- Usar CON para toda leitura periódica e manter o rádio acordado com retransmissões para um servidor fora do ar.
- Confundir Message ID com token: casar a resposta pelo Message ID quebra respostas separadas e notificações.
- Gerar Message IDs repetidos depois de um reset (comece de um valor aleatório) e ter mensagens novas descartadas como duplicatas.
- Mandar payloads maiores que o MTU sem Block2/Block1 e perder tudo por um fragmento.
- Esperar que o servidor alcance o dispositivo por UDP horas depois do último envio (o NAT já esqueceu).
- Achar que a observação entrega todo estado intermediário: entrega o mais recente.
- Esquecer de cancelar observações; o servidor continua mandando notificações a quem não quer mais.
- Usar uma mesma chave PSK em toda a frota.
- Enviar JSON quando o CoAP e o enlace pedem CBOR.

## Gabarito
1. `51 02 00 42 07` (Ver 1 e NON = 1 dão `0x50`, mais TKL 1 = `0x51`; 0.02 POST) + Uri-Path "leituras" (`B8` + 8 bytes) + Content-Format 60 (delta 1, comprimento 1: `11 3C`) + `FF` + 10 bytes = 5 + 9 + 2 + 1 + 10 = 27 bytes.
2. `40` = Ver 1, CON, TKL 0; `01` = GET; Message ID 0x0007; `B4` = opção 11 (Uri-Path) com 4 bytes: "temp". É `GET /temp`, confirmável, sem token.
3. O Message ID casa um CON com o seu ACK e serve para deduplicar; o token casa requisição e resposta. Mesmo Message ID: as retransmissões de um CON (e o ACK correspondente). Mesmo token com Message IDs diferentes: as notificações de uma observação, ou a resposta separada (CON do servidor) em relação ao GET original.
4. Retransmissões em 2,5; 7,5 (2,5 + 5); 17,5 (+ 10); 37,5 s (+ 20). Desiste em 37,5 + 40 = 77,5 s (2,5 × 31).
5. Até MAX_TRANSMIT_WAIT = 93 s de espera, com o rádio fora do PSM, por leitura: em um dia, 24 × 93 s ≈ 37 min de rádio a mais. Alternativas: NON, MAX_RETRANSMIT menor, ou detectar a falha e espaçar as tentativas (guardar leituras e mandar um lote depois).
6. 100 kB = 102 400 bytes. SZX 6 (1024 B): 100 blocos, 200 datagramas (CON + ACK). SZX 4 (256 B): 400 blocos, 800 datagramas.
7. Datagramas UDP podem chegar fora de ordem; uma notificação velha que chega depois sobrescreveria o estado novo. O número de sequência (com a regra de tempo da RFC 7641) permite descartá-la.
8. GET CON (20 B) → ACK vazio (4 B) → resposta CON 2.05 com o mesmo token e outro Message ID (12 B) → ACK vazio do cliente (4 B): 40 bytes em 4 datagramas, contra 32 bytes em 2 com a resposta piggybacked.
9. As notificações param. Se o servidor voltar sem estado, ele não sabe da observação; o cliente só descobre se tiver um tempo limite (Max-Age da última notificação) e precisa se registrar de novo. Se o servidor mandava notificações CON, o aiocoap avisa o erro na observação.
10. CoAP: o aparelho dorme quase sempre, manda pouco e raramente; sem TCP nem TLS por mensagem, com DTLS-PSK ou OSCORE e CBOR. A mudança de tarifa fica no servidor e é buscada pelo aparelho quando acorda (um GET depois do envio, ou na resposta ao POST). MQTT exigiria manter TCP e keepalive ou reconectar a cada 6 h com handshake completo.
