# M1.10.T05 — JSON, CBOR, Protobuf

> No T01 o corpo da requisição era `{"t":23.5,"u":61}` e ninguém discutiu. Mas esse corpo é o que viaja em **toda** mensagem, por todo o rádio, durante toda a vida do produto, e passa por firmware em C, broker, banco e painel. No M1.9.T05 você já viu o extremo: 4 bytes binários no LoRaWAN, decodificados por um *payload formatter*. Este tópico organiza as escolhas do meio. O **JSON** é legível e universal, mas caro em bytes e em memória; o **CBOR** (RFC 8949) é o "JSON binário" que o CoAP (T03) usa; o **Protobuf** tem esquema, números de campo e varints e roda no ESP32 com o **nanopb**; a **struct empacotada** é o mínimo absoluto. Tudo será contado byte a byte com o mesmo payload, e o tópico fecha com o critério de escolha — que nem sempre é o menor tamanho.

## Ao final você consegue
- Gerar e analisar JSON no firmware com cJSON (criação, impressão, análise, verificação de tipos, liberação de memória) e reconhecer o custo do JSON em bytes, em memória e em processamento.
- Codificar e decodificar CBOR pela RFC 8949 (tipos maiores, argumento, inteiros, strings, arrays, mapas, ponto flutuante, tags, codificação determinística) à mão e com bibliotecas.
- Definir mensagens Protocol Buffers (arquivo .proto, números de campo, tipos de fio, varint e zigzag, campos opcionais e repetidos, regras de compatibilidade) e usá-las no ESP32 com nanopb.
- Comparar o tamanho e o custo de JSON, CBOR, Protobuf e struct binária para o mesmo payload e escolher o formato conforme o enlace, a evolução do esquema e as ferramentas do lado da nuvem.

## Resumo
**1. Por que o formato importa.** Uma leitura de 25 bytes a cada minuto são 43 200 mensagens por mês. Cada byte a mais custa rádio ligado (energia), dados de plano celular, banda do broker e disco do banco, multiplicados pela frota. Mas o formato também decide **quem consegue ler** a mensagem sem código especial (um operador olhando o broker, um banco que entende JSON, um script de suporte) e **como o esquema evolui** quando o firmware 2.0 acrescenta um campo e metade da frota ainda está na 1.0. Os quatro candidatos, com o mesmo dado — `id` "forja-001", `ts` 1760000000, temperatura 23,5 °C, umidade 61%, bateria 3712 mV:

| Formato | Bytes | Esquema | Legível | Observação |
|---|---|---|---|---|
| JSON compacto | **61** | implícito (nomes no texto) | sim | universal; nomes repetidos em cada mensagem |
| CBOR, chaves texto | **38** | implícito | com ferramenta | mesmo modelo de dados do JSON |
| CBOR, chaves inteiras | **29** | combinado à parte | com ferramenta | chaves 1–5 no lugar dos nomes |
| Protobuf (nanopb) | **25** | `.proto` obrigatório | com o `.proto` | varints; campos novos não quebram os antigos |
| struct empacotada | **18** | só no código C | não | tamanho fixo; mudar exige versão |

Todos os números foram gerados de verdade com o `comparar.py` da seção 6 (Python 3.13, cbor2 6.1, protobuf 7.36) e conferidos com os programas em C das seções 2, 4 e 5.

**2. JSON e cJSON.** O JSON (RFC 8259) tem seis tipos: objeto, array, string, número, booleano e `null`. Não tem binário (vira base64, +33%), não tem inteiro separado de ponto flutuante e não diz nada sobre precisão: a RFC avisa que números além da precisão de um `double` (inteiros acima de 2^53) podem ser lidos errado do outro lado.

O **cJSON** monta uma **árvore** de nós alocados no heap. Para gerar, cria-se a árvore e imprime-se num texto (outra alocação); para analisar, faz-se o caminho inverso. Regras de sobrevivência:
- Todo `cJSON_Parse` e todo `cJSON_Create*` raiz exigem **um** `cJSON_Delete` na raiz (libera a árvore inteira); todo texto de `cJSON_Print*` exige `cJSON_free`.
- **Verifique o tipo** antes de usar o valor: `cJSON_IsNumber`, `cJSON_IsString`, `cJSON_IsBool`. Um campo ausente devolve `NULL`, e as funções `Is*` aceitam `NULL` e respondem falso.
- `cJSON_PrintUnformatted` gera o texto sem espaços; `cJSON_Print` indenta (útil só para depurar).
- Para não alocar o texto, `cJSON_PrintPreallocated` imprime num buffer seu.

Executado no PC com o `cJSON.c` do próprio ESP-IDF 5.5 (`gcc -std=c11 -Wall -Wextra -Werror -O2 -I$IDF_PATH/components/json/cJSON leitura_cjson.c $IDF_PATH/components/json/cJSON/cJSON.c -lm`) e compilado também para o ESP32, onde o `main` é omitido:

```c
/* leitura_cjson.c — gera e analisa JSON com cJSON, contando as alocações (mesmo código do ESP32) */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include "cJSON.h"

#ifndef ESP_PLATFORM   /* contagem de alocações só no PC */
static size_t n_aloc, bytes_vivos, pico;
static void *contar_malloc(size_t n)
{
    size_t *p = malloc(n + sizeof(size_t));
    if (!p) return NULL;
    *p = n; n_aloc++; bytes_vivos += n;
    if (bytes_vivos > pico) pico = bytes_vivos;
    return p + 1;
}
static void contar_free(void *q)
{
    if (!q) return;
    size_t *p = (size_t *)q - 1;
    bytes_vivos -= *p;
    free(p);
}
#endif

/* Monta {"id":...,"ts":...,"t":...,"u":...,"bat":...}; quem chama libera com cJSON_free. */
char *leitura_json(const char *id, double ts, double t, int u, int bat)
{
    cJSON *o = cJSON_CreateObject();
    if (o == NULL) return NULL;
    cJSON_AddStringToObject(o, "id", id);
    cJSON_AddNumberToObject(o, "ts", ts);
    cJSON_AddNumberToObject(o, "t", t);
    cJSON_AddNumberToObject(o, "u", u);
    cJSON_AddNumberToObject(o, "bat", bat);
    char *s = cJSON_PrintUnformatted(o);          /* NULL se faltar memória */
    cJSON_Delete(o);                              /* a árvore inteira, de uma vez */
    return s;
}

/* Analisa um comando de configuração; só aceita se os dois campos existirem com o tipo certo. */
int ler_config(const char *texto, int *intervalo_s, int *rele)
{
    cJSON *r = cJSON_Parse(texto);
    if (r == NULL) return -1;                     /* JSON malformado */
    const cJSON *iv = cJSON_GetObjectItemCaseSensitive(r, "intervalo_s");
    const cJSON *rl = cJSON_GetObjectItemCaseSensitive(r, "rele");
    int ok = cJSON_IsNumber(iv) && iv->valuedouble >= 10 && iv->valuedouble <= 3600 && cJSON_IsBool(rl);
    if (ok) { *intervalo_s = iv->valueint; *rele = cJSON_IsTrue(rl); }
    cJSON_Delete(r);
    return ok ? 0 : -2;                           /* -2: campos faltando ou de tipo errado */
}

#ifndef ESP_PLATFORM
int main(void)
{
    cJSON_Hooks h = { contar_malloc, contar_free };
    cJSON_InitHooks(&h);

    char *s = leitura_json("forja-001", 1760000000, 23.5, 61, 3712);
    printf("%s (%zu B)\n", s, strlen(s));
    printf("gerar: %zu alocações, pico %zu B de heap\n", n_aloc, pico);
    cJSON_free(s);

    n_aloc = pico = 0;
    const char *testes[] = { "{\"intervalo_s\":30,\"rele\":true}", "{\"intervalo_s\":\"30\",\"rele\":true}",
                             "{\"intervalo_s\":30,\"rele\":true", "{\"rele\":false,\"intervalo_s\":5}" };
    for (int i = 0; i < 4; i++) {
        int iv = 0, rl = 0;
        int r = ler_config(testes[i], &iv, &rl);
        printf("%-34s -> %s\n", testes[i], r == 0 ? "aceito" : r == -1 ? "JSON malformado" : "campos inválidos");
    }
    printf("analisar 4 textos: %zu alocações, pico %zu B; vazamento: %zu B\n", n_aloc, pico, bytes_vivos);
    return 0;
}
#endif
```

Saída:

```
{"id":"forja-001","ts":1760000000,"t":23.5,"u":61,"bat":3712} (61 B)
gerar: 14 alocações, pico 726 B de heap
{"intervalo_s":30,"rele":true}     -> aceito
{"intervalo_s":"30","rele":true}   -> campos inválidos
{"intervalo_s":30,"rele":true      -> JSON malformado
{"rele":false,"intervalo_s":5}     -> campos inválidos
analisar 4 textos: 24 alocações, pico 215 B; vazamento: 0 B
```

Leia como engenheiro de firmware: **14 alocações e ~0,7 kB de pico** para gerar 61 bytes (no PC de 64 bits; no ESP32, com ponteiros de 4 bytes, cada nó é menor, mas a ordem de grandeza é a mesma e o buffer de impressão começa em 256 bytes). Num ESP32 com 300 kB livres isso não preocupa; num laço que roda a cada 100 ms durante meses, cada `cJSON_Delete` esquecido é um vazamento que termina em reset (M1.7.T08). E o `"30"` entre aspas foi **recusado**: validar o tipo é obrigatório, porque o outro lado (um script, um painel) vai mandar string onde você esperava número.

**Armadilha do `float`.** `cJSON_AddNumberToObject(o, "t", 23.1f)` imprime `23.100000381469727`: o `float` vira `double` com o erro de representação à mostra, e a mensagem cresce 15 bytes. Arredonde antes (`round(t * 10) / 10.0`, que imprime `23.1`) ou mande inteiros em unidades menores (2310 centésimos de grau).

**3. CBOR à mão** (RFC 8949, *Major Types*). Cada item começa com um byte: os **3 bits altos** são o **tipo maior** e os **5 bits baixos**, o **argumento** (ou onde ele está):

| Tipo maior | Significado | Argumento é |
|---|---|---|
| 0 | inteiro não negativo | o valor |
| 1 | inteiro negativo | −1 − valor |
| 2 | string de bytes | o comprimento |
| 3 | string de texto (UTF-8) | o comprimento |
| 4 | array | número de itens |
| 5 | mapa | número de pares |
| 6 | tag | número da tag (o item seguinte é o conteúdo) |
| 7 | ponto flutuante e simples | `false` = F4, `true` = F5, `null` = F6; F9/FA/FB = float de 16/32/64 bits |

Os 5 bits baixos: **0 a 23** = o próprio argumento; **24, 25, 26, 27** = o argumento vem nos 1, 2, 4 ou 8 bytes seguintes, em **big-endian**. Valor 31 = comprimento indefinido (fluxo terminado por FF).

**Exemplo resolvido 1 (CBOR com chaves texto).** O mapa da tabela, na serialização determinística (chaves ordenadas pelos bytes codificados, cada valor na menor forma):

```
A5                       mapa (5) de 5 pares
61 74                    texto(1) "t"
F9 4D E0                 float16 23,5   (0 10011 0111100000: 1,46875 × 2^4)
61 75                    "u"
18 3D                    inteiro, argumento em 1 byte: 61
62 69 64                 "id"
69 66 6F 72 6A 61 2D 30 30 31   texto(9) "forja-001"
62 74 73                 "ts"
1A 68 E7 78 00           inteiro, argumento em 4 bytes: 0x68E77800 = 1 760 000 000
63 62 61 74              "bat"
19 0E 80                 inteiro, argumento em 2 bytes: 3712
```

Conta: 1 + (2 + 3) + (2 + 2) + (3 + 10) + (3 + 5) + (4 + 3) = **38 bytes**. Os nomes ainda viajam, mas cada string custa 1 byte de cabeçalho no lugar de 3 (aspas e dois-pontos), e os números viram binário. Trocando os nomes por inteiros 1–5 (cada chave cabe em 1 byte), o mapa cai para **29 bytes**. Repare no 23,5: ele é exato em meia precisão, então a forma preferida é `F9` + 2 bytes. Já 23,1 não é exato em float16 nem em float32: vai como `FB` + 8 bytes. Mais um motivo para mandar **inteiros escalados**.

- **Negativos**: −200 → tipo 1 com argumento 199 → `38 C7`. Sem complemento de dois, sem bit de sinal.
- **Tags** (*Tagging of Items*): `C1 1A 68 E7 78 00` é a tag 1 (tempo em segundos desde 1970) aplicada ao inteiro: o receptor sabe que é uma data.
- **Determinístico** (*Core Deterministic Encoding Requirements*): menor forma de cada argumento, sem comprimentos indefinidos, chaves de mapa ordenadas pela ordem lexicográfica dos bytes codificados. Importa quando a mensagem é **assinada** ou comparada por hash: os dois lados precisam gerar os mesmos bytes.

Um codificador mínimo em C (inteiros, texto e mapas, que é tudo o que uma leitura precisa), conferido contra o `cbor2` do Python e compilado também para o ESP32:

```c
/* cbor_min.c — codificador CBOR mínimo (RFC 8949): inteiros, strings de texto e mapas */
#include <stdint.h>
#include <stdio.h>
#include <string.h>

typedef struct { uint8_t *p; size_t n, max; int erro; } cbor_buf;

/* Cabeçalho: 3 bits de tipo maior + argumento na menor forma (0–23 no próprio byte; 24/25/26/27 = 1/2/4/8 bytes) */
static void cbor_cab(cbor_buf *b, uint8_t maior, uint64_t arg)
{
    uint8_t t[9];
    size_t k;
    if (arg < 24)               { t[0] = (uint8_t)(maior << 5 | arg); k = 1; }
    else if (arg <= 0xFF)       { t[0] = maior << 5 | 24; k = 2; }
    else if (arg <= 0xFFFF)     { t[0] = maior << 5 | 25; k = 3; }
    else if (arg <= 0xFFFFFFFF) { t[0] = maior << 5 | 26; k = 5; }
    else                        { t[0] = maior << 5 | 27; k = 9; }
    for (size_t i = 1; i < k; i++) t[i] = (uint8_t)(arg >> (8 * (k - 1 - i)));   /* big-endian */
    if (b->n + k > b->max) { b->erro = 1; return; }
    memcpy(b->p + b->n, t, k);
    b->n += k;
}

static void cbor_int(cbor_buf *b, int64_t v)       /* tipo 0 (não negativo) ou 1 (−1 − n) */
{
    if (v >= 0) cbor_cab(b, 0, (uint64_t)v);
    else        cbor_cab(b, 1, (uint64_t)(-1 - v));
}

static void cbor_texto(cbor_buf *b, const char *s)  /* tipo 3: comprimento + bytes UTF-8 */
{
    size_t n = strlen(s);
    cbor_cab(b, 3, n);
    if (b->n + n > b->max) { b->erro = 1; return; }
    memcpy(b->p + b->n, s, n);
    b->n += n;
}

static void cbor_mapa(cbor_buf *b, size_t pares) { cbor_cab(b, 5, pares); }   /* tipo 5 */

/* A leitura com chaves inteiras: {1: id, 2: ts, 3: t em 0,01 °C, 4: umidade, 5: bateria em mV} */
size_t leitura_cbor(uint8_t *out, size_t max, const char *id, uint32_t ts, int16_t t_centi,
                    uint8_t umidade, uint16_t bat_mv)
{
    cbor_buf b = { out, 0, max, 0 };
    cbor_mapa(&b, 5);
    cbor_int(&b, 1); cbor_texto(&b, id);
    cbor_int(&b, 2); cbor_int(&b, ts);
    cbor_int(&b, 3); cbor_int(&b, t_centi);
    cbor_int(&b, 4); cbor_int(&b, umidade);
    cbor_int(&b, 5); cbor_int(&b, bat_mv);
    return b.erro ? 0 : b.n;
}

#ifndef ESP_PLATFORM
int main(void)
{
    uint8_t buf[64];
    int16_t temps[] = { 2350, -200 };
    for (int i = 0; i < 2; i++) {
        size_t n = leitura_cbor(buf, sizeof buf, "forja-001", 1760000000u, temps[i], 61, 3712);
        printf("%zu B:", n);
        for (size_t k = 0; k < n; k++) printf(" %02x", buf[k]);
        printf("\n");
    }
    return 0;
}
#endif
```

Saída (o `cbor2.loads` devolve `{1: 'forja-001', 2: 1760000000, 3: 2350, 4: 61, 5: 3712}` e confirma que é a forma determinística):

```
29 B: a5 01 69 66 6f 72 6a 61 2d 30 30 31 02 1a 68 e7 78 00 03 19 09 2e 04 18 3d 05 19 0e 80
28 B: a5 01 69 66 6f 72 6a 61 2d 30 30 31 02 1a 68 e7 78 00 03 38 c7 04 18 3d 05 19 0e 80
```

Para decodificar CBOR qualquer no firmware, use uma biblioteca (TinyCBOR, QCBOR, ou o componente `espressif/cbor` do registro de componentes); no PC, `cbor2` (Python) e o site cbor.me, que mostra a anotação de cada byte.

**4. Protocol Buffers.** O Protobuf parte de um **esquema** compilado:

```proto
syntax = "proto3";

// Uma leitura do sensor da forja. Números de campo são para sempre:
// nunca reutilize um número apagado (use reserved).
message Leitura {
  string id        = 1;   // "forja-001"
  uint32 ts        = 2;   // segundos desde 1970 (UTC)
  sint32 t_centi   = 3;   // temperatura em 0,01 °C (zigzag: negativos curtos)
  uint32 umidade   = 4;   // %UR
  uint32 bat_mv    = 5;   // tensão da bateria em mV
}
```

No fio (*Message Structure*), cada campo é **tag + valor**, e a tag é um varint com `(número do campo << 3) | tipo de fio`. Tipos de fio: **0 = VARINT** (int32, uint32, sint32, bool, enum…), **1 = I64** (fixed64, double), **2 = LEN** (string, bytes, mensagens aninhadas, repeated empacotado), **5 = I32** (fixed32, float). Os nomes dos campos **não viajam**: só os números.

- **Varint** (*Base 128 Varints*): 7 bits de dado por byte, do menos significativo para o mais; o bit alto (0x80) diz "tem mais". Valores até 127 cabem em 1 byte; até 16 383, em 2.
- **Zigzag** (*More Integer Types*): um `int32` negativo vira um varint de **10 bytes** (é estendido para 64 bits). O `sint32` mapeia 0, −1, 1, −2, 2… para 0, 1, 2, 3, 4…: `(n << 1) ^ (n >> 31)`. Para grandezas que podem ser negativas (temperatura), use `sint32`.
- **Valor padrão não viaja**: em proto3, um `uint32` igual a 0 não é codificado. Se precisar distinguir "zero" de "ausente", declare `optional`.
- **repeated** de números vai **empacotado** (*packed*): uma tag LEN e os varints em sequência.

**Exemplo resolvido 2 (Protobuf à mão).**

```
0A 09 66 6F 72 6A 61 2D 30 30 31   campo 1, LEN (1<<3|2 = 0x0A), 9 bytes "forja-001"
10 80 F0 9D C7 06                  campo 2, VARINT (0x10): 1 760 000 000 em 5 bytes
18 DC 24                           campo 3, VARINT: zigzag(2350) = 4700 = 0x125C → DC 24
20 3D                              campo 4: 61
28 80 1D                           campo 5: 3712 = 0xE80 → 80 1D
```

Total: 11 + 6 + 3 + 2 + 3 = **25 bytes**. Confira o varint de 1 760 000 000: em grupos de 7 bits, do menos significativo, 0x00, 0x70, 0x1D, 0x47, 0x06; com o bit de continuação nos quatro primeiros, `80 F0 9D C7 06`. E −200 em `sint32`: zigzag = 399 → `8F 03` (2 bytes); em `int32` seriam 10.

**Compatibilidade** (*Updating A Message Type*): acrescentar um campo novo com número novo é seguro (o código antigo **ignora** campos desconhecidos; o novo vê o padrão onde o antigo não mandou). Renomear um campo é seguro no binário. **Nunca** mude o número de um campo nem reutilize o número de um campo apagado: declare `reserved 6;`. Trocar entre `int32`, `uint32`, `int64` e `bool` é compatível no fio; entre `sint32` e `int32`, não (o zigzag muda o significado).

**5. nanopb no ESP32.** O gerador oficial produz C++ com alocação dinâmica; o **nanopb** gera **structs C de tamanho fixo** e um codificador pequeno (alguns kB de flash), próprio para microcontrolador. Strings e repeated precisam de tamanho máximo, dado num arquivo `.options`:

```
Leitura.id max_size:16
```

Gera-se com `nanopb_generator leitura.proto` (do pacote `pip install nanopb`), que cria `leitura.pb.h` (a struct `Leitura` com `char id[16]` e a constante `Leitura_size`, o tamanho máximo codificado) e `leitura.pb.c`. No ESP-IDF, ponha `pb_common.c`, `pb_encode.c`, `pb_decode.c` e os cabeçalhos num componente `components/nanopb` e os `.pb.c/.pb.h` no `main`. Executado no PC e compilado no ESP-IDF v5.5 para o ESP32:

```c
/* leitura_nanopb.c — codifica e decodifica a mensagem Leitura com nanopb (o mesmo código roda no ESP32) */
#include <stdio.h>
#include <string.h>
#include "pb_decode.h"
#include "pb_encode.h"
#include "leitura.pb.h"

/* Codifica em buf; devolve o número de bytes ou 0 em erro. */
size_t leitura_codificar(const char *id, uint32_t ts, int32_t t_centi, uint32_t umidade,
                         uint32_t bat_mv, uint8_t *buf, size_t max)
{
    Leitura m = Leitura_init_zero;
    strncpy(m.id, id, sizeof m.id - 1);               /* id: char[16] por causa do max_size */
    m.ts = ts;
    m.t_centi = t_centi;
    m.umidade = umidade;
    m.bat_mv = bat_mv;
    pb_ostream_t s = pb_ostream_from_buffer(buf, max);
    if (!pb_encode(&s, Leitura_fields, &m)) {
        fprintf(stderr, "pb_encode: %s\n", PB_GET_ERROR(&s));
        return 0;
    }
    return s.bytes_written;
}

/* Decodifica; devolve false se os bytes estiverem corrompidos ou truncados. */
bool leitura_decodificar(const uint8_t *buf, size_t n, Leitura *m)
{
    *m = (Leitura)Leitura_init_zero;
    pb_istream_t s = pb_istream_from_buffer(buf, n);
    return pb_decode(&s, Leitura_fields, m);
}

#ifndef ESP_PLATFORM
int main(void)
{
    uint8_t buf[Leitura_size];                        /* o gerador calcula o tamanho máximo */
    size_t n = leitura_codificar("forja-001", 1760000000u, 2350, 61, 3712, buf, sizeof buf);
    printf("Leitura_size (máximo) = %d B; codificada = %zu B:", Leitura_size, n);
    for (size_t i = 0; i < n; i++) printf(" %02x", buf[i]);
    printf("\n");

    Leitura m;
    if (leitura_decodificar(buf, n, &m))
        printf("id=%s ts=%u t=%.2f °C u=%u%% bat=%u mV\n", m.id, (unsigned)m.ts,
               m.t_centi / 100.0, (unsigned)m.umidade, (unsigned)m.bat_mv);
    for (size_t corte = n - 1; corte >= n - 3; corte -= 2) {   /* o que acontece com bytes faltando? */
        bool ok = leitura_decodificar(buf, corte, &m);
        printf("truncada em %zu B: %s", corte, ok ? "aceita" : "recusada");
        if (ok) printf(", bat=%u mV", (unsigned)m.bat_mv);
        printf("\n");
    }
    return 0;
}
#endif
```

Saída (os 25 bytes são idênticos aos do `protobuf` oficial em Python):

```
Leitura_size (máximo) = 41 B; codificada = 25 B: 0a 09 66 6f 72 6a 61 2d 30 30 31 10 80 f0 9d c7 06 18 dc 24 20 3d 28 80 1d
id=forja-001 ts=1760000000 t=23.50 °C u=61% bat=3712 mV
truncada em 24 B: recusada
truncada em 22 B: aceita, bat=0 mV
```

A última linha é a lição: cortada **no meio** de um varint, a mensagem é recusada; cortada **na fronteira** de um campo, ela é **aceita** com `bat_mv = 0`, porque, para o Protobuf, campo ausente é campo com valor padrão. O Protobuf **não delimita** a mensagem nem detecta corrupção: quem faz isso é o transporte (o comprimento do PUBLISH no MQTT, o Content-Length no HTTP) ou um CRC seu. O `Leitura_size` = 41 é o pior caso (id de 15 caracteres, cada inteiro com varint de 5 bytes): é o tamanho do buffer que você reserva.

**6. A comparação de verdade.** O script que gerou a tabela da seção 1 (com o `leitura_pb2.py` gerado por `python -m grpc_tools.protoc -I. --python_out=. leitura.proto`):

```python
"""comparar.py — o mesmo payload em JSON, CBOR, Protobuf e struct binária."""
import json, struct
import cbor2
import leitura_pb2

dado = {"id": "forja-001", "ts": 1760000000, "t": 23.5, "u": 61, "bat": 3712}

js = json.dumps(dado, separators=(",", ":")).encode()
cb = cbor2.dumps(dado, canonical=True)               # determinístico: menor forma de cada valor
cb_ik = cbor2.dumps({1: "forja-001", 2: 1760000000, 3: 23.5, 4: 61, 5: 3712}, canonical=True)
pb = leitura_pb2.Leitura(id="forja-001", ts=1760000000, t_centi=2350, umidade=61, bat_mv=3712).SerializeToString()
st = struct.pack("<9sIhBH", b"forja-001", 1760000000, 2350, 61, 3712)   # little-endian, sem preenchimento

for nome, b in [("JSON compacto", js), ("CBOR, chaves texto", cb), ("CBOR, chaves inteiras", cb_ik),
                ("Protobuf", pb), ("struct empacotada", st)]:
    print(f"{nome:22s} {len(b):3d} B  {b.hex(' ')}")
```

```
JSON compacto           61 B  7b 22 69 64 22 3a 22 66 6f 72 6a 61 2d 30 30 31 22 2c 22 74 73 ...
CBOR, chaves texto      38 B  a5 61 74 f9 4d e0 61 75 18 3d 62 69 64 69 66 6f 72 6a 61 ...
CBOR, chaves inteiras   29 B  a5 01 69 66 6f 72 6a 61 2d 30 30 31 02 1a 68 e7 78 00 03 f9 4d e0 ...
Protobuf                25 B  0a 09 66 6f 72 6a 61 2d 30 30 31 10 80 f0 9d c7 06 18 dc 24 20 3d 28 80 1d
```

A struct: 9 bytes de id + 4 de ts + 2 de temperatura (int16) + 1 de umidade + 2 de bateria = **18 bytes**, mas só porque o Python não insere **preenchimento**. Em C, `struct { char id[9]; uint32_t ts; int16_t t; uint8_t u; uint16_t bat; }` tem 24 bytes no ESP32 por causa do alinhamento, a não ser que você use `__attribute__((packed))` ou serialize campo a campo. E a ordem dos bytes (little-endian no ESP32) precisa estar documentada para quem decodifica.

**Exemplo resolvido 3 (volume mensal).** Uma leitura por minuto durante 30 dias: 60 × 24 × 30 = 43 200 mensagens. Só de payload: JSON 61 × 43 200 = 2 635 200 B ≈ **2,64 MB**; Protobuf 25 × 43 200 = 1 080 000 B ≈ **1,08 MB**. Por dispositivo, a diferença é pequena num Wi-Fi; numa frota de 10 000 aparelhos em plano celular cobrado por MB, ou num enlace LoRaWAN com 51 bytes de payload máximo, é a diferença entre caber e não caber. Lembre também que o cabeçalho do protocolo (T01, T02) pode pesar mais que a diferença entre formatos.

**7. Como escolher.**
- **Wi-Fi ou Ethernet, poucas mensagens, integração web**: JSON. A legibilidade e as ferramentas compensam os bytes. Use nomes curtos e inteiros escalados.
- **Enlace caro ou pequeno** (NB-IoT, LTE-M, satélite) **com esquema que evolui**: Protobuf (nanopb) ou CBOR com chaves inteiras e um esquema documentado em CDDL.
- **CoAP** (T03): CBOR é o formato natural (Content-Format 60, `application/cbor`).
- **LoRaWAN, Sigfox, BLE com MTU pequeno**: bytes empacotados com campo de versão no primeiro byte e um decodificador do lado da nuvem (como o *payload formatter* do M1.9.T05).
- **Do lado da nuvem**, o formato do dispositivo pode ser convertido: o dispositivo manda Protobuf, uma regra (T06, T07) decodifica e grava JSON ou line protocol (T08).
- Sempre: **um campo ou tópico de versão**, inteiros em unidades pequenas em vez de float e testes que decodificam mensagens da versão anterior.

## Armadilhas comuns
- Esquecer `cJSON_Delete` (ou liberar um nó filho e depois a raiz): vazamento ou liberação dupla.
- Usar `valueint` sem antes conferir `cJSON_IsNumber`: um `"30"` vira 0.
- Mandar `float` direto para o cJSON e ver `23.100000381469727` no broker.
- Inteiros acima de 2^53 em JSON (contadores de 64 bits, IDs): o outro lado, em JavaScript, perde precisão. Mande como string.
- Mandar binário em JSON como base64 sem pensar no +33%.
- Usar `int32` para valores negativos no Protobuf (10 bytes) em vez de `sint32`.
- Reutilizar ou trocar números de campo no `.proto`.
- Achar que o Protobuf detecta mensagem truncada ou corrompida.
- Mandar uma `struct` C com `memcpy` sem `packed`, sem fixar a ordem dos bytes e sem versão.
- Escolher o formato só pelo tamanho e descobrir que ninguém na nuvem consegue ler.
- CBOR não determinístico quando a mensagem vai ser assinada ou comparada por hash.

## Gabarito
1. `{"id":"forja-002","t":-3.5,"u":88}` = 34 bytes. Com `indent=2`: 5 linhas (4 quebras de linha), 2 espaços antes de cada campo e um espaço depois de cada dois-pontos: 47 bytes.
2. `00`, `17`, `18 18`, `18 FF`, `19 01 00`, `1A 00 01 00 00`, `20`, `37`, `38 18`, `63 6F 6C 61`, `83 01 02 03`, `F5`, `F6`.
3. Mapa de 2 pares: `"a"` → 1, `"b"` → [2, 3]. Em JSON: `{"a":1,"b":[2,3]}`.
4. `10 AC 02` (campo 2, 300 = 0x12C → AC 02) e `18 01` (campo 3, zigzag(−1) = 1). Total: 5 bytes. Campos vazios e zerados não viajam.
5. `int32` negativo é estendido para 64 bits em complemento de dois, e o varint de um número com o bit 63 ligado ocupa 10 bytes. O zigzag do `sint32` leva −1 a 1, que ocupa 1 byte.
6. O servidor antigo ignora o campo 6 (campo desconhecido) e continua funcionando. O novo, recebendo mensagem antiga, vê `rssi = 0` (padrão): se 0 for um valor possível, declare `optional` para distinguir "ausente".
7. Mensagens antigas com umidade no campo 4 serão lidas como pressão: dado errado sem nenhum erro. O correto era `reserved 4;` e um número novo para `pressao`.
8. Um objeto de 5 campos: no PC de 64 bits, 6 nós de 64 bytes mais as strings dos nomes e do id, 408 bytes por chamada (medidos com o contador de alocações); com uma leitura por minuto, o heap do ESP32 acaba em horas ou dias, conforme o que estiver livre.
9. 2 000 × 12 × 24 × 30 = 17 280 000 mensagens por mês. JSON: 1,054 GB; Protobuf: 0,432 GB (só payload, sem cabeçalhos do protocolo).
10. Os 22 primeiros bytes terminam exatamente depois do campo 4; o campo 5 ausente vira o padrão 0. Detecção: o transporte delimitar a mensagem e o receptor conferir o tamanho esperado (ou o *Message framing* do nanopb com prefixo de comprimento), um CRC-16/32 no fim do payload, ou declarar o campo `optional` e tratar "ausente" como erro.
