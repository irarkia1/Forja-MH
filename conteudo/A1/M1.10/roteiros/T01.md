# M1.10.T01 — HTTP e REST

> O M1.9 levou o byte até o outro lado: IP, TCP, UDP, TLS. Falta combinar **o que** se diz. O HTTP é o protocolo de aplicação mais usado do mundo e você já o usou sem olhar por dentro: a OTA do M1.6.T09 baixou a imagem com um `GET` por HTTPS. ## Resumo
**1. A mensagem HTTP.** O HTTP/1.1 é **texto** sobre TCP (porta 80) ou sobre TLS (HTTPS, porta 443). Uma troca é sempre **requisição → resposta**, iniciada pelo cliente:

```
POST /v1/dispositivos/forja-001/leituras HTTP/1.1      ← linha de requisição: método, alvo, versão
Host: 192.168.0.10:8080                                 ← cabeçalhos (campos): nome: valor
User-Agent: ESP32 HTTP Client/1.0
Content-Type: application/json
Authorization: Bearer troque-este-token
Content-Length: 17
                                                        ← linha vazia (CRLF CRLF) separa o corpo
{"t":23.5,"u":61}                                       ← corpo (a representação)
```

```
HTTP/1.1 201 Created                                    ← linha de status: versão, código, frase
Server: BaseHTTP/0.6 Python/3.13.3
Date: Fri, 09 Oct 2026 19:29:18 GMT
Content-Type: application/json
Content-Length: 7
Location: /v1/dispositivos/forja-001/leituras/1

{"n":1}
```

Pontos que pegam quem escreve firmware:
- As linhas terminam em **CRLF** (`\r\n`), e o fim dos cabeçalhos é uma linha vazia. Nomes de campo **não** diferenciam maiúsculas.
- `Host` é obrigatório no HTTP/1.1: o mesmo IP serve vários sites.
- O tamanho do corpo vem de **Content-Length** ou de **Transfer-Encoding: chunked** (pedaços com tamanho em hexadecimal, terminados por um pedaço de tamanho 0). Sem um dos dois, o corpo vai até o fechamento da conexão.
- **Conexão persistente** (*Persistence*, RFC 9112): no HTTP/1.1 a conexão TCP fica aberta para as próximas requisições, salvo `Connection: close`. Reaproveitar a conexão economiza o handshake TCP e, principalmente, o TLS.
- **HTTP/2** (RFC 9113) mantém a semântica e muda o transporte: quadros **binários**, várias requisições **multiplexadas** na mesma conexão e cabeçalhos comprimidos (HPACK). **HTTP/3** (RFC 9114) leva isso para o **QUIC**, sobre UDP. Métodos, status e cabeçalhos são os mesmos nas três versões: por isso a RFC 9110 é separada das que descrevem o formato.

**2. Métodos e suas propriedades** (*Common Method Properties*). Três propriedades decidem o que um intermediário, uma biblioteca ou o seu firmware podem fazer sozinhos:
- **Seguro** (*safe*): o cliente não pede mudança de estado no servidor. Um robô de busca, um proxy ou uma pré-busca podem chamá-lo à vontade.
- **Idempotente**: repetir a mesma requisição N vezes tem o **mesmo efeito pretendido** que fazê-la uma vez. É o que permite **repetir depois de uma falha** sem saber se a primeira chegou. A resposta pode mudar (o segundo `DELETE` pode dar 404); o estado final não.
- **Cacheável**: a resposta pode ser guardada e reutilizada.

| Método | Uso | Seguro | Idempotente | Cacheável |
|---|---|---|---|---|
| GET | ler a representação de um recurso | sim | sim | sim |
| HEAD | como GET, só cabeçalhos | sim | sim | sim |
| OPTIONS | quais métodos e opções o alvo aceita | sim | sim | não |
| POST | processar o corpo conforme a semântica do recurso (criar item numa coleção, disparar ação) | não | **não** | só com informação explícita de validade (raro) |
| PUT | **substituir** o estado do recurso pelo corpo | não | sim | não |
| DELETE | remover o recurso | não | sim | não |
| PATCH (RFC 5789) | aplicar uma **alteração parcial** | não | não, em geral | não |

Todo método seguro é idempotente; o contrário não vale. A consequência prática está na seção 6: um `PUT` que deu tempo esgotado pode ser repetido; um `POST`, não, a menos que o servidor saiba reconhecer a repetição.

**3. Códigos de status** (*Status Codes*). O primeiro dígito é a classe: **1xx** informativo, **2xx** sucesso, **3xx** redirecionamento, **4xx** erro do **cliente** (repetir igual não adianta), **5xx** erro do **servidor** (repetir mais tarde pode adiantar). Os que uma API de dispositivos usa:

| Código | Quando | O firmware faz |
|---|---|---|
| 200 OK | sucesso com corpo | usa o corpo |
| 201 Created | POST criou um recurso (`Location` aponta para ele) | segue |
| 204 No Content | sucesso sem corpo (um PUT ou DELETE) | segue |
| 304 Not Modified | GET condicional: a cópia que você tem ainda vale | usa a cópia local |
| 400 Bad Request | sintaxe errada (JSON malformado) | registra, **não repete** |
| 401 Unauthorized | sem credencial ou credencial inválida (vem com `WWW-Authenticate`) | renova o token; não insiste |
| 403 Forbidden | autenticado, mas sem permissão | não repete |
| 404 Not Found | recurso não existe | não repete |
| 409 Conflict | conflito com o estado atual | relê e decide |
| 412 Precondition Failed | `If-Match` não confere: alguém mudou o recurso | relê e reaplica |
| 413 Content Too Large / 415 Unsupported Media Type | corpo grande demais / tipo errado | corrige, não repete |
| 422 Unprocessable Content | JSON válido, conteúdo inválido (campo faltando, fora da faixa) | não repete |
| 429 Too Many Requests (RFC 6585) | limite de taxa | espera (`Retry-After`) e repete |
| 500, 502, 503, 504 | erro interno, proxy sem resposta da origem, serviço indisponível, tempo esgotado no proxy | **repete com recuo** |

Algumas respostas são **cacheáveis por padrão**, sem cabeçalho explícito (200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414 e 501); controle isso com `Cache-Control`.

**4. REST para dispositivos.** REST (Fielding, cap. 5) não é um protocolo: é um **estilo** com restrições — cliente-servidor, **sem estado** (cada requisição traz tudo o que o servidor precisa, inclusive a credencial), respostas que dizem se são cacheáveis, **interface uniforme** (recursos identificados por URI e manipulados por representações com os mesmos métodos) e sistema em camadas (proxies e caches no meio sem o cliente saber). Na prática, uma API "REST" de IoT é:
- **Recursos são substantivos**; o método é o verbo: `GET /v1/dispositivos/forja-001`, não `GET /lerDispositivo?id=forja-001`. Coleções no plural; um item, pelo identificador.
- **Ações que não cabem num substantivo** viram um recurso de "comando": `POST /v1/dispositivos/forja-001/comandos` com `{"acao":"reiniciar"}`, que devolve `202 Accepted` e um `Location` para acompanhar.
- **Versão no caminho** (`/v1/`): o firmware em campo não se atualiza quando a API muda; a v1 tem de continuar no ar enquanto houver aparelho que a use.
- **Paginação** em coleções que crescem: `?limite=50&depois=<cursor>`. Nunca devolva "todas as leituras".
- **Erros com corpo padronizado**: o *Problem Details* da RFC 9457 (`application/problem+json` com `type`, `title`, `status`, `detail`).
- **Autenticação por token**: `Authorization: Bearer <token>` (RFC 6750), **um token por dispositivo** (revogável sozinho), sempre sobre TLS. Senha no URL acaba em log de proxy.
- **PUT × PATCH × POST**: PUT substitui o recurso inteiro (campo omitido = campo apagado ou valor padrão) e é idempotente; PATCH muda só os campos enviados; POST cria um item numa coleção (o servidor escolhe o identificador) ou dispara um processamento.

**5. Concorrência com ETag** (*Conditional Requests*). O servidor manda um **ETag** (uma etiqueta da versão da representação). O cliente pode:
- **Economizar banda** num GET: `If-None-Match: "<etag>"`. Se nada mudou, a resposta é **304** sem corpo. Um dispositivo que consulta a configuração a cada hora baixa o JSON só quando ela muda.
- **Evitar atualização perdida** num PUT/PATCH: `If-Match: "<etag>"`. Se outro cliente alterou o recurso depois da sua leitura, a resposta é **412** e nada é gravado. Sem isso, o aplicativo do técnico e o painel de administração sobrescrevem um ao outro.

**Exemplo resolvido 1 (classificar).** Um app pede `DELETE /v1/dispositivos/forja-007` e a conexão cai antes da resposta. Pode repetir? Sim: DELETE é idempotente; a segunda chamada pode responder 404, mas o estado final (aparelho removido) é o mesmo. E `POST /v1/dispositivos/forja-007/leituras`? Repetir pode gravar a leitura **duas vezes**: o POST não é idempotente. Solução da seção 6: o cliente manda um identificador único da leitura (número de sequência ou cabeçalho `Idempotency-Key`, proposto num rascunho do grupo HTTPAPI da IETF) e o servidor descarta o que já viu.

**6. Uma API de teste no PC.** Para treinar sem nuvem, uma API mínima em Python, só com a biblioteca padrão, com token, ETag, `If-None-Match`, `If-Match`, 201 com `Location`, 401, 412, 415 e 422 em *Problem Details* (executada com Python 3.13):

```python
#!/usr/bin/env python3
"""api_forja.py — API REST mínima de dispositivos (só biblioteca padrão)."""
import hashlib, json, re, threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

TOKEN = "troque-este-token"                    # num produto: um token por cliente, fora do código
dispositivos = {"forja-001": {"id": "forja-001", "intervalo_s": 60, "rele": False}}
leituras = {"forja-001": []}
trava = threading.Lock()

def etag(obj):
    return '"' + hashlib.sha256(json.dumps(obj, sort_keys=True).encode()).hexdigest()[:16] + '"'

class Api(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"              # conexões persistentes

    def responder(self, status, corpo=None, extra=None):
        dados = b"" if corpo is None else json.dumps(corpo, separators=(",", ":"), ensure_ascii=False).encode()
        self.send_response(status)
        if corpo is not None:
            ct = "application/problem+json" if status >= 400 else "application/json"
            self.send_header("Content-Type", ct)
        self.send_header("Content-Length", str(len(dados)))
        for k, v in (extra or {}).items():
            self.send_header(k, v)
        self.end_headers()
        if self.command != "HEAD":
            self.wfile.write(dados)

    def erro(self, status, titulo):
        self.responder(status, {"type": "about:blank", "title": titulo, "status": status})

    def autorizado(self):
        if self.headers.get("Authorization") == f"Bearer {TOKEN}":
            return True
        self.responder(401, {"type": "about:blank", "title": "token ausente ou inválido", "status": 401},
                       {"WWW-Authenticate": 'Bearer realm="forja"'})
        return False

    def corpo_json(self):
        n = int(self.headers.get("Content-Length", 0))
        if n > 4096:
            self.erro(413, "corpo grande demais"); return None
        if not self.headers.get("Content-Type", "").startswith("application/json"):
            self.erro(415, "use application/json"); return None
        try:
            return json.loads(self.rfile.read(n))
        except json.JSONDecodeError:
            self.erro(400, "JSON malformado"); return None

    def do_GET(self):
        if not self.autorizado(): return
        m = re.fullmatch(r"/v1/dispositivos/([\w-]+)(/leituras)?(?:\?limite=(\d+))?", self.path)
        if not m or m[1] not in dispositivos:
            return self.erro(404, "recurso não existe")
        with trava:
            if m[2]:
                lim = min(int(m[3] or 10), 100)
                return self.responder(200, leituras[m[1]][-lim:])
            d = dispositivos[m[1]]
            tag = etag(d)
            if self.headers.get("If-None-Match") == tag:
                return self.responder(304, None, {"ETag": tag})
            self.responder(200, d, {"ETag": tag, "Cache-Control": "no-cache"})

    def do_POST(self):                          # cria uma leitura: não idempotente
        if not self.autorizado(): return
        m = re.fullmatch(r"/v1/dispositivos/([\w-]+)/leituras", self.path)
        if not m or m[1] not in dispositivos:
            return self.erro(404, "recurso não existe")
        c = self.corpo_json()
        if c is None: return
        if not isinstance(c.get("t"), (int, float)):
            return self.erro(422, "campo t (número) obrigatório")
        with trava:
            leituras[m[1]].append(c)
            n = len(leituras[m[1]])
        self.responder(201, {"n": n}, {"Location": f"/v1/dispositivos/{m[1]}/leituras/{n}"})

    def do_PATCH(self):                         # altera parte da configuração
        if not self.autorizado(): return
        m = re.fullmatch(r"/v1/dispositivos/([\w-]+)", self.path)
        if not m or m[1] not in dispositivos:
            return self.erro(404, "recurso não existe")
        c = self.corpo_json()
        if c is None: return
        with trava:
            d = dispositivos[m[1]]
            if_match = self.headers.get("If-Match")
            if if_match and if_match != etag(d):
                return self.erro(412, "configuração mudou desde a sua leitura")
            permitidos = {"intervalo_s": int, "rele": bool}
            for k, v in c.items():
                if k not in permitidos or not isinstance(v, permitidos[k]):
                    return self.erro(422, f"campo {k} inválido")
            d.update(c)
            self.responder(200, d, {"ETag": etag(d)})

    def log_message(self, fmt, *args):
        print(f"{self.command} {self.path} -> {args[1] if len(args) > 1 else ''}")

if __name__ == "__main__":
    ThreadingHTTPServer(("0.0.0.0", 8080), Api).serve_forever()
```

**7. O cliente no ESP32.** O `esp_http_client` faz HTTP e HTTPS; com `crt_bundle_attach = esp_crt_bundle_attach`, confere o certificado do servidor contra o pacote de CAs do ESP-IDF (M1.9.T09). Três decisões que separam o firmware de bancada do firmware de campo:
- **Tempo limite** sempre (`timeout_ms`): sem ele, uma rede que aceita a conexão e não responde trava a tarefa.
- **Repetir só o que é transitório**: sem resposta, 408, 429 e 5xx. Um 400, 401, 403, 404 ou 422 não vai mudar repetindo; repetir em laço é negação de serviço contra o próprio servidor.
- **Recuo exponencial com sorteio** (*backoff* com *jitter*): 1, 2, 4, 8 s… até um teto, mais um atraso aleatório. Sem o sorteio, mil dispositivos que perderam a rede no mesmo apagão voltam **no mesmo segundo** e derrubam o servidor que acabou de voltar.

Compilado no ESP-IDF v5.5 para o ESP32 (a conexão Wi-Fi vem do M1.6.T04):

```c
/* cliente_rest.c — envia uma leitura por HTTPS com esp_http_client: tempo limite,
 * verificação do servidor, tratamento do status e novas tentativas com recuo exponencial */
#include <inttypes.h>
#include <stdbool.h>
#include <stdio.h>
#include <string.h>
#include "esp_crt_bundle.h"
#include "esp_http_client.h"
#include "esp_log.h"
#include "esp_random.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

static const char *TAG = "rest";

#define URL_LEITURAS "https://api.exemplo.com.br/v1/dispositivos/forja-001/leituras"
#define TOKEN        "Bearer troque-este-token"   /* num produto: lido da NVS, um por dispositivo */

/* Faz um POST e devolve o status HTTP, ou -1 se não houve resposta (DNS, TCP, TLS, tempo). */
static int postar_json(const char *url, const char *json, const char *chave_idem,
                       char *resp, size_t max_resp)
{
    esp_http_client_config_t cfg = {
        .url = url,
        .method = HTTP_METHOD_POST,
        .timeout_ms = 5000,                          /* vale para conectar e para cada leitura */
        .crt_bundle_attach = esp_crt_bundle_attach,  /* confere o certificado do servidor */
    };
    esp_http_client_handle_t c = esp_http_client_init(&cfg);
    if (c == NULL) return -1;
    esp_http_client_set_header(c, "Content-Type", "application/json");
    esp_http_client_set_header(c, "Authorization", TOKEN);
    esp_http_client_set_header(c, "Idempotency-Key", chave_idem);  /* o servidor descarta repetições */

    int status = -1;
    int n = (int)strlen(json);
    resp[0] = '\0';
    if (esp_http_client_open(c, n) == ESP_OK) {
        if (esp_http_client_write(c, json, n) == n && esp_http_client_fetch_headers(c) >= 0) {
            status = esp_http_client_get_status_code(c);
            int lidos = esp_http_client_read_response(c, resp, (int)max_resp - 1);
            resp[lidos > 0 ? lidos : 0] = '\0';
        }
    }
    esp_http_client_close(c);
    esp_http_client_cleanup(c);
    return status;
}

/* Vale a pena repetir? Só falhas transitórias. 4xx (exceto 408 e 429) não melhora repetindo. */
static bool transitorio(int status)
{
    return status < 0 || status == 408 || status == 429 || status >= 500;
}

/* Envia uma leitura com até 5 tentativas; espera 1, 2, 4, 8 s (teto de 30 s) mais um sorteio
 * de até 1 s, para que mil aparelhos que caíram juntos não voltem todos no mesmo instante. */
bool enviar_leitura(uint32_t seq, float temperatura, int umidade)
{
    char corpo[96], chave[24], resp[128];
    snprintf(corpo, sizeof corpo, "{\"seq\":%" PRIu32 ",\"t\":%.1f,\"u\":%d}", seq, temperatura, umidade);
    snprintf(chave, sizeof chave, "forja-001-%" PRIu32, seq);   /* mesma chave em todas as tentativas */

    uint32_t espera_ms = 1000;
    for (int tentativa = 1; tentativa <= 5; tentativa++) {
        int st = postar_json(URL_LEITURAS, corpo, chave, resp, sizeof resp);
        if (st >= 200 && st < 300) {
            ESP_LOGI(TAG, "seq %" PRIu32 " aceita (%d) %s", seq, st, resp);
            return true;
        }
        if (!transitorio(st)) {
            ESP_LOGE(TAG, "seq %" PRIu32 " recusada (%d) %s: não repito", seq, st, resp);
            return false;
        }
        uint32_t sorteio = esp_random() % 1000;
        ESP_LOGW(TAG, "tentativa %d falhou (%d); nova em %" PRIu32 " ms", tentativa, st, espera_ms + sorteio);
        vTaskDelay(pdMS_TO_TICKS(espera_ms + sorteio));
        espera_ms = espera_ms * 2 > 30000 ? 30000 : espera_ms * 2;
    }
    return false;   /* quem chamou guarda a leitura numa fila local e tenta depois */
}
```

Notas:
- Abrir e fechar o cliente a cada leitura paga TCP + TLS toda vez. Para várias requisições seguidas, mantenha o `esp_http_client_handle_t` e chame `esp_http_client_perform()` de novo: o componente reaproveita a conexão (*Persistent Connections*).
- O `esp_http_client_open()` + `write()` + `fetch_headers()` + `read_response()` é a API de fluxo (*HTTP Stream*): serve para corpos grandes que não cabem na RAM (um firmware, um log). Para corpos pequenos, `esp_http_client_set_post_field()` + `esp_http_client_perform()` com um tratador de eventos é mais curto.
- O token sai da NVS, não do código: o mesmo binário vai para mil aparelhos.

**8. O servidor no ESP32.** O `esp_http_server` (já usado no M1.6.T04 para a página do AP) serve uma API local, útil para configuração na instalação ou integração na rede da casa. Rotas por URI e método; o corpo é lido com `httpd_req_recv` em laço, porque pode chegar em pedaços; o JSON é analisado com o cJSON (o T05 aprofunda) e **validado inteiro antes de aplicar** (compilado no ESP-IDF v5.5):

```c
/* servidor_rest.c — API REST local no ESP32 com esp_http_server:
 * GET /v1/estado e PATCH /v1/config (corpo JSON analisado com cJSON) */
#include <stdbool.h>
#include <stdio.h>
#include "cJSON.h"
#include "esp_http_server.h"
#include "esp_log.h"
#include "esp_timer.h"

static const char *TAG = "api";
static int intervalo_s = 60;
static bool rele = false;

static esp_err_t enviar_json(httpd_req_t *req, const char *status, const char *json)
{
    httpd_resp_set_status(req, status);
    httpd_resp_set_type(req, "application/json");
    return httpd_resp_sendstr(req, json);
}

static esp_err_t get_estado(httpd_req_t *req)
{
    char json[128];
    snprintf(json, sizeof json, "{\"uptime_s\":%lld,\"intervalo_s\":%d,\"rele\":%s}",
             esp_timer_get_time() / 1000000, intervalo_s, rele ? "true" : "false");
    return enviar_json(req, "200 OK", json);
}

static esp_err_t patch_config(httpd_req_t *req)
{
    char buf[128];
    if (req->content_len == 0 || req->content_len >= sizeof buf)
        return enviar_json(req, "413 Content Too Large", "{\"erro\":\"corpo vazio ou grande demais\"}");
    int lidos = 0;
    while (lidos < (int)req->content_len) {                    /* o corpo pode chegar em pedaços */
        int r = httpd_req_recv(req, buf + lidos, req->content_len - lidos);
        if (r == HTTPD_SOCK_ERR_TIMEOUT) continue;
        if (r <= 0) return ESP_FAIL;                            /* conexão caiu: o servidor fecha */
        lidos += r;
    }
    buf[lidos] = '\0';

    cJSON *raiz = cJSON_Parse(buf);
    if (raiz == NULL) return enviar_json(req, "400 Bad Request", "{\"erro\":\"JSON malformado\"}");
    const cJSON *iv = cJSON_GetObjectItemCaseSensitive(raiz, "intervalo_s");
    const cJSON *rl = cJSON_GetObjectItemCaseSensitive(raiz, "rele");
    bool ok = (iv == NULL || (cJSON_IsNumber(iv) && iv->valueint >= 10 && iv->valueint <= 3600))
           && (rl == NULL || cJSON_IsBool(rl)) && (iv != NULL || rl != NULL);
    if (ok) {                                                   /* valida tudo antes de aplicar */
        if (iv) intervalo_s = iv->valueint;
        if (rl) rele = cJSON_IsTrue(rl);
    }
    cJSON_Delete(raiz);
    if (!ok) return enviar_json(req, "422 Unprocessable Content", "{\"erro\":\"campos inválidos\"}");
    ESP_LOGI(TAG, "config: intervalo %d s, relé %d", intervalo_s, rele);
    return get_estado(req);                                     /* devolve o estado novo */
}

httpd_handle_t api_iniciar(void)
{
    httpd_config_t cfg = HTTPD_DEFAULT_CONFIG();               /* porta 80, até 7 sockets */
    httpd_handle_t srv = NULL;
    if (httpd_start(&srv, &cfg) != ESP_OK) return NULL;
    const httpd_uri_t rotas[] = {
        { .uri = "/v1/estado", .method = HTTP_GET,   .handler = get_estado },
        { .uri = "/v1/config", .method = HTTP_PATCH, .handler = patch_config },
    };
    for (size_t i = 0; i < sizeof rotas / sizeof rotas[0]; i++)
        httpd_register_uri_handler(srv, &rotas[i]);
    return srv;
}
```

Teste da rede local: `curl -i http://<ip-do-esp>/v1/estado` e `curl -i -X PATCH -H 'Content-Type: application/json' -d '{"rele":true}' http://<ip-do-esp>/v1/config`. Esta API não tem autenticação nem TLS: só serve numa rede confiável e com a função desligada fora do modo de instalação. Uma URI sem rota responde 404 e um método não registrado na URI, 405, sozinhos.

**9. Quanto custa o HTTP.** Medido com a API da seção 6 (requisição montada como a do `esp_http_client`, com o mesmo token):

**Exemplo resolvido 2 (overhead).** Corpo `{"t":23.5,"u":61}` = **17 bytes**. Linha de requisição e cabeçalhos = **206 bytes**; requisição inteira = **223 bytes**. Resposta: 197 bytes de linha de status e cabeçalhos + 7 de corpo = **204 bytes**. Na camada de aplicação, só 17 de 427 bytes (ida e volta) são o dado: **4,0%**; contando só a ida, 17/223 = **7,6%**. Somando 40 bytes de IPv4 + TCP por segmento (M1.9.T01), o segmento da requisição tem 263 bytes. Com uma conexão nova por leitura, ainda entram o handshake de três vias, os ACKs e o encerramento (cerca de 8 segmentos de 40 bytes) e, em HTTPS, o handshake TLS, que com a cadeia de certificados passa facilmente de 4 kB.

Por isso:
- HTTP é ótimo para **configuração, comandos esporádicos, OTA, integração com sistemas web** e para dispositivos na tomada.
- Para **telemetria frequente** de um aparelho a bateria, prefira uma conexão persistente com cabeçalho mínimo (MQTT, T02: 2 bytes de cabeçalho fixo) ou UDP (CoAP, T03: 4 bytes).
- Se tiver de usar HTTP, **junte leituras** num POST só (um array a cada 10 minutos em vez de 10 POSTs) e **mantenha a conexão** aberta.

## Pratique
1. Classifique GET, HEAD, POST, PUT, DELETE e PATCH quanto a seguro e idempotente e diga, para cada um, se um cliente pode repetir sozinho depois de um tempo esgotado.

4. Projete as URIs e os métodos de uma API para: listar dispositivos de um cliente, ler e alterar a configuração de um, enviar leituras em lote, pedir a reinicialização e consultar o andamento.

## Armadilhas comuns
- Repetir um POST sem identificador de idempotência e gravar a mesma leitura duas vezes.
- Repetir em laço, sem recuo e sem sorteio, erros 4xx que nunca vão mudar.
- Esquecer o `timeout_ms` e ter uma tarefa travada para sempre numa rede que aceita a conexão e não responde.
- Desligar a verificação do certificado "para funcionar" (`skip_cert_common_name_check`, servidor sem CA) e deixar assim no produto.
- Usar GET para mudar estado (`GET /rele?ligar=1`): proxies, pré-buscas e robôs vão disparar o relé.
- Devolver 200 com `{"erro":...}` no corpo: o cliente e os intermediários não sabem que falhou.
- Token ou senha no URL (`?token=`): vai parar em logs de servidor e de proxy.
- Um token igual em todos os aparelhos: vazou um, vazaram todos.
- Abrir uma conexão HTTPS nova a cada leitura num dispositivo a bateria.
- Ler o corpo com uma só chamada de `httpd_req_recv` e processar meia mensagem.
- Aplicar campo a campo uma configuração recebida e descobrir o erro no terceiro campo, com os dois primeiros já trocados.

## Gabarito
1. Seguros e idempotentes: GET, HEAD. Idempotentes, não seguros: PUT, DELETE. Nem seguros nem idempotentes: POST e, em geral, PATCH. Podem ser repetidos sozinhos: GET, HEAD, PUT, DELETE; POST e PATCH só com identificador de idempotência (ou um PATCH que seja idempotente por construção, como "defina intervalo = 30").
2. PUT substitui: o estado vira `{"intervalo_s":30}` e `rele` some ou volta ao padrão (por isso o PUT exige a representação completa). PATCH: `{"intervalo_s":30,"rele":true}`.
3. 400; 422; 401 (com `WWW-Authenticate`); 403 (ou 404, se nem a existência do dispositivo deve vazar); 503 (ou 500); 429 com `Retry-After`.
4. `GET /v1/clientes/{c}/dispositivos?limite=&depois=`; `GET` e `PATCH /v1/dispositivos/{id}/config` (com ETag); `POST /v1/dispositivos/{id}/leituras` com um array; `POST /v1/dispositivos/{id}/comandos` com `{"acao":"reiniciar"}` → `202 Accepted` e `Location: /v1/dispositivos/{id}/comandos/{n}`; `GET` nesse `Location` para o andamento.
5. 412 Precondition Failed; nada é gravado. O app relê (`GET`, ETag `"b2"`), mostra a mudança ao usuário ou reaplica a sua alteração sobre o estado novo e envia de novo com `If-Match: "b2"`.
6. Uma leitura: 20/200 = 10%. Lote: corpo = 10 × 20 + 9 vírgulas + 2 colchetes = 211 bytes; 211/391 = 54%.
7. Esperas de 1 + 2 + 4 + 8 = 15 s entre a primeira e a quinta tentativa. Com teto de 4 s: 1 + 2 + 4 + 4 = 11 s.
8. 422 diz que o conteúdo é inválido: a mesma requisição vai falhar sempre (o certo é registrar e descartar ou corrigir). 503 é falha temporária do servidor: repetir com recuo (respeitando `Retry-After`, se vier) é o correto.
9. Na segunda requisição, o curl mostra `Re-using existing connection` (o texto exato varia com a versão): não houve novo handshake TCP.
10. O TCP entrega um fluxo de bytes, não mensagens (M1.9.T01): o corpo pode chegar em vários segmentos, e uma chamada devolve só o que já chegou. É preciso ler até completar o `content_len`, tratando o tempo esgotado.
