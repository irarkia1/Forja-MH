# M1.7.T05 — Semáforos e mutex

> Tempo previsto: ~13,6 h — ≈ 5 h de leitura (os capítulos *Interrupt Management* e *Resource Management* do livro do FreeRTOS e a parte de sincronização do Labrosse), ≈ 3 h de exercícios de corrida e de deadlock, ≈ 4 h de prática (corrida medida no simulador POSIX, semáforo dado por uma interrupção de timer no QEMU ou na placa), ≈ 1,5 h de revisão. A fila (T04) leva **dados**. Muitas vezes o que se quer passar é só um **sinal** ("chegou", "terminou", "tem vaga") ou garantir que **só uma tarefa por vez** use um recurso (a UART, o barramento I²C, uma struct de configuração). Para isso existem os semáforos e o mutex, e para entendê-los é preciso ver primeiro o problema que eles resolvem: a condição de corrida.

## Ao final você consegue
- Usar semáforos binários e contadores (xSemaphoreCreateBinary, xSemaphoreCreateCounting, xSemaphoreTake, xSemaphoreGive e xSemaphoreGiveFromISR) para sincronizar tarefas e interrupções e contar eventos ou recursos.
- Identificar condições de corrida e proteger dados compartilhados com seção crítica (taskENTER_CRITICAL), suspensão do escalonador (vTaskSuspendAll) ou mutex, escolhendo o mecanismo pelo custo.
- Usar mutexes, mutexes recursivos e tarefas guardiãs (gatekeeper) e distinguir mutex de semáforo binário quanto a posse, herança de prioridade e uso em ISR.
- Reconhecer e prevenir deadlock (as quatro condições de Coffman, ordem global de aquisição, tempo limite no xSemaphoreTake) e diagnosticá-lo pelo estado das tarefas.

## Resumo
**1. A condição de corrida.** `contador++` parece uma operação, mas no Cortex-M são três instruções: `ldr` (lê), `add`, `str` (escreve). Se uma tarefa for preemptada entre o `ldr` e o `str` e outra incrementar o mesmo contador, um dos incrementos se perde.

**Exemplo 1 (corrida medida).** Duas tarefas de mesma prioridade incrementam 2 000 000 de vezes cada um `volatile uint32_t` compartilhado, no simulador POSIX com time slicing:
```c
static volatile uint32_t ulContador;

static void vIncrementa( void *pv )
{
    for( uint32_t i = 0; i < 2000000UL; i++ ) {
        ulContador++;                              /* ldr / add / str: pode ser interrompido no meio */
    }
    vTaskDelete( NULL );
}
```
| Proteção | Resultado (esperado 4 000 000) |
|---|---|
| nenhuma | **2 334 761** (variou a cada execução) |
| `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()` | 4 000 000 |
| mutex (`xSemaphoreTake` / `xSemaphoreGive`) | 4 000 000 |

`volatile` **não** resolve: ele só obriga o compilador a ler e escrever na memória, não torna a sequência indivisível. Uma corrida assim passa em todos os testes de bancada e aparece em campo uma vez por semana.

Recurso compartilhado é tudo o que duas tarefas (ou uma tarefa e uma ISR) usam: variáveis e structs, um periférico (a UART em que duas tarefas escrevem mensagens que se misturam), funções não reentrantes (`strtok`, muitos `printf` da newlib sem configuração), o barramento I²C com uma transação em andamento.

**2. Três maneiras de proteger, em ordem de custo.**

**(a) Seção crítica.** `taskENTER_CRITICAL()` eleva o BASEPRI até `configMAX_SYSCALL_INTERRUPT_PRIORITY` (T04): nenhuma troca de contexto e nenhuma ISR que use a API pode entrar. Aninha (o kernel conta os níveis). Em ISR, use `taskENTER_CRITICAL_FROM_ISR()` / `taskEXIT_CRITICAL_FROM_ISR(x)`.
- Custo: algumas instruções. Efeito colateral: **aumenta a latência** de todas as interrupções abaixo do limite.
- Use para trechos de **poucos microssegundos**: ler um `uint64_t`, atualizar dois campos coerentes, mexer num registrador compartilhado. Nunca chame a API que bloqueia dentro dela.

**(b) Suspender o escalonador.** `vTaskSuspendAll()` … `xTaskResumeAll()` impede trocas de contexto, mas **deixa as interrupções habilitadas**. Serve para trechos mais longos que só disputam com outras **tarefas** (não com ISRs). Não chame funções da API que possam bloquear nesse intervalo. O próprio heap_4 usa isso no `pvPortMalloc`.

**(c) Mutex.** Só as tarefas que **disputam** o recurso esperam; as outras e todas as ISRs seguem normais. É o mecanismo para trechos longos (uma transação I²C de 2 ms, um `printf`). Custo: chamadas à API e, havendo disputa, trocas de contexto. Detalhes na seção 4.

Alternativas sem bloquear: acesso **atômico** (palavras alinhadas de 32 bits, LDREX/STREX ou `<stdatomic.h>` no M3/M4, M1.4.T04), dados com **um único escritor**, ou a tarefa **guardiã** (seção 5), que elimina o compartilhamento.

**3. Semáforos: sinalizar e contar.**

**Semáforo binário**: uma "ficha" que está ou não está disponível. `xSemaphoreCreateBinary()` cria **vazio**; `xSemaphoreGive` põe a ficha; `xSemaphoreTake(s, tempo)` bloqueia até ela existir e a retira. Uso clássico: uma **ISR avisa uma tarefa** (processamento adiado, T04) sem passar dado.
```c
static SemaphoreHandle_t xSemADC;          /* xSemaphoreCreateBinary(): nasce vazio */

void DMA2_Stream0_IRQHandler( void )       /* fim da conversão de um bloco do ADC por DMA (M1.4.T07) */
{
    BaseType_t xAcordou = pdFALSE;
    if( DMA2->LISR & DMA_LISR_TCIF0 ) {
        DMA2->LIFCR = DMA_LIFCR_CTCIF0;    /* limpa a flag do periférico */
        xSemaphoreGiveFromISR( xSemADC, &xAcordou );
    }
    portYIELD_FROM_ISR( xAcordou );
}

static void vTarefaADC( void *pv )         /* prioridade alta: processamento adiado */
{
    for( ;; ) {
        if( xSemaphoreTake( xSemADC, pdMS_TO_TICKS( 20 ) ) == pdTRUE ) {
            processa_bloco();
        } else {
            /* 20 ms sem conversão: DMA parado? avise o supervisor */
        }
    }
}
```
**Limite do binário**: se a ISR der o semáforo duas vezes antes de a tarefa tomá-lo, **o segundo evento se perde** (a ficha já estava lá). Quando cada evento conta, use um **semáforo contador** (ou uma notificação com contagem, T07), ou processe tudo o que estiver pendente a cada despertar (o livro mostra esse padrão em *Improving the Implementation*).

**Semáforo contador**: `xSemaphoreCreateCounting(uxMaxCount, uxInitialCount)`. Dois usos:
- **Contar eventos**: começa em 0; cada `Give` soma 1 (até o máximo); cada `Take` subtrai 1.
- **Gerenciar recursos**: começa em N (N recursos livres); `Take` pega um, bloqueando se não houver; `Give` devolve. Ex.: 3 buffers de transmissão, 4 conexões de socket.

**Exemplo 2 (binário × contador, no QEMU).** O TIMER0 do `mps2-an385`, a 100 Hz, dá um semáforo binário e um contador (máximo 10) a cada interrupção; a tarefa fica 55 ms sem tomar nenhum dos dois. Resultado observado: o contador acumulou **6** eventos; o binário guardava **1**.

**4. Mutex.** Um mutex (*mutual exclusion*) é um semáforo binário especializado em **proteger recurso**:
```c
static SemaphoreHandle_t xMutexI2C;        /* xSemaphoreCreateMutex(): nasce DISPONÍVEL */

int i2c_le_registrador( uint8_t end, uint8_t reg, uint8_t *v )   /* 0 = ok, negativo = erro */
{
    if( xSemaphoreTake( xMutexI2C, pdMS_TO_TICKS( 50 ) ) != pdTRUE ) {
        return -1;                         /* ocupado: nunca espere para sempre por um barramento */
    }
    int r = i2c_transacao( end, reg, v );  /* START, endereço, registrador, RESTART, leitura, STOP */
    xSemaphoreGive( xMutexI2C );           /* devolva em TODOS os caminhos de saída */
    return r;
}
```

| | Semáforo binário | Mutex |
|---|---|---|
| Criado | vazio | disponível |
| Para | **sinalizar** (um dá, outro toma) | **excluir** (a mesma tarefa toma e devolve) |
| Dono | não tem | a tarefa que tomou (`xSemaphoreGetMutexHolder`) |
| Herança de prioridade | não | **sim** (T06) |
| Em ISR | `GiveFromISR` permitido | **não**: a ISR não é tarefa, não pode ser dona nem herdar prioridade |

**Mutex recursivo** (`xSemaphoreCreateRecursiveMutex`, `xSemaphoreTakeRecursive`, `xSemaphoreGiveRecursive`): a tarefa dona pode tomá-lo de novo (por exemplo, uma função pública que chama outra função pública do mesmo módulo); ele só fica livre depois de tantos `Give` quantos foram os `Take`. Com um mutex **comum**, a mesma tarefa tomando duas vezes **trava em si mesma** — no simulador, o segundo `xSemaphoreTake(xMutex, 0)` da mesma tarefa devolveu `pdFALSE`; com `portMAX_DELAY`, ela ficaria bloqueada para sempre.

**Mutex e escalonamento.** Liberar um mutex que uma tarefa de prioridade maior espera provoca preempção imediata; liberar e tomar de novo em laço apertado, entre tarefas de **mesma** prioridade, pode fazer uma delas nunca conseguir o mutex (ela fica Ready, mas a outra o retoma antes do próximo tick). O livro mostra esse caso em *Mutexes and Task Scheduling*; a solução é ceder (`taskYIELD()`) ou não reter o mutex em laço.

**5. Tarefa guardiã (gatekeeper).** Em vez de um mutex em volta do recurso, **uma única tarefa é dona dele** e as demais lhe mandam pedidos por fila. Sem mutex, sem inversão de prioridade, sem deadlock por esse recurso — e funciona até a partir de ISRs (`xQueueSendFromISR`). É o padrão para a serial de log:
```c
static QueueHandle_t xFilaLog;             /* xQueueCreate( 8, sizeof( char * ) ) */

void log_msg( const char *pcMsg )          /* pcMsg: string constante ou buffer que não muda */
{
    xQueueSend( xFilaLog, &pcMsg, 0 );     /* não bloqueia quem loga; mensagem perdida se cheia */
}

static void vTarefaGuardiaLog( void *pv )  /* a única que toca na UART */
{
    const char *pcMsg;
    for( ;; ) {
        xQueueReceive( xFilaLog, &pcMsg, portMAX_DELAY );
        uart_escreve( pcMsg );
    }
}
```

**6. Deadlock.** Duas tarefas, dois recursos: T1 toma A e espera B; T2 toma B e espera A. Nenhuma avança — o "abraço mortal" (*deadly embrace*). As quatro **condições de Coffman** (todas precisam valer ao mesmo tempo):
1. **exclusão mútua** — o recurso só serve a um por vez;
2. **posse e espera** — quem tem um recurso espera outro sem soltar o primeiro;
3. **sem preempção de recurso** — ninguém tira o recurso de quem o tem;
4. **espera circular** — T1 espera T2, que espera T1 (ou um ciclo maior).

Prevenir = quebrar uma delas:
- **Ordem global de aquisição** (quebra a 4): todos tomam A antes de B, sempre. É a regra mais eficaz; documente a ordem no código.
- **Pegar tudo de uma vez ou nada** (quebra a 2): se não conseguir o segundo com tempo limite, solte o primeiro e tente de novo mais tarde.
- **Tempo limite** em todo `xSemaphoreTake`: não previne, mas **transforma** o deadlock num erro detectável e tratável.
- **Guardiã**: um só dono por recurso (seção 5).

**Exemplo 3 (deadlock detectado por tempo limite).** No simulador, T1 tomou A e T2 tomou B; cada uma pediu o outro. T1 usou tempo limite de 50 ms, desistiu, soltou A — e T2, que esperava A, completou. Com `portMAX_DELAY` nas duas, ambas ficariam bloqueadas para sempre.

**Diagnóstico.** Um deadlock aparece como tarefas **em Blocked para sempre** com a CPU ociosa. `vTaskList()` (T09) mostra o estado de todas as tarefas; `xSemaphoreGetMutexHolder()` diz quem segura cada mutex; um depurador com suporte a FreeRTOS mostra a mesma coisa. A tarefa supervisora do T09 detecta o sintoma porque as tarefas presas param de dar sinal de vida.

## Armadilhas comuns
- Achar que `volatile` torna o acesso atômico.
- Seção crítica longa (laço, `printf`, espera de periférico): latência de interrupção destruída.
- Chamar `xSemaphoreTake` ou `vTaskDelay` dentro de uma seção crítica ou com o escalonador suspenso.
- Usar semáforo binário para exclusão mútua: sem dono e sem herança de prioridade (T06).
- Esquecer o `Give` num caminho de erro (o `return` no meio da função).
- Criar o binário esperando que ele nasça "cheio" (nasce vazio; o mutex nasce disponível).
- `portMAX_DELAY` em todos os `Take`: o deadlock fica invisível.
- Tomar mutexes em ordens diferentes em lugares diferentes do código.
- Dar um mutex em ISR, ou tomar um mutex dentro de um callback de timer de software que bloqueia (T07).

## Gabarito
1. `volatile` só obriga a ler e escrever na memória; a sequência `ldr r1, [r0]` / `adds r1, #1` / `str r1, [r0]` continua podendo ser interrompida entre a leitura e a escrita.
2. Escrita rara e leitura de 40 bytes por tarefas: mutex (ou suspensão do escalonador, se a cópia for rápida). Com leitura também na ISR: seção crítica curta para copiar a struct (a ISR não pode esperar mutex) — ou um esquema de cópia dupla com índice atômico.
3. Vê **1** (o binário guarda uma ficha). Use semáforo contador, notificação como contador (`ulTaskNotifyTake(pdFALSE, …)`, T07) ou uma fila de eventos.
4. `xSemaphoreCreateCounting(4, 4)`: máximo 4, inicial 4 (todos livres).
5. O mutex tem dono e herança de prioridade: a ISR não é uma tarefa, não pode ser dona, não pode ter prioridade herdada nem bloquear esperando.
6. Trava em si mesma: o segundo `Take` espera um mutex que a própria tarefa segura. Soluções: mutex recursivo, ou separar funções internas (que supõem o mutex já tomado) das públicas (que o tomam).
7. T1 tem SPI e espera flash; T2 tem flash e espera SPI: espera circular. Correção: ordem global (sempre SPI antes de flash, nas duas), ou tempo limite com liberação e nova tentativa.
8. Exclusão mútua, posse e espera, sem preempção, espera circular. A guardiã elimina a disputa pelo recurso: só uma tarefa o usa, então não há posse e espera nem ciclo envolvendo esse recurso.
