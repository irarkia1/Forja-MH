# M1.7.T04 — Filas

> Tempo previsto: ~13,6 h — ≈ 5 h de leitura (os capítulos *Queue Management* e *Interrupt Management* do livro do FreeRTOS e a página do port Cortex-M sobre prioridades), ≈ 3 h de exercícios de dimensionamento e de prioridades, ≈ 4 h de prática (filas no simulador POSIX; ISR de UART entregando bytes a uma tarefa no QEMU ou na placa), ≈ 1,5 h de revisão. No superloop, ISR e laço conversam por variáveis `volatile` e flags (M1.2.T05, M1.4.T04); entre tarefas, isso vira corrida (T05). A **fila** é o canal oficial do FreeRTOS: copia os dados, bloqueia quem espera e acorda quem precisa, com tempo limite. Este tópico usa filas entre tarefas e, principalmente, **de uma interrupção para uma tarefa** — o padrão de processamento adiado que todo driver com RTOS segue —, e explica a regra de prioridades que decide quais ISRs podem falar com o kernel.

## Ao final você consegue
- Usar filas do FreeRTOS (xQueueCreate, xQueueSend, xQueueSendToFront, xQueueReceive, xQueuePeek, xQueueOverwrite) com tempos de bloqueio, entendendo a cópia por valor.
- Projetar a comunicação por fila: dimensionar comprimento e tamanho do item, enviar ponteiros com posse definida, identificar a origem das mensagens e escutar várias filas com queue sets.
- Passar dados de uma ISR para uma tarefa com as funções FromISR, pxHigherPriorityTaskWoken e portYIELD_FROM_ISR, aplicando o processamento adiado de interrupções.
- Configurar configKERNEL_INTERRUPT_PRIORITY e configMAX_SYSCALL_INTERRUPT_PRIORITY no Cortex-M e dizer quais ISRs podem chamar a API do kernel e por quê.

## Resumo
**1. A fila do FreeRTOS.** Uma fila guarda um número fixo de itens de tamanho fixo, definidos na criação:
```c
QueueHandle_t xQueueCreate( UBaseType_t uxQueueLength, UBaseType_t uxItemSize );  /* NULL se faltar heap */
```
- **Cópia por valor**: `xQueueSend` copia `uxItemSize` bytes do endereço dado para dentro da fila; `xQueueReceive` copia para o seu buffer. O remetente pode reutilizar a variável logo em seguida, e nenhuma tarefa enxerga a memória da outra. O preço: copiar itens grandes custa tempo e RAM.
- **FIFO**: `xQueueSendToBack` (igual a `xQueueSend`) põe no fim; `xQueueSendToFront` põe na frente (mensagem urgente).
- **Bloqueio na leitura**: `xQueueReceive(q, &x, xTicksToWait)` bloqueia até chegar um item ou o tempo vencer (devolve `pdPASS` ou `pdFAIL`). Com várias tarefas esperando, a de **maior prioridade** recebe primeiro (empate: a que espera há mais tempo).
- **Bloqueio na escrita**: com a fila cheia, `xQueueSend` bloqueia até abrir espaço ou o tempo vencer. Tempo zero = não bloqueia (útil para descartar e contar perdas).
- **Espiar**: `xQueuePeek` lê sem retirar.
- **Caixa postal** (*mailbox*): fila de **1 item** escrita com `xQueueOverwrite` (sobrescreve, nunca bloqueia) e lida com `xQueuePeek` — "o valor mais recente", lido por quantas tarefas quiserem.
- **Custo de RAM**: a estrutura da fila (80 bytes num Cortex-M3 com a configuração do módulo, medido com `sizeof(StaticQueue_t)`) + comprimento × tamanho do item.

**2. Projetar a comunicação.**

**(a) Mensagens com origem.** Um consumidor que recebe de vários produtores precisa saber quem mandou: inclua um campo de origem (ou tipo) na struct.
```c
typedef enum { eSensorTemp, eSensorUmid, eBotao } Origem_t;
typedef struct {
    Origem_t   eOrigem;
    int32_t    lValor;
    TickType_t xQuando;
} Mensagem_t;                                       /* 12 bytes num Cortex-M */

static QueueHandle_t xFilaEventos;                 /* criada no main: xQueueCreate( 5, sizeof( Mensagem_t ) ) */

static void vProdutor( void *pv )
{
    Origem_t eOrig = ( Origem_t ) ( intptr_t ) pv;
    for( ;; ) {
        Mensagem_t m = { eOrig, le_sensor( eOrig ), xTaskGetTickCount() };
        if( xQueueSendToBack( xFilaEventos, &m, pdMS_TO_TICKS( 10 ) ) != pdPASS ) {
            contador_de_perdas++;                   /* fila cheia por 10 ms: o consumidor não está dando conta */
        }
        vTaskDelay( pdMS_TO_TICKS( 100 ) );
    }
}

static void vConsumidor( void *pv )
{
    Mensagem_t m;
    for( ;; ) {
        if( xQueueReceive( xFilaEventos, &m, pdMS_TO_TICKS( 500 ) ) == pdPASS ) {
            switch( m.eOrigem ) { /* trata cada origem */ }
        } else {
            /* 500 ms sem nada: produtores travados? avise o supervisor (T09) */
        }
    }
}
```
(Versão com três produtores e um consumidor executada no simulador POSIX: as nove mensagens chegaram intercaladas na ordem de envio e, depois de 100 ms sem mensagens, o tempo limite foi tratado.)

**(b) Itens grandes: passe o ponteiro, defina a posse.** Para quadros de 512 bytes, copiar o quadro duas vezes é desperdício. A fila leva só o **ponteiro** (`sizeof(uint8_t *)`, 4 bytes no Cortex-M) — e então vale a regra: **quem recebe o ponteiro passa a ser o dono do buffer**; o remetente não toca mais nele.
```c
static QueueHandle_t xFilaQuadros;                 /* xQueueCreate( 4, sizeof( uint8_t * ) ) */

void vEnviaQuadro( void )
{
    uint8_t *pucQuadro = pvPortMalloc( 512 );      /* ou um bloco de um pool fixo (T08) */
    if( pucQuadro == NULL ) return;
    preenche( pucQuadro, 512 );
    if( xQueueSend( xFilaQuadros, &pucQuadro, 0 ) != pdPASS ) {
        vPortFree( pucQuadro );                    /* não entregou: a posse continua aqui */
    }
    /* entregou: daqui em diante, pucQuadro pertence ao receptor */
}

void vRecebeQuadro( void )
{
    uint8_t *pucQuadro;
    if( xQueueReceive( xFilaQuadros, &pucQuadro, portMAX_DELAY ) == pdPASS ) {
        processa( pucQuadro, 512 );
        vPortFree( pucQuadro );                    /* o dono libera (ou devolve ao pool) */
    }
}
```
Num produto, troque `pvPortMalloc` por um **pool de blocos fixos** — por exemplo, uma segunda fila com os ponteiros livres: pegar um bloco é `xQueueReceive` na fila de livres, devolver é `xQueueSend`. Sem fragmentação e com espera limitada.

**(c) Dimensionar a fila.** O comprimento cobre a **rajada** que chega enquanto o consumidor não pode ler: comprimento ≥ taxa de chegada × pior atraso do consumidor (+ margem). Uma fila sempre cheia não é fila pequena: é consumidor lento demais (análise do T03).

**Exemplo 1.** Bytes chegam a 115 200 bit/s (10 bits por byte: um byte a cada 86,8 µs). A tarefa que os consome pode ficar até 5 ms sem rodar (preemptada por tarefas mais prioritárias). Chegam 5000/86,8 = 57,6 → **58 bytes** nesse intervalo: uma fila de **64** bytes. Conte as perdas (`xQueueSendFromISR` falhando) para confirmar em campo.

**(d) Escutar várias filas: queue sets.** Uma tarefa que espera comandos de uma fila e amostras de outra pode bloquear nas duas com um **queue set** (`configUSE_QUEUE_SETS = 1`):
```c
QueueSetHandle_t xSet = xQueueCreateSet( COMPRIMENTO_A + COMPRIMENTO_B );   /* soma dos comprimentos */
xQueueAddToSet( xFilaA, xSet );            /* as filas precisam estar vazias ao entrar no set */
xQueueAddToSet( xFilaB, xSet );
for( ;; ) {
    QueueSetMemberHandle_t xQual = xQueueSelectFromSet( xSet, portMAX_DELAY );
    if( xQual == xFilaA ) { xQueueReceive( xFilaA, &a, 0 ); /* … */ }
    else if( xQual == xFilaB ) { xQueueReceive( xFilaB, &b, 0 ); /* … */ }
}
```
O livro do FreeRTOS lembra que queue sets custam RAM e tempo e que, em geral, **uma fila só com mensagens que carregam a origem** (item a) é mais simples e mais eficiente. Use o set quando as filas vêm de código que você não controla (uma biblioteca que entrega a sua própria fila).

**3. Da ISR para a tarefa.** Uma ISR **não pode bloquear** e não roda numa tarefa, então ela usa as versões **FromISR** da API: `xQueueSendFromISR`, `xQueueReceiveFromISR`, `xSemaphoreGiveFromISR`, `vTaskNotifyGiveFromISR`… Elas nunca bloqueiam e têm um parâmetro a mais, **`pxHigherPriorityTaskWoken`**:
- comece com `pdFALSE`; a função o põe em `pdTRUE` se a operação **desbloqueou uma tarefa de prioridade maior que a interrompida**;
- no fim da ISR, `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)` pende o PendSV se for `pdTRUE`: ao sair da ISR, a tarefa acordada roda **imediatamente**. Sem isso, ela esperaria o próximo tick (até 1 ms de atraso a mais).

**Processamento adiado de interrupção** (*deferred interrupt processing*). A ISR faz o mínimo — ler o dado, limpar a flag do periférico, entregar à tarefa — e o processamento (decodificar o comando, calcular, falar com outros periféricos) fica numa tarefa de **prioridade alta**. Vantagens: a ISR fica curta (latência baixa para as outras), o processamento pode usar toda a API (bloquear, usar mutex) e entra na análise de tempo como qualquer tarefa.

**Exemplo 2 (UART → fila → tarefa no STM32F401).** USART2 a 115 200 bit/s; a ISR entrega cada byte e a tarefa monta linhas:
```c
#include "stm32f4xx.h"
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

static QueueHandle_t xFilaRx;              /* 64 itens de 1 byte (Exemplo 1) */
static volatile uint32_t ulPerdidos;

void USART2_IRQHandler( void )
{
    BaseType_t xAcordouMaisAlta = pdFALSE;
    if( USART2->SR & USART_SR_RXNE ) {
        uint8_t b = ( uint8_t ) USART2->DR;                     /* ler DR limpa o RXNE */
        if( xQueueSendFromISR( xFilaRx, &b, &xAcordouMaisAlta ) != pdPASS ) {
            ulPerdidos++;                                       /* fila cheia: nunca bloquear aqui */
        }
    }
    portYIELD_FROM_ISR( xAcordouMaisAlta );
}

static void vTarefaComandos( void *pv )                         /* prioridade alta */
{
    char linha[ 32 ]; size_t n = 0; uint8_t b;
    for( ;; ) {
        xQueueReceive( xFilaRx, &b, portMAX_DELAY );            /* dorme até chegar byte */
        if( b == '\n' || b == '\r' ) {
            if( n ) { linha[ n ] = '\0'; executa_comando( linha ); n = 0; }
        } else if( n < sizeof linha - 1 ) {
            linha[ n++ ] = ( char ) b;
        }
    }
}

void vComandosInit( void )
{
    xFilaRx = xQueueCreate( 64, sizeof( uint8_t ) );
    configASSERT( xFilaRx != NULL );
    /* … clock, GPIO e BRR da USART2 como no M1.4 … */
    USART2->CR1 |= USART_CR1_RXNEIE;
    NVIC_SetPriority( USART2_IRQn, 6 );    /* 6 ≥ configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY (5): pode usar FromISR */
    NVIC_EnableIRQ( USART2_IRQn );
    xTaskCreate( vTarefaComandos, "cmd", 256, NULL, 3, NULL );
}
```
(O mesmo padrão foi executado no QEMU `mps2-an385`, com a UART CMSDK do modelo no lugar da USART2: as linhas digitadas chegaram à tarefa com zero bytes perdidos. Mudando a prioridade da IRQ para 0, a primeira chamada a `xQueueSendFromISR` disparou o `configASSERT` de `vPortValidateInterruptPriority` — exatamente o erro que a seção 4 explica.)

**Fila por byte é cara.** Cada `xQueueSendFromISR` custa algumas centenas de ciclos: para 115 200 bit/s serve; para 1 Mbit/s ou para rajadas longas, use **DMA circular + IDLE** (M1.4.T06) e entregue **blocos** à tarefa, ou um **stream buffer** (`xStreamBufferSendFromISR`), feito para fluxo de bytes com um único escritor e um único leitor.

**4. Quais ISRs podem chamar o kernel.** O FreeRTOS no Cortex-M3/M4 **não desliga todas as interrupções** nas seções críticas: ele escreve no **BASEPRI** (M1.4.T04) o valor `configMAX_SYSCALL_INTERRUPT_PRIORITY`, mascarando só as interrupções de prioridade **igual ou menos urgente** que esse limite. Daí as duas faixas:

| Prioridade lógica no STM32 (0 = mais urgente) | Mascarada pelo kernel? | Pode chamar a API FromISR? |
|---|---|---|
| 0 … 4 (acima do limite) | **nunca**: latência zero acrescentada pelo RTOS | **não** — o kernel pode estar no meio de uma operação |
| 5 … 15 (de `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` até a mínima) | sim, durante as seções críticas | **sim**, só as funções FromISR |
| 15 (`configKERNEL_INTERRUPT_PRIORITY`) | — | é onde ficam o SysTick e o PendSV |

```c
#define configPRIO_BITS                               4      /* __NVIC_PRIO_BITS do STM32 */
#define configLIBRARY_LOWEST_INTERRUPT_PRIORITY       15
#define configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY  5
#define configKERNEL_INTERRUPT_PRIORITY      ( configLIBRARY_LOWEST_INTERRUPT_PRIORITY << ( 8 - configPRIO_BITS ) )      /* 0xF0 = 240 */
#define configMAX_SYSCALL_INTERRUPT_PRIORITY ( configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY << ( 8 - configPRIO_BITS ) ) /* 0x50 = 80  */
```
Regras práticas:
- As constantes `configKERNEL…` e `configMAX_SYSCALL…` são valores **do byte do registrador** (deslocados para os bits altos); as funções do CMSIS (`NVIC_SetPriority`) recebem o valor **lógico** (5, 6…). Daí as duas versões "LIBRARY".
- `configMAX_SYSCALL_INTERRUPT_PRIORITY` **nunca** pode ser 0 (BASEPRI = 0 não mascara nada).
- Uma IRQ habilitada sem `NVIC_SetPriority` fica com prioridade **0**: a mais urgente, **acima** do limite. Se ela chamar `xQueueSendFromISR`, o kernel se corrompe de forma intermitente. Com `configASSERT` definido, o port confere isso em tempo de execução (`vPortValidateInterruptPriority`).
- O FreeRTOS exige **todos os bits como preempção** (PRIGROUP sem subprioridade; na HAL, `HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_4)`); o port também confere com `configASSERT`.
- Use a faixa acima do limite para o que não tolera nem alguns microssegundos de atraso (comutação de motor, proteção) e que, portanto, **não fala com o kernel** — ela pode, no máximo, pender outra IRQ de prioridade menor que fale.
- No **Cortex-M0/M0+** não há BASEPRI: as seções críticas desligam **todas** as interrupções (PRIMASK) e não existe faixa "acima do kernel".

**Aninhamento.** ISRs de prioridade diferente se aninham normalmente; as que usam a API ficam todas abaixo do limite e são mascaradas juntas durante as seções críticas do kernel, que são curtas.

1. Uma fila de 10 itens de `Mensagem_t` (12 bytes) num Cortex-M3: quantos bytes de heap ela consome, sabendo que a estrutura da fila tem 80 bytes?
2. O consumidor tem prioridade **maior** que o produtor. Quantos itens a fila chega a acumular? E se tiver prioridade menor?
3. Escreva a caixa postal da última temperatura lida (escrita por uma tarefa, lida por três).
4. A 921 600 bit/s, um byte chega a cada quantos µs? Com o consumidor atrasando até 2 ms, de que tamanho precisa a fila? Ainda vale uma fila por byte?
5. O que acontece se a ISR do Exemplo 2 omitir o `portYIELD_FROM_ISR`?
6. Num STM32 com `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`, quais destas IRQs podem chamar `xQueueSendFromISR`: prioridade 2, 5, 9, 15?
7. Calcule `configMAX_SYSCALL_INTERRUPT_PRIORITY` para um MCU com 3 bits de prioridade e limite lógico 2.
8. Por que enviar ponteiros pela fila sem regra de posse é perigoso? Dê um cenário de falha.

## Armadilhas comuns
- Criar a fila com `sizeof(ponteiro)` e enviar a struct (ou o contrário).
- Enviar o endereço de uma variável local que o remetente vai reutilizar logo depois (a fila copia o ponteiro, não o conteúdo).
- Chamar `xQueueSend` (sem FromISR) dentro de uma ISR, ou bloquear numa ISR.
- Esquecer o `portYIELD_FROM_ISR`: funciona, mas com até um tick de atraso a mais.
- Deixar a IRQ com prioridade 0 (padrão) e chamar a API dela.
- Usar o valor deslocado (0x50) em `NVIC_SetPriority`, ou o valor lógico (5) em `configMAX_SYSCALL_INTERRUPT_PRIORITY`.
- `portMAX_DELAY` no `xQueueSend` de um produtor crítico: se o consumidor travar, o produtor trava junto. Prefira tempo limite e contagem de perdas.
- Uma fila por byte em alta velocidade: CPU gasta só com a API.

## Gabarito
1. 80 + 10 × 12 = **200 bytes** (mais o cabeçalho de alocação do heap, T08).
2. Consumidor mais prioritário: assim que um item entra, o consumidor preempta o produtor e o retira — a fila quase nunca passa de **1** item. Consumidor menos prioritário: os itens se acumulam até o produtor bloquear (fila cheia) ou ceder a CPU.
3. `xQueueCreate(1, sizeof(float))`; o produtor faz `xQueueOverwrite(q, &t)`; os leitores fazem `xQueuePeek(q, &t, 0)` (ou com tempo limite, para esperar a primeira leitura).
4. 10 bits / 921 600 bit/s ≈ **10,85 µs**; 2000 / 10,85 ≈ 184 → fila de 256. Uma chamada da API a cada 10 µs come boa parte da CPU: use DMA circular com IDLE ou stream buffer.
5. A tarefa acordada só roda no próximo tick (ou na próxima troca de contexto): latência até um tick maior, sem erro aparente.
6. 5, 9 e 15. A de prioridade 2 está acima do limite (nunca mascarada) e **não** pode.
7. 2 << (8 − 3) = 2 × 32 = **64** (0x40).
8. Se o remetente continuar escrevendo no buffer depois de enviar, o receptor lê dados misturados; se os dois liberarem, há liberação dupla e o heap se corrompe. Exemplo: a tarefa de rede manda o ponteiro do quadro e, logo em seguida, recebe o próximo pacote **no mesmo buffer**.
