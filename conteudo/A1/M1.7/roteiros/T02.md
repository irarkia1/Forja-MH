# M1.7.T02 — Tarefas e estados

> Tempo previsto: ~13,6 h — ≈ 5 h de leitura (o capítulo *Task Management* do livro do FreeRTOS, a referência da API e o código do port Cortex-M), ≈ 3 h de exercícios de estados e de pilha, ≈ 4 h de prática no simulador POSIX e no QEMU (ou na placa), ≈ 1,5 h de revisão. A **tarefa** é o objeto central de um RTOS: uma função com laço infinito, uma pilha só dela e um bloco de controle que o kernel usa para guardá-la quando ela não está rodando. Este tópico cria, apaga, suspende e acorda tarefas, mostra os quatro estados e as transições entre eles, ensina a tarefa periódica sem deriva e abre a **troca de contexto** no Cortex-M — o PendSV e a PSP que o M1.3.T06 apresentou e o M1.4.T11 encontrou no HardFault agora ganham o seu verdadeiro papel.

## Ao final você consegue
- Criar e apagar tarefas com xTaskCreate, xTaskCreateStatic e vTaskDelete, passando parâmetros, e explicar o TCB, a pilha própria de cada tarefa e o tamanho de pilha em palavras.
- Descrever os estados Running, Ready, Blocked e Suspended e as transições causadas por vTaskDelay, objetos do kernel, vTaskSuspend e vTaskResume.
- Implementar tarefas periódicas sem deriva com xTaskDelayUntil e explicar a tarefa ociosa, o idle hook e o efeito de uma tarefa que nunca bloqueia.
- Explicar a troca de contexto no Cortex-M (PendSV na menor prioridade, PSP para as tarefas e MSP para o kernel, registradores salvos pelo hardware e pelo software, SVC para iniciar a primeira tarefa).

## Resumo
**1. Tarefa = função + pilha + TCB.** Uma tarefa do FreeRTOS é uma função do tipo `void f(void *pvParametros)` que **nunca retorna**: ou fica num laço infinito, ou se apaga com `vTaskDelete(NULL)`. Ao criá-la, o kernel aloca:
- uma **pilha própria** (`usStackDepth` **palavras**, ou seja, elementos de `StackType_t`: 4 bytes no Cortex-M; o ESP-IDF é a exceção e conta em bytes, M1.6.T02);
- um **TCB** (*Task Control Block*, a `struct tskTCB` de `tasks.c`), cujo **primeiro campo** é `pxTopOfStack`, o topo da pilha salvo na última troca de contexto. Seguem os itens de lista que põem a tarefa nas listas de prontas, bloqueadas ou de eventos, a prioridade (e a prioridade-base, usada pela herança de prioridade, T06), o ponteiro para o início da pilha, o nome e o valor de notificação (T07).

```c
BaseType_t xTaskCreate( TaskFunction_t pvTaskCode,      /* a função da tarefa */
                        const char * const pcName,       /* só para depuração */
                        configSTACK_DEPTH_TYPE uxStackDepth, /* em PALAVRAS */
                        void *pvParameters,              /* chega como argumento */
                        UBaseType_t uxPriority,          /* 0 .. configMAX_PRIORITIES − 1 */
                        TaskHandle_t *pxCreatedTask );   /* handle, ou NULL */
```
Retorna `pdPASS` ou `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY` (faltou heap: **sempre teste**). Número maior = prioridade maior; 0 é a da tarefa ociosa.

**Alocação estática.** Com `configSUPPORT_STATIC_ALLOCATION = 1`, você fornece a pilha e o TCB, e a tarefa não usa o heap (T08):
```c
#define PILHA_SENSOR 256                                  /* palavras */
static StackType_t  xPilhaSensor[ PILHA_SENSOR ];
static StaticTask_t xTcbSensor;

TaskHandle_t h = xTaskCreateStatic( vTarefaSensor, "sensor", PILHA_SENSOR, NULL, 2,
                                    xPilhaSensor, &xTcbSensor );   /* nunca falha por falta de heap */
```

**Parâmetros.** O `pvParameters` é um `void *`: passe o endereço de algo que **continue existindo** depois que a função criadora retornar (variável global, `static` ou `const`). Passar o endereço de uma variável local do `main` funciona por acaso no FreeRTOS para Cortex-M (o `main` nunca retorna), mas quebra se a criação for feita dentro de outra função.

**Apagar.** `vTaskDelete(h)` tira a tarefa de todas as listas. Se ela se apagou (`vTaskDelete(NULL)`), quem libera a pilha e o TCB é a **tarefa ociosa** — que precisa ganhar CPU de vez em quando. Uma função de tarefa que "cai" no fim executa `prvTaskExitError`, que dispara o `configASSERT`.

**2. Os estados.**
```
                 vTaskSuspend()                       vTaskSuspend()
   ┌──────────────────────────── Suspended ◄──────────────────────────┐
   │ vTaskResume()                    ▲                                │
   ▼                                  │ vTaskSuspend()                 │
 Ready ◄──── evento ou tempo limite ── Blocked ◄── chamada que bloqueia ┤
   │  ▲                                                                 │
   │  │ preempção ou taskYIELD()                                        │
   ▼  │                                                                 │
 Running ───────────────────────────────────────────────────────────────┘
```
- **Running**: a que está na CPU (uma só por núcleo).
- **Ready**: pronta para rodar, esperando a CPU porque há outra de prioridade **maior ou igual** rodando.
- **Blocked**: esperando **tempo** (`vTaskDelay`, `xTaskDelayUntil`) ou um **evento** (fila, semáforo, mutex, event group, notificação), quase sempre com **tempo limite**. Não consome CPU. Com `INCLUDE_vTaskSuspend = 1`, esperar com `portMAX_DELAY` é esperar para sempre.
- **Suspended**: fora do escalonamento até alguém chamar `vTaskResume` (ou `xTaskResumeFromISR`). Não há tempo limite. Uso legítimo raro: depuração, desligar uma função inteira, tarefas de inicialização.
- `eTaskGetState()` também devolve `eDeleted` (apagada, à espera da limpeza pela ociosa).

Detalhe que surpreende: suspender uma tarefa **bloqueada** e depois retomá-la a põe em **Ready**: a espera em curso é abandonada (para um `vTaskDelay`, ela acorda antes da hora).

**Exemplo 1 (estados no simulador POSIX).** Uma tarefa "dorminhoca" faz `vTaskDelay(1000)` em laço; um monitor de prioridade maior consulta e altera o estado dela:
```c
static TaskHandle_t xDorminhoca;
static void vDorminhoca( void *pv ) { ( void ) pv; for( ;; ) { vTaskDelay( pdMS_TO_TICKS( 1000 ) ); } }

static const char *pcEstado( eTaskState e )
{
    static const char *n[] = { "Running", "Ready", "Blocked", "Suspended", "Deleted", "Invalid" };
    return n[ e ];
}

static void vMonitor( void *pv )                 /* prioridade 3 */
{
    ( void ) pv;
    vTaskDelay( 5 );
    printf( "dorminhoca: %s\n", pcEstado( eTaskGetState( xDorminhoca ) ) );   /* Blocked   */
    vTaskSuspend( xDorminhoca );
    printf( "dorminhoca: %s\n", pcEstado( eTaskGetState( xDorminhoca ) ) );   /* Suspended */
    vTaskResume( xDorminhoca );
    printf( "dorminhoca: %s\n", pcEstado( eTaskGetState( xDorminhoca ) ) );   /* Ready     */
    printf( "monitor: %s\n", pcEstado( eTaskGetState( xTaskGetCurrentTaskHandle() ) ) ); /* Running */
    for( ;; ) { vTaskDelay( portMAX_DELAY ); }
}
```
(Executado com o kernel V11.1 no port POSIX: a saída foi exatamente Blocked, Suspended, Ready e Running. O `Ready` depois do `vTaskResume` mostra que o atraso de 1000 ticks foi abandonado.)

**3. Tarefas periódicas: `vTaskDelay` × `xTaskDelayUntil`.**
- `vTaskDelay(n)` bloqueia por n ticks **contados a partir da chamada**. Como a chamada pode cair em qualquer ponto entre dois ticks, o atraso real fica entre **(n − 1) e n períodos de tick** — `vTaskDelay(1)` pode durar quase nada. Numa tarefa periódica, o período vira **trabalho + n** e varia com o trabalho: **deriva**.
- `xTaskDelayUntil(&xUltimoDespertar, n)` bloqueia até o tick **xUltimoDespertar + n** e atualiza a variável: o período é fixo, independentemente do tempo de trabalho. Retorna `pdFALSE` se o instante já passou (a tarefa atrasou mais que um período) — sinal de sobrecarga que vale registrar.

**Exemplo 2 (deriva medida).** Duas tarefas iguais fazem 3 ticks de trabalho e esperam 10 ticks, uma com cada função:
```c
static void vComDeriva( void *pv )
{
    for( ;; ) {
        vTrabalho( 3 );                          /* 3 ticks de processamento */
        vTaskDelay( 10 );                        /* período real: 3 + 10 = 13 ticks */
    }
}

static void vSemDeriva( void *pv )
{
    TickType_t xUltimo = xTaskGetTickCount();   /* referência inicial */
    for( ;; ) {
        vTrabalho( 3 );
        if( xTaskDelayUntil( &xUltimo, 10 ) == pdFALSE ) {
            /* perdeu o instante: o trabalho passou de um período */
        }
    }
}
```
No simulador POSIX, os intervalos medidos entre despertares foram **13, 13, 13** ticks com `vTaskDelay` e **10, 10, 10** com `xTaskDelayUntil`. Depois de 100 ciclos, a primeira está 300 ticks atrasada; a segunda, nenhum.

**4. A tarefa ociosa e o idle hook.** `vTaskStartScheduler()` cria a **tarefa ociosa** (*idle*) com prioridade 0, para que sempre exista uma tarefa pronta. Ela:
- libera a memória das tarefas que se apagaram;
- chama o **idle hook** `vApplicationIdleHook()` a cada volta, se `configUSE_IDLE_HOOK = 1` — o lugar para medir carga de CPU, pôr o núcleo em `__WFI()` ou fazer trabalho de fundo. **Nunca bloqueie** no idle hook;
- com `configIDLE_SHOULD_YIELD = 1`, cede a CPU logo a tarefas de aplicação também de prioridade 0.

**A tarefa que nunca bloqueia.** Uma tarefa de prioridade 2 com laço `for (;;) { le_sensor(); }` sem nenhuma chamada que bloqueie **mata de fome** (*starvation*) todas as tarefas de prioridade 0 e 1, inclusive a ociosa: as tarefas apagadas nunca são limpas e o idle hook nunca roda. Toda tarefa que não seja a de menor prioridade precisa **bloquear** em algum ponto do laço — esperando tempo ou evento. É a regra mais importante do projeto com RTOS: **tarefas orientadas a eventos**, não a varredura.

**5. A troca de contexto no Cortex-M.** O port do Cortex-M usa os recursos que o M1.3.T06 apresentou:

| Recurso | Papel no FreeRTOS |
|---|---|
| **PSP** | pilha das **tarefas** (modo Thread, CONTROL.SPSEL = 1) |
| **MSP** | pilha do **kernel e das interrupções** (modo Handler); depois que o escalonador inicia, o MSP volta ao topo da RAM definido na tabela de vetores |
| **SysTick** | gera o tick; na rotina, se uma tarefa de maior prioridade acordou, **pende o PendSV** |
| **PendSV** (exceção 14) | faz a troca de contexto; configurado na **menor prioridade** |
| **SVC** (exceção 11) | usado uma vez, para iniciar a **primeira** tarefa |

**Por que o PendSV na menor prioridade?** Quem decide trocar (o SysTick, uma ISR que deu um semáforo, uma tarefa que chamou `taskYIELD()`) apenas **pende** o PendSV (`portYIELD()` escreve `PENDSVSET` no `SCB->ICSR`). Ele só roda quando **todas** as outras interrupções terminaram, encadeado por tail-chaining. Assim a troca nunca acontece no meio de uma ISR, e várias ISRs que pedem troca no mesmo instante geram **uma** troca só.

**A sequência** (port `GCC/ARM_CM3`, função `xPortPendSVHandler`):
1. Ao entrar no PendSV, o **hardware** já empilhou na PSP da tarefa que sai: R0–R3, R12, LR, PC e xPSR (8 palavras).
2. O tratador lê a PSP (`mrs r0, psp`), empilha **R4–R11** (8 palavras) nessa pilha e salva o novo topo no **primeiro campo do TCB** (`pxTopOfStack`).
3. Eleva o BASEPRI até `configMAX_SYSCALL_INTERRUPT_PRIORITY` (T04) e chama `vTaskSwitchContext()`, que aponta `pxCurrentTCB` para a tarefa pronta de maior prioridade.
4. Lê o `pxTopOfStack` da nova tarefa, desempilha R4–R11, escreve a PSP e retorna com `bx r14` (EXC_RETURN = 0xFFFF_FFFD: Thread, PSP). O **hardware** desempilha as outras 8 palavras — e a nova tarefa continua de onde parou.

```asm
xPortPendSVHandler:                  @ trecho real do port ARM_CM3 (V11)
    mrs   r0, psp
    isb
    ldr   r3, =pxCurrentTCB
    ldr   r2, [r3]
    stmdb r0!, {r4-r11}              @ salva o resto do contexto na pilha da tarefa
    str   r0, [r2]                   @ pxCurrentTCB->pxTopOfStack = r0
    stmdb sp!, {r3, r14}
    mov   r0, #configMAX_SYSCALL_INTERRUPT_PRIORITY
    msr   basepri, r0
    bl    vTaskSwitchContext         @ escolhe a próxima tarefa
    mov   r0, #0
    msr   basepri, r0
    ldmia sp!, {r3, r14}
    ldr   r1, [r3]
    ldr   r0, [r1]                   @ topo da pilha da nova tarefa
    ldmia r0!, {r4-r11}
    msr   psp, r0
    isb
    bx    r14                        @ o hardware desempilha R0-R3, R12, LR, PC, xPSR
```
No **Cortex-M4F**, o port `ARM_CM4F` salva também o **R14** (o EXC_RETURN de cada tarefa) e, se o bit 4 do EXC_RETURN indicar contexto de ponto flutuante ativo, **S16–S31**; o hardware, nesse caso, empilha o quadro estendido de 26 palavras (com S0–S15 e FPSCR).

**A primeira tarefa.** Ao criar uma tarefa, `pxPortInitialiseStack()` monta na pilha dela um **quadro falso**, como se ela tivesse sido interrompida: xPSR = 0x0100_0000 (bit Thumb), PC = endereço da função, LR = `prvTaskExitError`, R0 = `pvParameters` — é assim que o parâmetro chega como argumento — e espaço para R4–R11. `prvPortStartFirstTask()` volta o MSP ao topo, habilita interrupções e executa `svc 0`; o `vPortSVCHandler` carrega o contexto da primeira tarefa e retorna com EXC_RETURN 0xFFFF_FFFD. Só uma **exceção** consegue "retornar" para uma tarefa que nunca rodou: por isso o SVC.

**Exemplo 3 (contexto em bytes).** Quanto da pilha de cada tarefa a troca de contexto consome?
- Cortex-M3 (port ARM_CM3): 8 (hardware) + 8 (R4–R11) = **16 palavras = 64 bytes**.
- Cortex-M4F (port ARM_CM4F) numa tarefa que não usa a FPU: 8 + 9 (R4–R11 e R14) = **17 palavras = 68 bytes**.
- Cortex-M4F com FPU ativa: 26 (quadro estendido) + 9 + 16 (S16–S31) = **51 palavras = 204 bytes**.
- Além disso, a pilha da tarefa recebe o quadro de **qualquer interrupção** que chegue enquanto ela roda (8 ou 26 palavras), já que a entrada da ISR empilha na pilha em uso (PSP). As ISRs aninhadas, depois, usam o MSP.

**Exemplo 4 (PSP e MSP no QEMU).** No `mps2-an385` (Cortex-M3) do QEMU, duas tarefas imprimem os ponteiros de pilha:
```c
static inline uint32_t ulLePSP( void ) { uint32_t r; __asm volatile( "mrs %0, psp" : "=r"( r ) ); return r; }
static inline uint32_t ulLeCONTROL( void ) { uint32_t r; __asm volatile( "mrs %0, control" : "=r"( r ) ); return r; }

static void vTarefa( void *pv )
{
    for( ;; ) {
        printf( "%s: PSP=0x%x CONTROL=%u livre=%u palavras\r\n", ( char * ) pv,
                ( unsigned ) ulLePSP(), ( unsigned ) ulLeCONTROL(),
                ( unsigned ) uxTaskGetStackHighWaterMark( NULL ) );
        vTaskDelay( 10 );
    }
}
```
Saída observada (arm-none-eabi-gcc 13.3, kernel V11.1, QEMU 9.2): no `main`, antes do escalonador, `CONTROL=0` (MSP); nas tarefas, `CONTROL=2` (SPSEL = 1: PSP, privilegiado), com PSPs diferentes (0x2000_0620 e 0x2000_0A88), cada uma dentro da pilha alocada no heap para a sua tarefa.

## Armadilhas comuns
- Tratar `usStackDepth` como bytes num Cortex-M (pilha quatro vezes maior que a pretendida) ou como palavras no ESP-IDF (quatro vezes menor).
- Não testar o retorno de `xTaskCreate`.
- Deixar a função da tarefa terminar sem `vTaskDelete(NULL)`.
- Usar `vTaskDelay` para períodos: o período deriva com o tempo de trabalho.
- Bloquear (`vTaskDelay`, `xQueueReceive` com espera) dentro do idle hook.
- Tarefa de prioridade alta que nunca bloqueia: inanição de todas as de baixo, inclusive a ociosa.
- Usar `vTaskSuspend` como mecanismo de sincronização (corrida entre suspender e retomar): use semáforos ou notificações (T05, T07).
- Pôr o PendSV numa prioridade alta à mão: a troca de contexto pode acontecer no meio de uma ISR.

## Gabarito
1. 200 palavras × 4 bytes = **800 bytes**. No ESP-IDF, 200 **bytes** — pequeno demais para quase tudo.
2. (a) `eRunning`; (b) `eBlocked` (com `INCLUDE_vTaskSuspend = 1`, o kernel guarda a espera infinita na lista de suspensas, mas `eTaskGetState` percebe que a tarefa está na lista de espera da fila e informa `eBlocked`); (c) `eReady` (a espera foi abandonada).
3. Período real de 24 ms (4 + 20, mais uma fração de tick). Depois de 50 ciclos: 50 × 4 = **200 ms** de atraso acumulado.
4. `pdFALSE`, sem bloquear. Conte essas ocorrências (são prazos perdidos) e decida: descartar o ciclo, avisar o supervisor ou rever a análise de tempo (T03).
5. Quando a função criadora retorna, a variável deixa de existir e a tarefa passa a ler lixo da pilha — o erro aparece tarde e longe da causa.
6. As de prioridade 0 (inclusive a ociosa) nunca mais rodam. As de prioridade 2 continuam normais: preemptam a tarefa de prioridade 1 sempre que ficam prontas.
7. Com contexto de ponto flutuante ativo: 26 + 9 + 16 = 51 palavras = **204 bytes**.
8. Uma tarefa que nunca rodou precisa ter o contexto carregado como se voltasse de uma interrupção: PSP apontando para o quadro falso, modo Thread e EXC_RETURN 0xFFFF_FFFD. Só um retorno de exceção faz isso; o SVC põe a CPU em modo Handler para poder executar esse retorno.
