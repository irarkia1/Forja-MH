# M1.7.T10 — Zephyr (introdução)

> Tempo previsto: ~13,6 h — ≈ 5 h de leitura (o *Getting Started Guide*, os guias de devicetree e de Kconfig e os serviços do kernel na documentação do Zephyr), ≈ 2,5 h de exercícios de devicetree, Kconfig e tradução de código FreeRTOS, ≈ 4,5 h de prática (instalar o ambiente com west, compilar e rodar amostras em `native_sim` e `qemu_cortex_m3` e, se tiver, na Nucleo), ≈ 1,5 h de revisão. O FreeRTOS é uma **biblioteca**: você traz o resto (drivers, build, configuração). O **Zephyr** é um **sistema completo**: kernel, centenas de drivers, pilhas de rede e BLE, sistema de build e um modelo de configuração herdado do Linux. Este tópico fecha o módulo traduzindo o que você aprendeu para o segundo RTOS mais importante do mercado de IoT — e apresenta as duas ideias que mais confundem quem chega nele: **devicetree** (o hardware descrito como dados) e **Kconfig** (o software escolhido por opções). Elas voltam nos módulos de produto (M3) e de firmware profissional (M4).

## Ao final você consegue
- Descrever a organização do Zephyr (kernel, drivers, subsistemas, west e CMake) e comparar suas threads e prioridades cooperativas e preemptivas com as tarefas do FreeRTOS.
- Ler e escrever trechos de devicetree (nós, compatible, reg, status, aliases, overlays) e acessar dispositivos pelas macros DT_ALIAS, DEVICE_DT_GET e GPIO_DT_SPEC_GET.
- Configurar o build com Kconfig (prj.conf, menuconfig, símbolos CONFIG_) e separar o papel do devicetree (descrição do hardware) do papel do Kconfig (escolha do software).
- Escrever uma aplicação Zephyr com threads (K_THREAD_DEFINE, k_msleep), k_msgq, k_sem, k_mutex e k_timer e compilá-la com west build para native_sim ou qemu_cortex_m3.

## Resumo
**1. O que é o Zephyr.** Um RTOS de código aberto (licença Apache 2.0) mantido sob a Linux Foundation, com:
- **kernel** com threads, escalonador por prioridade, ISRs, objetos de sincronização e comunicação, timers, filas de trabalho (*workqueues*);
- **drivers** com API uniforme (GPIO, I²C, SPI, UART, ADC, PWM, sensores…) para centenas de placas;
- **subsistemas**: rede (IPv4/IPv6, TCP, MQTT, CoAP), Bluetooth LE certificável, USB, sistemas de arquivos, gerência de energia, logging, shell, atualização por MCUboot;
- **build** em CMake, organizado pelo **west** (a ferramenta que baixa o repositório principal e os módulos, compila, grava e depura);
- **configuração** em duas camadas: **devicetree** (hardware) e **Kconfig** (software).

Uma aplicação mínima:
```
minha_app/
├─ CMakeLists.txt     ← find_package(Zephyr …), project(), target_sources(app …)
├─ prj.conf           ← opções Kconfig da aplicação (CONFIG_…=y)
├─ app.overlay        ← (opcional) mudanças no devicetree da placa
└─ src/main.c
```
```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(minha_app)
target_sources(app PRIVATE src/main.c)
```
```sh
west build -b native_sim minha_app        # roda como processo Linux (como o port POSIX do FreeRTOS)
west build -t run
west build -p always -b qemu_cortex_m3 minha_app && west build -t run    # Cortex-M3 emulado
west build -p always -b nucleo_f401re minha_app && west flash            # placa real
```

**2. Threads e prioridades: o mapa FreeRTOS → Zephyr.**

| Conceito | FreeRTOS | Zephyr |
|---|---|---|
| unidade de execução | tarefa (`xTaskCreate`) | thread (`k_thread_create` ou `K_THREAD_DEFINE`, estática) |
| pilha | palavras | **bytes** (`K_THREAD_STACK_DEFINE`) |
| prioridade | **número maior = mais urgente** | **número menor = mais urgente** |
| não preemptível | modo cooperativo global (`configUSE_PREEMPTION 0`) | por thread: prioridade **negativa** = **cooperativa** |
| atraso | `vTaskDelay(pdMS_TO_TICKS(ms))` | `k_msleep(ms)` ou `k_sleep(K_MSEC(ms))` |
| fila | `xQueueCreate` / `xQueueSend` / `xQueueReceive` | `K_MSGQ_DEFINE` / `k_msgq_put` / `k_msgq_get` |
| semáforo | `xSemaphoreCreateCounting` | `K_SEM_DEFINE(nome, inicial, limite)` / `k_sem_give` / `k_sem_take` |
| mutex | `xSemaphoreCreateMutex` (herança) | `K_MUTEX_DEFINE` / `k_mutex_lock` (herança **e** recursivo) |
| timer | callback na tarefa de serviço | `K_TIMER_DEFINE` — a função de expiração roda em **contexto de interrupção** |
| adiar trabalho de ISR | notificação, `xTimerPendFunctionCallFromISR` | `k_work_submit` (fila de trabalho do sistema), semáforo |
| tempos limite | ticks (`portMAX_DELAY`, 0) | `k_timeout_t`: `K_FOREVER`, `K_NO_WAIT`, `K_MSEC(…)` |

**Prioridades no Zephyr** (*Threads → Thread Priorities*):
- **Cooperativas**: valores negativos, de −`CONFIG_NUM_COOP_PRIORITIES` a −1. Uma thread cooperativa em execução **não é preemptada** por outras threads (só por ISRs) até bloquear ou ceder (`k_yield`). Útil para trechos que não podem ser interrompidos por outras threads sem desligar interrupções.
- **Preemptivas**: de 0 a `CONFIG_NUM_PREEMPT_PRIORITIES` − 1; a de valor menor preempta a de valor maior. A thread ociosa fica na prioridade mais baixa.
- Macros portáveis: `K_PRIO_COOP(x)` = −(`CONFIG_NUM_COOP_PRIORITIES` − x) e `K_PRIO_PREEMPT(x)` = x.
- *Time slicing* entre threads preemptivas de mesma prioridade: `CONFIG_TIMESLICING` e `CONFIG_TIMESLICE_SIZE` (ms).
- O escalonamento é o mesmo do T03: prioridade fixa, preemptivo, a pronta mais urgente roda. Toda a análise (RMS, RTA, bloqueio) vale igual — só inverta o sentido dos números.

**3. Devicetree: o hardware como dados.** O devicetree vem do Linux: um arquivo de texto (`.dts`, com includes `.dtsi`) que descreve **o que existe** na placa — CPU, memória, periféricos, pinos, LEDs, sensores no I²C. No Zephyr, ele é processado **na compilação** e vira macros C (`devicetree_generated.h`): não há interpretação em tempo de execução.
```dts
/ {
    aliases {
        led0 = &green_led;                    /* nome genérico usado pelas amostras */
    };
    leds {
        compatible = "gpio-leds";
        green_led: led_0 {                    /* rótulo: nome do nó */
            gpios = <&gpioa 5 GPIO_ACTIVE_HIGH>;   /* PA5 na Nucleo-F401RE */
            label = "User LD2";
        };
    };
};

&i2c1 {                                       /* referência a um nó definido no .dtsi do SoC */
    status = "okay";                          /* liga o periférico (por padrão vem "disabled") */
    pinctrl-0 = <&i2c1_scl_pb8 &i2c1_sda_pb9>;
    pinctrl-names = "default";
    clock-frequency = <I2C_BITRATE_FAST>;
    bme280@76 {                               /* nó-filho: endereço I²C 0x76 */
        compatible = "bosch,bme280";          /* escolhe o driver e o binding (YAML) */
        reg = <0x76>;
    };
};
```
- **`compatible`** liga o nó a um **binding** (arquivo YAML em `dts/bindings`) que diz quais propriedades são válidas e a um **driver**.
- **`reg`**: endereço (de registradores, ou no barramento: 0x76 no I²C).
- **`status = "okay"`** habilita; `"disabled"` faz o nó ser ignorado.
- **Aliases** e **chosen** (`zephyr,console = &usart2;`) dão nomes estáveis para a aplicação não depender da placa.
- **Overlay**: a aplicação não edita o `.dts` da placa; ela acrescenta `app.overlay` (ou `boards/nucleo_f401re.overlay`) com as mudanças, e o build junta tudo. O resultado final fica em `build/zephyr/zephyr.dts` — o primeiro lugar a olhar quando algo não aparece.

**Acesso pelo C.**
```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>
#include <zephyr/device.h>

#define LED_NODE DT_ALIAS(led0)                                   /* identificador do nó, em compilação */
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED_NODE, gpios);   /* porta, pino e flags */
static const struct device *const i2c = DEVICE_DT_GET(DT_NODELABEL(i2c1));

int main(void)
{
    if (!gpio_is_ready_dt(&led) || !device_is_ready(i2c)) {
        return 0;                                  /* driver não inicializou: veja o zephyr.dts e o prj.conf */
    }
    gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);
    for (;;) {
        gpio_pin_toggle_dt(&led);
        k_msleep(500);
    }
}
```
O mesmo `main.c` pisca o LED de qualquer placa cujo devicetree tenha o alias `led0`: trocar de placa é trocar o `-b` do `west build`. Compare com o M1.4, em que o pino estava escrito no código.

**4. Kconfig: o software como opções.** O Kconfig (também do Linux, e o mesmo do ESP-IDF, M1.6.T02) decide **o que é compilado** e com que parâmetros: quais subsistemas, quais drivers, tamanhos de pilha, número de prioridades.
```ini
# prj.conf
CONFIG_GPIO=y
CONFIG_I2C=y
CONFIG_SENSOR=y
CONFIG_LOG=y
CONFIG_MAIN_STACK_SIZE=2048
CONFIG_TIMESLICING=y
CONFIG_TIMESLICE_SIZE=10
CONFIG_THREAD_ANALYZER=y        # uso de pilha e de CPU por thread (equivale ao vTaskList)
```
- Valores vêm, em camadas, dos padrões dos `Kconfig`, do `<placa>_defconfig`, do `prj.conf` e de fragmentos extras (`-DEXTRA_CONF_FILE=…`). O resultado está em `build/zephyr/.config` e vira `autoconf.h` (`#define CONFIG_GPIO 1`).
- `west build -t menuconfig` (ou `guiconfig`) mostra as opções, as dependências e **por que** uma opção não pode ser ligada. Mudanças feitas lá valem só para aquele build: copie para o `prj.conf` o que quiser manter.
- **Regra para separar**: devicetree diz **o que o hardware tem** (o BME280 está no I²C1, no endereço 0x76); Kconfig diz **o que o software usa** (compile o subsistema de sensores e o driver do BME280). Um sensor descrito no devicetree sem o driver ligado no Kconfig não funciona — e um driver ligado sem nó `okay` no devicetree também não.

**5. Uma aplicação com threads, fila, semáforo, mutex e timer.** A versão Zephyr do esqueleto do T09 (aquisição por timer, processamento, comunicação):
```c
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>

struct amostra { uint32_t seq; uint16_t bruto; };

K_MSGQ_DEFINE(fila_amostras, sizeof(struct amostra), 16, 4);   /* 16 itens alinhados em 4 bytes */
K_SEM_DEFINE(sem_gatilho, 0, 1);                                /* binário: inicial 0, limite 1 */
K_MUTEX_DEFINE(mutex_estado);
static uint32_t blocos;                                         /* protegido por mutex_estado */

static void expira(struct k_timer *t)          /* roda em CONTEXTO DE INTERRUPÇÃO: só sinaliza */
{
    k_sem_give(&sem_gatilho);
}
K_TIMER_DEFINE(timer_100hz, expira, NULL);

static void aquisicao(void *a, void *b, void *c)
{
    uint32_t seq = 0;
    k_timer_start(&timer_100hz, K_MSEC(10), K_MSEC(10));
    for (;;) {
        k_sem_take(&sem_gatilho, K_FOREVER);
        struct amostra s = { seq++, (uint16_t)(2048 + (seq % 100)) };   /* ADC sintético */
        if (k_msgq_put(&fila_amostras, &s, K_NO_WAIT) != 0) {
            printk("perda\n");
        }
    }
}

static void processamento(void *a, void *b, void *c)
{
    struct amostra s;
    uint32_t n = 0, soma = 0;
    for (;;) {
        k_msgq_get(&fila_amostras, &s, K_FOREVER);
        soma += s.bruto;
        if (++n == 10) {
            k_mutex_lock(&mutex_estado, K_FOREVER);
            blocos++;
            k_mutex_unlock(&mutex_estado);
            printk("bloco %u media %u\n", s.seq, soma / n);
            n = 0; soma = 0;
        }
    }
}

/* nome, pilha (BYTES), função, 3 argumentos, prioridade (menor = mais urgente), opções, atraso */
K_THREAD_DEFINE(t_aquis, 1024, aquisicao,     NULL, NULL, NULL, 2, 0, 0);
K_THREAD_DEFINE(t_proc,  1024, processamento, NULL, NULL, NULL, 3, 0, 0);
```
Repare nas diferenças em relação ao FreeRTOS: objetos e threads **estáticos** por macro (nada no heap, como a alocação estática do T08); a aquisição tem prioridade **2** e o processamento **3** — no Zephyr, 2 é **mais** urgente; a função do `k_timer` roda em ISR, por isso só dá o semáforo (no FreeRTOS, o callback rodava numa tarefa); `printk` é o print leve do kernel. Para tempos e uso de pilha, `CONFIG_THREAD_ANALYZER=y` imprime por thread o equivalente do `vTaskList`.

(Este código segue a API documentada do Zephyr 3.x/4.x, mas **não** foi compilado durante a escrita deste roteiro: o ambiente usado não tinha o SDK do Zephyr instalado. Compile-o no Experimento da seção Pratique e corrija o que a sua versão pedir.)

**6. FreeRTOS ou Zephyr?**

| Critério | FreeRTOS | Zephyr |
|---|---|---|
| Tamanho mínimo | menor (kernel de poucos KB) | maior, mas configurável até poucos KB em configurações mínimas |
| Drivers e pilhas | do fabricante (HAL, ESP-IDF) ou de terceiros | inclusos, com API uniforme |
| Curva de aprendizado | baixa: três arquivos C | alta: west, CMake, devicetree, Kconfig |
| Portabilidade da aplicação entre placas | depende de você criar a camada (o `plataforma.h` do T09) | parte do modelo (devicetree + API de drivers) |
| Ecossistema | onipresente; RTOS do ESP-IDF; AWS | forte em BLE e rede (Nordic nRF Connect SDK é baseado nele), segurança, atualizações |
| Quando escolher | MCU pequeno, SDK do fabricante já baseado nele (ESP32), equipe pequena | produto com rede/BLE, várias placas, longo ciclo de vida, requisitos de segurança |

## Armadilhas comuns
- Inverter o sentido das prioridades ao portar do FreeRTOS (no Zephyr, menor = mais urgente).
- Contar a pilha em palavras (no Zephyr é em bytes, como no ESP-IDF).
- Esquecer que prioridades negativas são cooperativas: a thread não é preemptada por outras threads.
- Bloquear na função de expiração do `k_timer` (contexto de interrupção).
- Editar o `.dts` da placa em vez de usar um overlay.
- Ligar o nó no devicetree e esquecer o `CONFIG_` do driver (ou o contrário).
- Mudar opções no menuconfig e esperar que sobrevivam a um `west build -p always`.
- Usar o nome de placa errado para a versão do Zephyr (os nomes mudaram com o modelo de placas da versão 3.7, por exemplo `native_posix` → `native_sim`).

## Gabarito
1. Prático. No `zephyr.dts`, procure o nó com `compatible = "gpio-leds"` e o alias `led0`; no `.config`, `CONFIG_GPIO=y`.
2. Prático: o thread analyzer imprime nome, pilha usada/total e uso de CPU de cada thread.
3. 256 palavras × 4 = **1024 bytes**; prioridade baixa em número, por exemplo `K_PRIO_PREEMPT(1)` ou 1 (no FreeRTOS, 3 de 0–4 era alta; no Zephyr, perto de 0 é alta). Ex.: `K_THREAD_DEFINE(t_f, 1024, f, NULL, NULL, NULL, 1, 0, 0);`.
4. −(16 − 14) = **−2**. É cooperativa: uma thread de prioridade 0 (preemptiva) **não** a interrompe; ela só perde a CPU para ISRs ou quando bloqueia/cede.
5. `&i2c1 { status = "okay"; pinctrl-0 = <&i2c1_scl_pb8 &i2c1_sda_pb9>; pinctrl-names = "default"; bme280@77 { compatible = "bosch,bme280"; reg = <0x77>; }; };` e, no `prj.conf`, `CONFIG_I2C=y` e `CONFIG_SENSOR=y`.
6. Driver não compilado (falta `CONFIG_SENSOR`/`CONFIG_BME280` — veja o `.config`), barramento pai desabilitado ou sem pinos (veja o `zephyr.dts`), ou o sensor não respondeu na inicialização (endereço errado, fiação — veja o log de boot).
7. Porque roda em contexto de interrupção: ISRs não podem bloquear. Ela deve apenas sinalizar (semáforo, `k_work_submit`) e deixar o trabalho para uma thread.
8. O devicetree diz que existe um BME280 no I²C1, endereço 0x76 (hardware); o Kconfig diz que o driver de sensores e o do BME280 serão compilados e com que opções (software). Os dois são necessários.
