# M1.7.T07 — Timers de software e eventos

> Tempo previsto: ~13,6 h — ≈ 5 h de leitura (os capítulos *Software Timer Management*, *Event Groups* e *Task Notifications* do livro do FreeRTOS), ≈ 3 h de exercícios de escolha de mecanismo e de bits, ≈ 4 h de prática no simulador POSIX (timers, grupos de eventos e notificações), ≈ 1,5 h de revisão. Filas, semáforos e mutex (T04, T05) resolvem a maior parte dos problemas, mas nem sempre do jeito mais barato. Este tópico apresenta três ferramentas que completam a caixa: **timers de software**, para executar uma função num instante futuro sem gastar uma tarefa; **event groups**, para esperar **combinações** de eventos ("Wi-Fi conectado **e** hora sincronizada"); e **notificações de tarefa**, o mecanismo mais rápido e mais leve do FreeRTOS para sinalizar uma tarefa específica. No fim, uma tabela para escolher o mecanismo certo para cada problema.

## Ao final você consegue
- Criar timers de software one-shot e auto-reload (xTimerCreate, xTimerStart, xTimerReset, xTimerChangePeriod) e explicar a tarefa de serviço dos timers, a fila de comandos e as regras do callback.
- Sincronizar tarefas com event groups (xEventGroupSetBits, xEventGroupWaitBits esperando um ou todos os bits, xEventGroupSync) e calcular quantos bits de evento estão disponíveis.
- Usar task notifications como semáforo leve, valor de 32 bits e conjunto de bits (xTaskNotifyGive, ulTaskNotifyTake, xTaskNotify, xTaskNotifyWait) e conhecer as limitações delas.
- Escolher entre timer de software, timer de hardware, tarefa periódica, fila, semáforo, event group e notificação para cada problema de sincronização pelo custo em RAM, tempo e flexibilidade.

## Resumo
**1. Timers de software.** Um timer de software chama uma **função de callback** depois de um período, uma vez (**one-shot**) ou repetidamente (**auto-reload**), sem precisar de uma tarefa só para isso.
```c
TimerHandle_t xTimerCreate( const char *pcNome, TickType_t xPeriodo,
                            BaseType_t xAutoReload,          /* pdTRUE: repete; pdFALSE: one-shot */
                            void *pvTimerID,                 /* dado livre do usuário */
                            TimerCallbackFunction_t pxCallback );
```
Como funciona (`configUSE_TIMERS = 1`, `timers.c`):
- O kernel cria uma tarefa, a **tarefa de serviço dos timers** (também chamada *daemon*; aparece como "Tmr Svc"), com prioridade `configTIMER_TASK_PRIORITY` e pilha `configTIMER_TASK_STACK_DEPTH`.
- `xTimerStart`, `xTimerStop`, `xTimerReset`, `xTimerChangePeriod` **não** mexem no timer diretamente: enviam um **comando** pela **fila de comandos dos timers** (`configTIMER_QUEUE_LENGTH`) para a tarefa de serviço. Por isso têm um parâmetro de tempo de bloqueio (para o caso de a fila estar cheia) e versões FromISR.
- Todos os callbacks rodam **na tarefa de serviço**, um depois do outro. Regras: o callback deve ser **curto** e **nunca bloquear** (nada de `vTaskDelay`, nem `xQueueReceive` com espera, nem mutex com espera), porque bloquear a tarefa de serviço atrasa **todos** os timers.
- Resolução = **um tick**. O período de um auto-reload é contado a partir do instante de expiração anterior, não do fim do callback: não há deriva acumulada.
- A prioridade da tarefa de serviço decide quando os callbacks rodam em relação às suas tarefas; se ela for baixa, uma tarefa ocupada atrasa todos os timers. É comum pô-la entre as mais altas.
- **Timer ID**: um `void *` guardado no timer; um único callback pode servir a vários timers e distinguir quem expirou (`pvTimerGetTimerID`), ou usar o ID como contador.
- `xTimerReset` reinicia a contagem: o timer passa a expirar um período **depois do reset**. Com um one-shot, é o padrão "apague a luz de fundo 5 s depois da última tecla".

**Exemplo 1 (pisca e luz de fundo).**
```c
static TimerHandle_t xPisca, xLuzFundo;

static void vCbPisca( TimerHandle_t xTimer )                 /* roda na tarefa de serviço dos timers */
{
    uint32_t n = ( uint32_t ) ( uintptr_t ) pvTimerGetTimerID( xTimer ) + 1;
    vTimerSetTimerID( xTimer, ( void * ) ( uintptr_t ) n );   /* o ID como contador */
    alterna_led();
    if( n == 3 ) xTimerChangePeriod( xTimer, pdMS_TO_TICKS( 50 ), 0 );   /* passa a piscar mais rápido */
    if( n == 5 ) xTimerStop( xTimer, 0 );
}

static void vCbLuzFundo( TimerHandle_t xTimer ) { desliga_luz_de_fundo(); }

void vInterfaceInit( void )
{
    xPisca    = xTimerCreate( "pisca", pdMS_TO_TICKS( 100 ), pdTRUE,  ( void * ) 0, vCbPisca );
    xLuzFundo = xTimerCreate( "luz",   pdMS_TO_TICKS( 300 ), pdFALSE, NULL,         vCbLuzFundo );
    configASSERT( xPisca && xLuzFundo );
    xTimerStart( xPisca, 0 );
    xTimerStart( xLuzFundo, 0 );
}

void vTeclaApertada( void ) { xTimerReset( xLuzFundo, 0 ); }   /* adia o desligamento */
```
No simulador POSIX (tick de 1 ms), o pisca expirou em 101, 201, 301, depois em 351 e 401 (período trocado para 50 ms) e parou; a tecla, simulada em t = 201, empurrou o desligamento da luz de 301 para **501**.

**Adiando trabalho de uma ISR para a tarefa de serviço.** `xTimerPendFunctionCallFromISR(funcao, p1, p2, &xAcordou)` põe na fila de comandos um pedido para executar `funcao(p1, p2)` na tarefa de serviço: processamento adiado sem criar uma tarefa só para isso (o livro mostra em *Deferring Work to the RTOS Daemon Task*). O `xEventGroupSetBitsFromISR` usa exatamente esse mecanismo por baixo.

**Timer de software × timer de hardware.** O de software tem resolução de um tick, *jitter* de até um tick mais o atraso da tarefa de serviço, e é barato (uma struct de ~44 bytes num Cortex-M3). Para PWM, amostragem de ADC a 10 kHz, medição de pulso ou qualquer coisa abaixo de alguns ms com precisão, use um **timer de hardware** (M1.4.T05) e, se for preciso falar com uma tarefa, o processamento adiado (T04).

**2. Event groups.** Um event group é um conjunto de **bits de evento** com nome (`#define BIT_WIFI (1 << 0)`), que tarefas e ISRs ligam e desligam, e pelos quais tarefas esperam:
```c
EventBits_t xEventGroupWaitBits( EventGroupHandle_t xGrupo,
                                 EventBits_t uxBitsParaEsperar,
                                 BaseType_t xLimparAoSair,     /* pdTRUE: zera os bits esperados ao retornar */
                                 BaseType_t xEsperarTodos,     /* pdTRUE: E lógico; pdFALSE: OU lógico */
                                 TickType_t xTempo );
```
- Devolve o valor dos bits no momento do retorno: **sempre confira** se a condição foi satisfeita ou se o tempo esgotou.
- **Várias tarefas** podem esperar o mesmo grupo, por combinações diferentes; um `xEventGroupSetBits` pode desbloquear **todas** as que ficaram satisfeitas (diferente de fila e semáforo, que entregam a uma só). Isso é *broadcast*.
- **Quantos bits**: o tipo `EventBits_t` tem a largura do tick, e os **8 bits altos** são reservados para controle do kernel. Com tick de 32 bits: **24** bits de evento; com 16 bits: **8**; com 64 bits: **56**.
- `xEventGroupSetBitsFromISR` não é determinístico (pode desbloquear um número qualquer de tarefas): por isso ele **adia** a operação para a tarefa de serviço dos timers, e pode falhar se a fila de comandos estiver cheia.

**Exemplo 2 (publicar só quando tudo estiver pronto).**
```c
#define BIT_WIFI   ( 1u << 0 )
#define BIT_SENSOR ( 1u << 1 )
#define BIT_HORA   ( 1u << 2 )
static EventGroupHandle_t xEventos;                 /* xEventGroupCreate() */

static void vPublicador( void *pv )
{
    for( ;; ) {
        EventBits_t uxBits = xEventGroupWaitBits( xEventos, BIT_WIFI | BIT_SENSOR | BIT_HORA,
                                                  pdFALSE,   /* não limpa: os estados continuam valendo */
                                                  pdTRUE,    /* espera TODOS */
                                                  pdMS_TO_TICKS( 30000 ) );
        if( ( uxBits & ( BIT_WIFI | BIT_SENSOR | BIT_HORA ) ) == ( BIT_WIFI | BIT_SENSOR | BIT_HORA ) ) {
            publica();
            vTaskDelay( pdMS_TO_TICKS( 60000 ) );
        } else {
            registra_falta( uxBits );                /* quais faltaram? */
        }
    }
}
/* a tarefa de Wi-Fi faz xEventGroupSetBits( xEventos, BIT_WIFI ) ao conectar e
   xEventGroupClearBits( xEventos, BIT_WIFI ) ao cair; idem para os outros */
```
No simulador, com os bits ligados em t = 611 (SENSOR), 621 (WIFI) e 631 (HORA), uma tarefa que esperava **qualquer** um entre WIFI e SENSOR acordou em 611, e o publicador, que esperava **todos**, em 631.

**Ponto de encontro.** `xEventGroupSync(xGrupo, meu_bit, todos_os_bits, tempo)` liga o bit da tarefa e espera que **todas** as participantes liguem os seus — uma barreira, de forma atômica (os bits são limpos ao liberar). Uso: três tarefas que precisam começar o próximo ciclo juntas.

**3. Notificações de tarefa.** Cada tarefa tem, no próprio TCB, um **valor de notificação** de 32 bits e um **estado** (pendente ou não), um par por posição do vetor `configTASK_NOTIFICATION_ARRAY_ENTRIES`. Outra tarefa ou uma ISR **notifica diretamente** a tarefa, sem objeto intermediário. A página *RTOS Task Notifications* do freertos.org relata que desbloquear uma tarefa por notificação é **45 % mais rápido** e usa menos RAM que por semáforo binário.

| Uso | Quem envia | Quem recebe |
|---|---|---|
| **Semáforo binário leve** | `xTaskNotifyGive(h)` / `vTaskNotifyGiveFromISR(h, &x)` | `ulTaskNotifyTake(pdTRUE, tempo)` — zera ao sair |
| **Semáforo contador leve** | os mesmos | `ulTaskNotifyTake(pdFALSE, tempo)` — decrementa 1 |
| **Bits de evento** | `xTaskNotify(h, bits, eSetBits)` | `xTaskNotifyWait(0, 0xFFFFFFFF, &v, tempo)` |
| **Valor** (caixa postal de 32 bits) | `xTaskNotify(h, v, eSetValueWithOverwrite)` ou `eSetValueWithoutOverwrite` | `xTaskNotifyWait(…, &v, …)` |
| **Incremento** | `xTaskNotify(h, 0, eIncrement)` | qualquer das anteriores |

**Exemplo 3 (ISR do DMA notificando a tarefa, a versão leve do T05).**
```c
static TaskHandle_t xTarefaADC;            /* guardado no xTaskCreate */

void DMA2_Stream0_IRQHandler( void )
{
    BaseType_t xAcordou = pdFALSE;
    if( DMA2->LISR & DMA_LISR_TCIF0 ) {
        DMA2->LIFCR = DMA_LIFCR_CTCIF0;
        vTaskNotifyGiveFromISR( xTarefaADC, &xAcordou );   /* incrementa o valor de notificação */
    }
    portYIELD_FROM_ISR( xAcordou );
}

static void vTarefaADC( void *pv )
{
    for( ;; ) {
        uint32_t n = ulTaskNotifyTake( pdFALSE, pdMS_TO_TICKS( 20 ) );   /* contador: não perde blocos */
        if( n == 0 ) { /* 20 ms sem DMA: avise o supervisor */ continue; }
        processa_bloco();
    }
}
```
Detalhe que confunde: `ulTaskNotifyTake` devolve o valor **antes** de decrementar ou zerar. No simulador, três `xTaskNotifyGive` seguidos fizeram o primeiro `ulTaskNotifyTake(pdFALSE, …)` devolver **3** (e deixar 2); o `ulTaskNotifyTake(pdTRUE, 0)` seguinte devolveu **2** e zerou. Dois `eSetBits` (0x01 e 0x04) chegaram como **0x05**; dois `eSetValueWithOverwrite` (111 e 222) deixaram **222**; e um `eSetValueWithoutOverwrite` com valor ainda pendente devolveu `pdFAIL`.

**Limitações** (livro, *Benefits and Limitations of Task Notifications*):
- só servem para mandar **para uma tarefa** específica (é preciso o handle); uma ISR não pode ser destino;
- **um receptor só**: não dá para várias tarefas esperarem a mesma notificação (use event group);
- não há fila: um valor de 32 bits por posição — dados chegando mais rápido que o consumo se perdem ou se sobrescrevem;
- o remetente **não pode bloquear** esperando o receptor consumir (não há "fila cheia");
- bibliotecas do próprio FreeRTOS (stream buffers, por exemplo) usam a posição 0 do vetor: se usar notificações junto, prefira outra posição (`configTASK_NOTIFICATION_ARRAY_ENTRIES` > 1 e as funções `…Indexed`).

**4. Escolhendo o mecanismo.** Custos medidos com `sizeof` dos tipos estáticos num Cortex-M3 (arm-none-eabi-gcc 13.3, kernel V11.1, configuração do módulo): fila e semáforo **80 bytes** (o semáforo é uma fila de itens de tamanho zero), timer **44 bytes**, event group **28 bytes**, notificação **zero** a mais (já está no TCB).

| Problema | Mecanismo indicado | Por quê |
|---|---|---|
| ISR avisa **uma** tarefa, sem dado | notificação (`vTaskNotifyGiveFromISR`) | mais rápida e sem RAM extra |
| Contar eventos de uma ISR para uma tarefa | notificação como contador ou semáforo contador | não perde eventos até o limite |
| Passar **dados** (vários itens, ordem) | fila (ou stream/message buffer) | cópia, ordem, bloqueio do remetente |
| Último valor de um sensor, para vários leitores | fila de 1 item com overwrite/peek | caixa postal |
| Proteger um recurso | mutex (ou tarefa guardiã) | dono e herança de prioridade |
| Esperar **combinação** de condições, ou acordar **várias** tarefas | event group | E/OU de bits, broadcast |
| Ação periódica curta ou atraso único (LED, tempo limite de inatividade) | timer de software | sem pilha própria |
| Trabalho periódico pesado ou que bloqueia | tarefa com `xTaskDelayUntil` | pode bloquear, entra na análise |
| Tempo preciso abaixo de alguns ms | timer de hardware + processamento adiado | resolução e jitter |

## Pratique
1. Um callback de timer chama `vTaskDelay(100)`. O que acontece com os outros timers?
2. A tarefa de serviço dos timers tem prioridade 1 e uma tarefa de prioridade 3 calcula durante 40 ms. Um timer de 10 ms expira nesse intervalo. Quando o callback roda?
3. Com tick de 32 bits, quantos bits de evento um event group oferece? E com tick de 16 bits?
4. Uma tarefa espera `BIT_A | BIT_B` com `xEsperarTodos = pdFALSE` e `xLimparAoSair = pdTRUE`. Só `BIT_A` é ligado. O que ela recebe e o que acontece com `BIT_B`?
5. Uma ISR chama `vTaskNotifyGiveFromISR` 4 vezes antes de a tarefa rodar. Que valor `ulTaskNotifyTake(pdTRUE, 0)` devolve? E se fosse `pdFALSE`?
6. Por que um event group é melhor que uma notificação para avisar 3 tarefas de que o Wi-Fi conectou?
7. Escolha o mecanismo: (a) apagar o display 30 s depois da última tecla; (b) ADC por DMA a 1 kHz avisando a tarefa de filtro; (c) a tarefa de rede precisa de "sensor calibrado E hora sincronizada"; (d) bytes da UART a 115 200 bit/s.
8. Quantos bytes de RAM a mais custam 6 semáforos binários num Cortex-M3, comparados com 6 notificações?

## Armadilhas comuns
- Bloquear no callback de um timer.
- Achar que `xTimerStart` acontece na hora: é um comando na fila; com a fila cheia e tempo de bloqueio 0, ele falha.
- Tarefa de serviço dos timers com prioridade baixa: callbacks atrasados por qualquer tarefa ocupada.
- Esperar precisão de microssegundos de um timer de software.
- Usar os 8 bits altos do event group (reservados).
- Não conferir o retorno de `xEventGroupWaitBits` (tempo esgotado parece sucesso).
- Notificar uma tarefa pelo handle antes de ela ser criada (handle NULL).
- Usar notificação como fila: valores sobrescritos ou perdidos.
- Esquecer que `ulTaskNotifyTake` devolve o valor **antes** de mudar.

## Gabarito
1. A tarefa de serviço fica bloqueada 100 ticks: **nenhum** outro callback roda nesse tempo, e os comandos se acumulam na fila de comandos.
2. Só quando a tarefa de prioridade 3 bloquear ou terminar os 40 ms: o callback atrasa até ~30 ms. Suba a prioridade da tarefa de serviço.
3. **24** bits (32 − 8); com 16 bits, **8**.
4. Recebe o valor com `BIT_A` ligado (a condição OU foi satisfeita). Ao sair, o kernel limpa os bits da máscara esperada (`BIT_A | BIT_B`): `BIT_A` volta a 0 e `BIT_B`, que já estava em 0, continua em 0.
5. `pdTRUE`: devolve **4** e zera. `pdFALSE`: devolve **4** e deixa 3 (as próximas chamadas devolvem 3, 2, 1 sem bloquear).
6. A notificação tem um receptor só; o event group acorda todas as tarefas que esperam o bit, de uma vez.
7. (a) timer de software one-shot com `xTimerReset` a cada tecla; (b) notificação (como contador) da ISR do DMA; (c) event group, esperando todos os bits; (d) fila de bytes ou stream buffer — ou DMA com IDLE e blocos.
8. 6 × 80 = **480 bytes** (mais o cabeçalho do heap de cada alocação); as notificações já estão no TCB: 0 bytes a mais.
